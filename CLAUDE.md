# Fabrik — Development Guide for Claude

## Project Overview

Fabrik is a Go CLI that orchestrates Claude Code through an SDLC pipeline defined on a GitHub Project board. Issues are the unit of work. The pipeline stages (Specify → Research → Plan → Implement → Review → Validate) are configured via YAML files.

## Build & Test

```bash
go build -o fabrik .     # Build
go test ./...            # Run all tests
go test -race ./...      # Run with race detector
go vet ./...             # Lint
```

### Four test layers (unit → sim e2e → wire-contract → live e2e)

The sim bed is a fast, free **pre-gate** — it is never a replacement for the live
integration suite, which has no substitute and is never reduced. See
`adrs/1454-sim-pre-gate-not-replacement.md` for the full decision.

| Layer | Where | Runs |
|---|---|---|
| `go test ./...` (unit) | repo-wide | every PR |
| sim e2e (`tests/sim`) | scenario-driven, deterministic, `-race`-clean, $0 tokens | every PR — no build tag, already inside `go test -race ./...`; also `scripts/sim/run.sh` for on-demand runs |
| github wire-contract tests (`github/wire_contract_test.go` + `github/testdata/`) | schema validation + recorded fixtures | every PR — no build tag, already inside `go test -race ./...` |
| live e2e (`tests/e2e`, `-tags e2e`) | real Claude, real review bots, real GitHub, real merge-queue semantics | release-gate only — CI compiles it but never runs it; `scripts/e2e/run.sh` (a shim over the Go gate runner in `tests/gate`, #1994; run standalone, or invoked from `scripts/cut-release.sh`) is the only thing that executes it, before every release. **Coverage-based (#1972):** the gate is accepted when every required (live test, leg) pair has a PASS in the per-SHA ledger (`.e2e-coverage/`, git-ignored), across any number of invocations — `run.sh --resume` runs only what is still missing, so an interrupted ~10-hour run is not thrown away. **Sparse auth × train matrix (#1975, ADR-1975):** every live test runs in one baseline cell (`app/on`) and in each other cell only if the registry marks it `sensitive` to what that cell changes (`auth`/`train` fields, no default); `E2E_MATRIX=full` restores the four full legs and should be used for a release that changes the auth layer, the landing path or the classification itself |

`scripts/e2e/run.sh` refuses to spend live budget (bed preflight, build, or any live
GitHub/Claude call) until the sim suite and the wire-contract tests pass first —
see the gate runner's `RunPregate` (`tests/gate/pregate.go`). `scripts/cut-release.sh` mirrors that ordering and makes the
live suite mandatory by default — accepting it on **accumulated coverage** (it asks
`run.sh coverage` first, resumes with `run.sh --clean --resume` if incomplete, and records
the engine SHA and invocation count in the release notes); `--skip-integration=<reason>` is
a loud, release-notes-recorded escape hatch, never a silent skip. See `tests/sim/README.md`
and `tests/e2e/README.md` for the full detail, including each layer's blind spots
(the sim's inability to see GitHub wire correctness, most prominently) and the
fidelity-drift policy: any live-e2e failure the sim passed is a fidelity bug in the
sim, fixed there as well as in the engine. Which live scenarios have a sim twin is
recorded per test in `tests/e2e/registry/registry.json` (ADR-1933) and enforced in plain
`go test ./...`; adding a live test requires adding its registry entry.

CI's layer-1 `go test` step runs the **whole module on every PR** — no `paths:` filter
and no dependency-graph test selection, by decision (`adrs/1857-no-per-pr-test-selection.md`,
which also records why `tests/sim/simgh` is not sharded). The release gate runs the full
suite by default; `scripts/cut-release.sh`'s `--skip-tests` is a last-resort escape hatch
that skips the `go test -race ./...` step (with a warning), never a narrowed run.

## Documentation bundle (docs/llms-full.txt)

When you modify any of the canonical doc pages — `docs/USER_GUIDE.md`, `docs/state-machine.md`, `docs/stage-lifecycle.md`, or `docs/positioning.md` — you MUST regenerate `docs/llms-full.txt` in the same commit:

```bash
bash scripts/generate-llms-full.sh
git add docs/llms-full.txt
```

CI's `docs-drift` workflow (`.github/workflows/docs-drift.yml`) runs the regen and fails the PR if the committed bundle differs from the regen output. Forgetting the regen costs an extra round-trip; doing it consistently keeps PRs green on first push. This requirement applies to **every** stage (Specify, Research, Plan, Implement, Review, Validate) — wherever a doc edit happens, the bundle must follow.

## Architecture

- `cmd/root.go` — CLI entry point, flag parsing, .env loading
- `engine/engine.go` — Engine struct, Config, construction, Run() entry point
- `engine/github_app_auth.go` — GitHub App installation authentication (#1713), co-equal with the PAT path: all-or-nothing config validation (`validateGitHubAppConfig`, R5), the GHES+App-auth mutual refusal, `engineRequiredGitHubAppPermissions` (the engine's own hand-maintained required-permission set — distinct from Pruefer's, since `internal/githubauth`'s `Options.RequiredPermissions` is caller-supplied, not package-owned), the R4 user-owned-board refusal (via `(*gh.Client).ResolveOwner`, not `ProjectBoard.OwnerType` — the latter merely echoes a caller-supplied argument in the common case), and the R3 fail-hard grant check (via the new `(*githubauth.Reconciler).VerifyGrants`, additive to that package's existing soft `verifyPinnedGrants` from ADR-1709 — same comparison primitives, different caller severity). Called synchronously from `New()` (not `Run()`), since `e.readClient` captures whichever concrete client is live at that point; only the resulting `Reconciler`'s refresh-loop goroutines need a real `ctx`, started later from `Run()`. See ADR-1713. `setUpGitHubAppAuth` also forwards `Config.NoBrowser` into `githubauth.Options.NoBrowser` (#1763) — defaulted to `true` (suppressed) by `cmd/root.go`'s `--no-browser`/`FABRIK_NO_BROWSER`/`no_browser` resolution, the inverse of Pruefer's own `no_browser` default, since a long-running daemon is a bad place for an unconditional browser-open. Structurally unreachable in the engine's current all-or-nothing pinned-installation runtime (the non-pinned discovery branch that would open one is never entered), but exercised by tests via `internal/githubauth`'s `Options.OpenBrowser` seam — see ADR-1763. **Optional-permission advisory (#2071, ADR-2071):** after the fail-hard check, `setUpGitHubAppAuth` (and `fabrik init`'s `runGitHubAppSetup`) makes a second, soft `VerifyGrants(OptionalGitHubAppPermissions())` call and prints one advisory notice per shortfall, built by `OptionalPermissionNotices` from the `optionalPermissions` descriptors that also feed the new-App manifest; a failed read is one warning line, never fatal.
- `engine/app_identity.go` — the App-mode identity (#1893), replacing the operator `cfg.User` for everything but PAT mode: `lockIdentity()`/`lockLabel()` (`cfg.User` in PAT mode; `<slug>-<6-hex hash of hostname+fabrikDir>` under App auth, ≤29-char slug so `fabrik:locked:<id>` fits GitHub's 50-char label limit and two local instances of one App never share a lock label), `commitIdentity()` (`<slug>[bot]` / `<bot-user-id>+<slug>[bot]@users.noreply.github.com`, ID from `GET /users/<slug>[bot]` resolved once in `New()` and fail-soft to the ID-less email; written to bare clones by `setAppCommitterIdentity` with `fabrik.managed-name`/`fabrik.managed-email` marker keys so a Fabrik-written operator identity is replaced but an operator-chosen one never is), `mentionTargets(item)` (awaiting-input @mentions: human assignees → human author → nobody; bot logins and the App itself excluded), `spawnAssignees(item)`, `operatorNote()`, and the one-shot legacy `fabrik:locked:<cfg.User>` sweep in `runStartupCleanup`. Every accessor returns today's `cfg.User`-based value when `e.ghAppAuth == nil`, so PAT mode is unchanged by construction. `New()` also zeroes `cfg.Token` under App auth (no PAT structurally), `releaseUpgradeToken` returns `""`, and a still-configured `user:` is tolerated but ignored (logged). `selfLogin()` is a *separate* concern (the login Fabrik posts as) and must not be used for lock labels. See ADR-1893 and `docs/state-machine.md` §7.4.
- `engine/poll.go` — Main poll loop, idle-upgrade, concurrent worker dispatch. `Run()` also starts and joins the GitHub App auth refresh loop (`e.ghAppAuth.RunRefreshLoops`, #1713) when App auth is configured — its `defer wait()` is registered before `defer cancel()` so that on shutdown, context cancellation always precedes (and unblocks) the wait, itself ordered ahead of the log-file-close defer.
- `engine/item.go` — Per-issue processing: stage runs, comment processing, blocking/pausing
- `engine/pr.go` — Output posting: issue comments, PR comments, summary extraction
- `engine/feedback_gate.go` — the single live "is anything unprocessed on this item?" predicate (`unprocessedFeedback`) and its fail-closed gate (`feedbackGateBlocks`, #1953): consulted at `attemptMergeOnValidate`, `handleStageComplete`'s advance and `runCatchUpPhase2`'s non-Validate advance; logs `[#N feedback-gate] holding …` with the feedback IDs and records a `feedback-pending` cooldown. See ADR-1953-a.
- `engine/spec_persist.go` — Specify spec persistence (#2034, ADR 2034): when a stage sets `persist_spec: true`, `persistSpec` projects the stage's canonical `FABRIK_ISSUE_UPDATE` body to `specs/<issue>-<slug>/spec.md` and commits that single file (pathspec-scoped; `## Open Questions` stripped; slug derived once from the title and then locked by reusing any existing `specs/<issue>-*/` directory; no empty commits; errors non-fatal). Called from `finalizeStageOutcome` (the existing post-run push carries it) and `publishCommentOutput` (pushes only when a commit was made); skipped on `FABRIK_NO_WORK_NEEDED`. The stage stays `read_only: true` — the engine, not Claude, does the write. `commitsAheadOfBase` ignores commits touching only the item's own spec (`isSpecOnlyCommit`) so #921's empty-coordinator rule still fires. See `docs/state-machine.md` §7.16.
- `engine/comments.go` — Comment detection and filtering logic. `processCommentsClassified` also hosts the post-merge guard (`engine/post_merge_comments.go`, #1862): once an item's work has landed (merged linked PR, or a merge-train member's `fabrik:credited-pr:<N>`/`fabrik:awaiting-landing-verification`) it runs no worker, pushes nothing and adds no 🚀, and answers each human comment once with a marker-deduped "not applied" reply. `engine/feedback_gate.go`'s `feedbackGateBlocks` (#1953; it replaced the comment-only `commentGateBlocksLanding`) is the matching gate at `attemptMergeOnValidate`'s landing decision and at stage advance, covering comments, unresolved review threads and unaddressed review bodies read live, returning `deferred=true` at landing — see ADR-1862, ADR-1953-a and `docs/state-machine.md` §2.2/§6.6.6
- `engine/context.go` — Context files (.fabrik-context/) and stage comment lookup
- `engine/repo.go` — Per-repo identity helpers (parseOwnerRepo, repoName, issueKey)
- `engine/claude.go` — Claude Code invocation, prompt building, marker extraction
- `engine/worktree.go` — Git worktree lifecycle (create, update, push, cleanup)
- `engine/merge_train.go` — Merge-train worker: trial branch assembly, inline conflict resolution, integration PR creation and CI polling (ADR-059 D3). Since #1648, Queued members are partitioned by resolved base branch (`engine/poll.go`'s `groupQueuedByRepoAndBase`) and one independent worker runs per (repo, base) partition, not one per repo — `dispatchMergeTrainWorker`/`prepareTrainWorker` take the partition's already-resolved base explicitly rather than calling `wm.DefaultBaseBranch()` unconditionally, and every guard/counter (`mergeTrainInFlight`, the runaway guard's trial counters, `store.repoWorkers`) is keyed on the composite `mergeTrainKey(repoKey, baseBranch)` (`defaultPartitionBase`, the empty-string sentinel, for the common no-`base:`-label case — collapses to the bare `repoKey`, byte-identical to pre-#1648 behavior) instead of bare `repoKey`. See ADR-1648. `runMergeTrainWorker`'s re-form loop checks `trySingletonFastPath` on every iteration where the batch is down to exactly one member, before building a trial: when the pinned base SHA is a fast-forward ancestor of the member's head, the member's own PR is mergeable, and its own CI is green and complete (`singletonFastPathEligible`, reusing ADR-1153/ADR-1441's classifiers unmodified), it lands the member's own PR directly (`MergePRAtHeadSHA`, pinned to the validated head SHA to close the TOCTOU gap of merging an externally-writable branch — the first merge-train landing path to do so — then `finishSingletonFastPathLanding`) instead of assembling and re-validating a trial — skipping is gated strictly on positive evidence, any ambiguity falls through to the unchanged trial path. `applyPendingReviewEjects` (#1208, and the #1863 comment-eject signal) is applied to the singleton member before the fast path is even considered — a fourth checkpoint alongside its three pre-existing ones, needed because the fast path never calls `assembleAndValidate` and so would otherwise bypass all of them. See ADR-1644 and `docs/state-machine.md` §6.20. Immediately before either `landMergeTrainBatch` or `landSingleton` opens or reuses an integration/landing PR, `refuseIfBaseContradictsMembers` (#1773) refuses to proceed if the pinned base is the repository default while any batch member's **live** `base:<branch>` label (`e.client.FetchLabels`, never the cached `trainMember.item.Labels` and never `e.readClient`, which is boardcache-backed) declares a different base, or if that live read errors — leaving members in Queued and logging loudly rather than repairing. A second, independent line of defence against the #1688 incident class, deliberately not sharing code with #1772's partition-time fix; a no-op on any non-default-base partition and on a healthy default-base batch. `landMergeTrainBatch`'s call is additionally skipped when the found `integrationPR` is already merged (the FR-2 restart-safety state) — nothing is being opened or reused there, so refusing would only strand an already-landed batch in Queued forever with no protective benefit. See ADR-1773 and `docs/state-machine.md` §6.24. At fresh batch formation only, `prepareTrainWorker` runs `admitTrainMembers` (`engine/merge_train_admission.go`, #1821) right after `fetchTrainMembers`: each member's own-PR check-runs (live `e.client.FetchCheckRuns` at the snapshotted head SHA) are classified by `classifyLandingCI` unmodified, and only a confirmed `TrainCIRed` is deferred — routed off `Queued` via `rerouteQueuedMemberOffHolding` (ADR-1208's reroute-before-side-effects), never paused and never counted toward `MaxMergeTrainEjections` — while pending/green/zero-runs/read-error all admit (fail-open, the inverse of the singleton fast path's fail-closed polarity). Skipped entirely unless the stage before the holding stage has `wait_for_ci: true` (nothing else would re-detect a deferred member). Never reached by the restart-reconstruction paths, bisection, `landOneAtATime`, or `landGreenBatch`. See ADR-1821 and `docs/state-machine.md` §6.25. The two "resume an interrupted landing" branches — `completeDeferredLanding` (Route 1 of `reconstructTrainState`, per member) and the `pr.Merged` branch of `trySingletonFastPath` — first call `liveLandingState` (#1871), a live `e.client.FetchProjectItemStatus` read (never the batch's snapshot `item.Status`/`Labels`, nor `e.readClient`): a non-empty, non-holding live Status means the landing already completed after the board snapshot was read and is skipped (no Done move, close, comment or label write); a holding or empty Status resumes; a read error defers to the next poll (fail-closed — both branches re-run every poll, so nothing is stranded). Closes the duplicate-landing race where a fresh worker dispatches from a pre-landing snapshot right after `finishTrain` releases the in-flight marker. The same read also runs at fresh batch formation (`dropLiveLandedMembers`, after `fetchTrainMembers`, before `admitTrainMembers`): live-moved members are dropped and read-failed members excluded from that batch only, so a stale snapshot listing several just-landed members cannot reach a trial and be re-landed; one live read per member per formation. `landSingleton`'s stale-Queued case is a known untraced gap. See ADR-1871 and `docs/state-machine.md` §6.28. A length-1 batch that `trySingletonFastPath` declines only because the member is *behind* the pinned base goes to `trySingletonCatchUp` (#2044, `engine/merge_train_catchup.go`) before any trial is built: it merges the pinned base SHA into the member's own `fabrik/issue-N` branch (merge commit, `--force-with-lease=<ref>:<head>` push, in the member's own worktree), waits in-worker for the member PR's own CI and re-enters `trySingletonFastPath` on the new head. See the `engine/merge_train_catchup.go` bullet below. **CI infrastructure (#2052, ADR 2052):** `pollTrainCI` reads `FetchWorkflowRuns` on the zero-check-run path *before* the zero-check green shortcut; a `startup_failure`/zero-job `failure` run is retriggered by `retriggerPR` (close then immediately reopen the trial PR, `maxCIRetriggers` = 2, `startupWatch` counting only runs absent from the last retrigger's baseline) and then abandoned as the new `TrainCIInfra` result — a distinct value so no call site can charge it (`assembleAndValidate` skips `recordTrial`), bisect it (`bisect`/`handleRedBatch` abort the episode) or read it as green; members stay Queued and `dispatchMergeTrainWorker` holds the partition off for `trainInfraAbandonCooldown`. The first confirmed check-run failure re-runs the failed jobs once (`RerunFailedJobs`, run IDs from `DetailsURL`) before `TrainCIRed`, with a stale-failure guard on check-run IDs. The stage `wait_for_ci` gate has the same handling via `settlePRMergeStateForCIGate` → `PRSettleResult.StartupFailure` → `pauseForCIStartupFailure`. See `docs/state-machine.md` §6.29, `engine/ci_startup.go`.
- `engine/merge_train_catchup.go`, `engine/worktree_catchup.go`, `engine/catchup_feedback.go` — the merge-train **singleton catch-up** (#2044, ADR-2044, `docs/state-machine.md` §6.30). `trySingletonCatchUp` runs in `runMergeTrainWorker`'s length-1 branch after a declined fast path and before the trial (never inside `assembleAndValidate`; `landOneAtATime` and batches of 2+ keep trials). Gated on `singleton_catch_up: merge|off` (default `merge`; `--singleton-catch-up`/`FABRIK_SINGLETON_CATCH_UP`, classified in `internal/workerenv.Scrubbed`), the per-member attempt cap (`effectiveMaxTrainRebaseCycles()`, in memory) and R4 ownership (`catchUpBusyReason`: in-flight worker, live `fabrik:editing`, then `PrepareCatchUp`'s dirty/mid-merge/remote-moved checks → *defer*, uncharged). `runCatchUpGit` merges `p.baseSHA` (two-parent shape verified, conflicts via `resolveTrainConflict` with `InvokeOptions.CatchUpBaseSHA` re-wording the prompt), stamps the audit-only `Fabrik-Train-Catch-Up` trailer and pushes through `PushCatchUp` (compare-and-swap lease; also advances the tracking ref); any failure restores the worktree. Push rejected / CI never starting / bad merge shape / cap → the trial, **uncharged** (no `recordTrial`, ejection count or pause); only an unresolvable conflict ejects and only a confirmed red (`ejectRedCatchUpSingleton`, after one failed-job re-run) pauses. `waitMemberCI` never retriggers (closes/reopens) the member's PR. **Review churn (R3):** `postCatchUpMarker` posts a self-authored `<!-- fabrik:train-catch-up head= base= pure= -->` comment; `dropCatchUpFeedback` (called from `queuedReviewFindings` and `unprocessedFeedback`) suppresses a *bot* review/thread finding only when the marker is the engine's own, its head is the PR's live head, `pure=true`, and the finding's `commit.oid`/`originalCommit.oid` (`PRReview.CommitID`/`Comment.CommitOID`, now selected by the board query) equals that head — **the commit trailer is never trusted** (the branch is writable by anyone). `trainCatchUpGitFn` is the test seam for the git half. **Policy memo (#2065, ADR-2065, `engine/catchup_policy.go`):** `PushCatchUp` returns a typed `*CatchUpPushError`; `classifyCatchUpPushRejection` calls a rejection policy only on a positive `GH006`/`GH013` marker (lease/transport markers veto; a secrets-mentioning `GH013` is ambiguous). `runCatchUpGit` then sets `catchUpGitOutcome.policyReason`, and `trySingletonCatchUp` records an in-memory per-`owner/repo` memo (`catchUpPolicyMemoTTL` 24h on `e.now()`, cleared on restart, never persisted) with one operator log line; while it is active the catch-up is skipped before `FetchCommitsBehind` and the trial path is taken, uncharged. `catchUpPolicyMemoSkipDisabledForTest` is the neutralisation seam.
- `engine/ci_settle.go` — `settleAwaitingCIScan`: the per-poll settle scan that owns `fabrik:awaiting-ci` items, sourced directly from `board.Items` so it is independent of `itemMayNeedWork`/`selectDeepFetchCandidates` admission (the fifth instance of the "dedicated settle scan" pattern — ADR-1270). Runs the shared `catchUpPhase1Handlers` chain, primes the store with a live check-run read (`RefreshCheckRunsLive`) so a stale cached PENDING classification cannot wedge the item, and applies an **unconditional `CIWaitTimeout` backstop** ahead of the handler chain so an item escalates even when some gate claims it before `checkCIGate` is ever reached. The main poll loop deliberately no longer processes these items (`poll.go` admits `hasComplete`-only); see ADR-1270 and #1303/#1325. The backstop is anchored on the later of the label's applied time and the item's latest `fabrik:paused` removal (`FetchLabelRemovedAt`, read live from the event log; an unreadable time falls back to the label anchor and still escalates), and never escalates blind: not while a worker for the item is in flight, and not on its first evaluation since the daemon started (`ciBackstopLiveEvaluated`, in memory) — the live-data chain runs first (#2059, ADR-2059, `docs/state-machine.md` §6.14.6).
- `engine/ci_flake_rerun.go` — the stage `wait_for_ci` gate's flake re-run (#2072, ADR 2072): `ciFlakeRerun`, called from `handleMergeAndCIGates`' `ciFailure` branch ahead of the `ci-fix-reinvoke` dispatch, re-runs the failed Actions jobs (the train's `rerunFailedWorkflowRuns`) at most once per PR head before the first dispatch (R1) and once after a recorded no-op fix (R2), claiming the item while it waits. State is `Engine.flakeReruns` (head-keyed, `flakeRerunMu`, budget marked before the API call); the stale-failure guard stores the failed check-run IDs across polls (`decideFlakeRerun`); `ErrForbidden`/no Actions run degrades to today's dispatch, once per head, never a pause. No comment is posted. See `docs/state-machine.md` §6.29.
- `engine/ci_suites.go` — `ciSuiteHold` (#1822): the single suite-aware completeness primitive every "green and complete" judgement for a PR head consults — `settlePRMergeState` (rules 9/18/19), `classifyLandingCI` (and through it `singletonFastPathEligible`) and `pollTrainCI`. A live, uncached `FetchCheckSuites` read (the `check_suite` webhook is a no-op) feeds `gh.OutstandingCheckSuites`: a non-`completed` suite holds the gate if it has produced check runs, or has none yet but is younger than the post-push dwell (anchored on the suite's `created_at`); an old run-less suite is inert and ignored, so it can never deadlock. A read error holds (fail-safe). The hold is `PRMergeUnsettled` with `MergeableState` omitted, so it is bounded by `CIBackstopTimeout`; `pauseForCITimeout` names the stuck suite. See ADR-1822 and `docs/state-machine.md` §6.4.
- `engine/queued_review_settle.go` — `settleQueuedReviewFindings`: the per-poll settle scan that detects unresolved review-thread feedback arriving on a Queued merge-train member's linked PR — and, when there is none, an **unprocessed human comment** (`settleQueuedCommentCause`, #1863: `filterHuman(findNewComments(item))`, the same predicate as the landing gate with the human restriction layered on top) — a window the `HoldingStage` exclusion otherwise blacks out entirely; the comment cause ejects through `ejectQueuedMemberForComments` (reroute first, then one `🏭` comment; never `ejectMember`, so no `MaxMergeTrainEjections` count, no pause, no `ReviewCycles` change) and a parallel `queuedCommentEjects` signal consumed by `applyPendingReviewEjects` — see ADR-1863. It is the sixth instance of the "dedicated settle scan" pattern — ADR-1270. The review-finding half ejects a flagged member off `Queued` via `ejectMember`/`ejectQueuedMemberForReviewFindings` (`engine/merge_train.go`) so the ordinary review-reinvoke path can address the finding, either directly (no merge-train worker in flight for the repo) or via a mutex-guarded pending-eject signal the worker itself consumes at its own checkpoints (`applyPendingReviewEjects`, mirroring the runaway guard's "poll writes a signal, worker checks it at a checkpoint" shape) when one is. See ADR-1208, `docs/state-machine.md` §6.16, and #1208.

- `internal/sessionreap/` — Worker process-tree reap (#1989), shared by `engine` and `pruefer` (neither imports the other; logging goes through a caller-supplied `Logger`). The target set is `{worker SID} ∪ {command-session SIDs}`: Claude's Bash tool runs every command through a shell that calls `setsid()`, so each command leads a session of its own that the worker's SID never reaches (observed live; the first version of #1989 and the #1798/#1814 `Getsid == worker PID` filters all missed it). `Discover` walks the PPID chain from the worker while it is alive and names every non-worker SID below it; `Tracker` samples that on a cadence (`commandSessionSampleInterval`) because the chain is gone once the worker exits, and is found by `Escalate`/`Sweep` through a registry keyed on worker PID. Discovery runs only while the worker's PID still carries the start-time token captured right after `cmd.Start()`; a command session's SID is trusted only while it provably names the sampled session (`ValidSession`: leader gone, or live with the recorded start token — else a recycled PID that became a leader would alias an unrelated session). Members are found by `unix.Getsid` over one process listing (`/proc` on Linux, `kern.proc.all` sysctl on macOS), zombies excluded; R4 refusals (SID 0, 1, the caller's own) apply to every SID in the set, plus a per-signal `Getsid` re-check and a per-session recycled-leader watch. `engine/procattr_unix.go`'s `killProcGroupGraceful` delegates to `Escalate` (SIGINT → grace → SIGTERM → grace → SIGKILL over the whole set); `runClaude` starts the tracker after `beginWorkerRecord` (`engine/command_sessions_unix.go`), runs `reapWorkerSession` (`Sweep`, no discovery) right after `killProcGroup` and ahead of the #1798/#1814 reapers, then `finishCommandSessions`. Each sampled command session is persisted in `workers.json` as a child record (`parent_id`, `start_token`) that `sweepOrphanedWorkerSessions` reaps only once the parent worker is confirmed gone — never as if it were a worker. `Options.WorkerSIDOnly` is the neutralisation seam the twin tests use. Pruefer starts Claude with `Setsid` for the same reason. A command that orphans itself between two samples, with the worker then exiting cleanly, is the residual gap (ADR 063's cwd reaper is the cover). See ADR-1989 and `docs/stage-lifecycle.md` "Kill escalation". `SignalGroup` (#1957) is the single ownership-checked entry point for every stored-PID `kill(-pid, …)` — both `killProcGroup` copies (and through them the webhook manager, whose subprocess start token is recorded with `RecordStart`) and this package's own listing-failure fallbacks: it refuses `0`/`1`/the caller's own group first (R4), then requires a live holder of the PID to lead its own group and match the recorded start token (or be our child), and allows a reaped leader only while its group is still populated (POSIX never reuses a PID that names a live group); anything unconfirmed is skipped and logged, never widened. The bash twin is `scripts/lib/killgroup.sh` (`kill_own_group`/`kill_own_pid`), used only by `scripts/sim/run.sh` (the e2e gate runner is Go since #1994 and sends no negative-PID group signal: it reaps through `sessionreap.Escalate` and sends a single-PID SIGTERM in `tests/gate/exec_unix.go`). See ADR-1957.

A tool failure — including `Fabrik daemon not running at <path>` — is an `isError` tool *result* and every daemon call is bounded by a timeout, so an absent or wedged daemon never hangs the session; JSON-RPC errors are for protocol problems only. **Channels (#1968, `channel.go`):** `initialize` declares `experimental["claude/channel"]`; with `--subscriber`/`FABRIK_SUBSCRIBER` set (no generated default) the shim starts `RunStream` after `notifications/initialized` and writes each event as `notifications/claude/channel` (`channelNotification`: string meta values, identifier-only keys), and turns the stream's drop/recovery into the live-only `daemon-unreachable` (after a 10 s grace) / `daemon-reachable`; `fabrik_subscribe`/`fabrik_unsubscribe` are the first tools that change daemon state (not `readOnlyHint`; `exclude_labels` absent vs `[]` stays distinct). Everything tied to the preview contract is in `channel.go`. `--stall-threshold`/`FABRIK_STALL_THRESHOLD` (`Config.StallThreshold`, default 30m) is the only engine config it adds.
- `engine/localapi.go`, `engine/localapi_server.go`, `engine/daemon_health.go` — the engine side of the local API (#1967, ADR-1966-a). `LocalAPIBackend()` serves `Status`/`Board`/`Health` **strictly from the Store (via `Peek`/`Scan`), already-guarded engine state and `daemonHealth`** — never `e.client`, `e.readClient`, `Store.Get` or the engine's `labelAppliedAt` (live `FetchLabelAppliedAt` fallback); `TestLocalAPISourceDoesNotReachGitHub` forbids those identifiers in `engine/localapi*.go` and a nil-client test proves zero GitHub calls. `daemonHealth` is the mutex-guarded mirror of the poll loop's single-goroutine fields (`lastPollAttemptAt`, `backoff*`) plus process start, last poll success, last reconcile success and last webhook delivery, published at their existing write sites (`PollWithBackoff`, `PollOnce`, `reconcileTick`, the two `deltaFn` closures) — API goroutines read only the mirror. Merge-train position is a label-based approximation (cached `base:` label, `(StatusEnteredAt, Number)` order, no `WorktreeManager`). `Run()` calls `startLocalAPI` after the instance lock and the webhook manager are set and before the first poll (non-fatal on bind failure), `defer closeLocalAPI`, and `performSighupRestart` closes it before the exec; startup's stale-socket replacement is the backstop for the self-upgrade exec and crashes.
- `engine/overseer_actions.go` + `internal/localapi` action methods + `internal/mcpstdio` action tools — the overseer actions (#1969, ADR-1966-c), the first part of the local API that writes to GitHub: `fabrik_promote`/`fabrik_set_autonomy`/`fabrik_revalidate`/`fabrik_clear_claude_limit`. A separate optional `localapi.Actor` interface beside the read `Backend` (the `Streamer` precedent), dispatched by `Server.handleAction` only — a server with no `Actor` answers `unknown_method` and `hello` omits the methods; refusals are `CodeRefused` carrying the item's current state in `Error.Data`. The engine side deliberately lives in `overseer_actions.go`, **not** `localapi*.go`/`channel_*.go`, so the read-path static scans (`TestLocalAPISourceDoesNotReachGitHub`, the channel scan) stay unweakened and keep forbidding `e.client` there. No new engine transition: each action reuses one the engine has (board Status move out of an unmanaged column via `moveItemToStatus` — IDs from the board cache's `ProjectID()`, the store's `ItemID` and `e.statusField`, never a per-call lookup; the autonomy labels; the one-shot `fabrik:revalidate`/`fabrik:clear-claude-limit` command labels), writing through `addLabelChecked`/`removeLabelChecked`/`postComment`. Guards: one managed open non-PR item, unknown facts refuse, `promote` and `revalidate` confirm the column with one live ID-keyed `FetchProjectItemStatus` (fail closed); `revalidate` refuses a paused item (it would clear the pause) and there is **no tool that lifts a pause or posts a free-form comment** — only a human comment after the pause does (ADR-1813). `set_autonomy` yields exactly the requested mode (add before remove). Every action requires the shim's `--subscriber` name (no per-call override), sanitised to `[A-Za-z0-9._:/-]` ≤64 chars, and posts one `🏭 **Fabrik — overseer action: <action>**` audit comment built by `overseerAuditBody` — the exact `🏭 **Fabrik` prefix is the only thing keeping it from being steering under PAT auth (the compliance scan lists `overseerAuditBody`; tests pin `findNewComments`/`resumeAuthorised`/`feedbackGateBlocks` and a `tests/sim` run). Write first, then comment; a failed comment leaves the action standing (`audit_comment: failed`). The socket is unauthenticated, so the name is an advisory audit aid. `Engine.OverseerActorForTest` is the tests/sim seam. See ADR-1966-c and `docs/state-machine.md` §7.15.
- `internal/channelevents/` — the engine-independent core of the MCP channel push (#1968, ADR-1966-b): the event catalogue (`EventType`, which are immediate / account-wide / shim-generated / synthetic), `Subscription` and its matching (dimensions ANDed, list entries ORed; `GlobMatch` where `*` crosses `:` and `/`; label patterns apply to label events only; `DefaultExcludeLabels` unless `ExcludeLabels` is a non-nil empty slice; an unknown milestone never matches a milestone scope; account-wide events ignore repo/issue/milestone), the persisted `Hub` (`subscriptions.json`, one `held-<hash>.json` per subscriber, `dedup.json` with settle-episode counters — tmp+rename writes, corrupt files quarantined) and the per-subscriber held queue (bounded, oldest dropped with one coalesced `events-dropped` notice, deduplicated on `Event.DedupKey`, age/TTL pruned, digest entries batched). `Hub.Publish` appends to the queue before any delivery and never blocks on a session; an attached session's drain loop sends in order and removes an entry only after a successful write; a second `Attach` under a name supersedes the first. It imports nothing from the engine, the store or GitHub. See `docs/state-machine.md` §7.14.
- `engine/channel_events.go`, `engine/channel_derive.go`, `engine/channel_settled.go`, `engine/channel_catchup.go`, `engine/channel_hooks.go`, `engine/channel_backend.go`, `engine/channel_seam.go` — the engine side of the channel push (#1968). One `itemstate` observer (`channelEvents.onChange`) only appends to a queue — label events from `Change.LabelDeltas` with an actor (`fabrik`/`human`/`bot`/`unknown`, `labelActor`), the label-derived `merged`/`blocker-cleared`/`landing-verification-failed`, and a debounced re-evaluation request; one consumer goroutine owns every piece of per-item memory and is the only publisher. State-derived events come from `internal/attention` (pause family and `stalled` are transitions into its states, with the one `--stall-threshold`), `awaiting-input-stale`, `cycle-limit-near` and the Claude suspension edge (ticker for a lazy lift). `validate-settled` is anchored at the engine's own settle point — `noteValidateSettled` at the top of `runCatchUpPhase2` (before the autonomy gate, so cruise is covered) and `noteValidateLanding` in `attemptMergeOnValidate` after its gates passed (yolo lands inside that call) — confirmed by a cache-only predicate (`validateSettledSnap`, feedback via `cachedPendingFeedback`, built on the pure cores `filterNewComments`/`filterReviewThreadComments`/`dropOutdatedThreadComments`/`reviewBodyCandidates` shared with the live feedback gate) and captured on the calling goroutine. Hooks (`emitCITimeout`, `emitReviewTimeout`, `emitChildrenSpawned`, `emitTrainEvent`, `channelNudge`) are nil-safe void calls after the engine's own writes. `channelStreamer` implements `localapi.Streamer` over the hub. **R9/R10:** these files read item state only through `Peek`/`Scan` and never `e.client`, `e.readClient`, `Store.Get`, `labelAppliedAt` or the live feedback/review gates — `TestChannelEventsSourceDoesNotReachGitHub` enforces it and `TestChannelEventsAreObservationOnly` (tests/sim) shows a run with a hub makes the same GitHub mutations as one without. `channel_seam.go` is the test seam tests/sim uses (`StartChannelEventsForTest`, `SetChannelTimingForTest`). `Run()` starts the hub before `startLocalAPI` and closes it after the socket; `performSighupRestart` closes it before the exec (state is already on disk). **Review follow-ups:** a yolo `validate-settled` is captured at the landing decision but announced only if the merge/enqueue succeeded (`settleLanding.finish`), and `fabrik:rebase-needed` ends the episode; `catch_up=true` snapshots (`channel_catchup.go`, built from `Peek`/`Scan`, no dedup key) go to a new subscription and to a session's first attach (`attach {catch_up}`, never a reconnect); held-queue overflow evicts non-immediate entries first and the `events-dropped` notice names the dropped types; the self-upgrade exec flushes (never closes) the hub through `selfupgrade`'s `PreExecHook`; a superseded shim emits one `stream-superseded` notice.

> **Editing built-in skills**: modify `plugin/fabrik-workflows/skills/<name>/SKILL.md` — the embedded source baked into the binary, and the only place an edit ships to other users. `.fabrik/plugin/` is the local deployed copy written by `fabrik init`; it is not tracked in git. An edit there is **detected, not discarded**: `CheckPluginState` flags it as a customization, `fabrik upgrade` then refuses with `--force`/`--reconcile` options rather than overwriting, and startup warns naming the differing files. So a `.fabrik/plugin/` edit does not vanish — it blocks your next upgrade until you reconcile it, which is the more common way to lose time on this.

## Key Patterns

### Reaction Flow
- 👀 (eyes) = comment acknowledged, processing started
- 🚀 (rocket) = comment processed successfully
- The rocket reaction is checked on restart to avoid reprocessing — it's durable state
- Review bodies are reacted to as well (#1953 R8): REST has no reactions endpoint for a pull-request review, so the synthetic `review-body:<id>` comment (no `DatabaseID`, but a `ReactionNodeID`) gets 👀/🚀 through GraphQL `addReaction` (`AddReviewReaction`). That reaction is only the human-visible signal — the durable "addressed" state for a review body stays the #1555 `review-ids-addressed` marker, and dedup never depends on a reaction. A failed reaction is logged and non-fatal.

### Markers in Claude Output
- `FABRIK_STAGE_COMPLETE` — Claude signals stage completion (must be on its own line)
- `FABRIK_BLOCKED_ON_INPUT` — Claude signals it needs user input before the stage can continue; mutually exclusive with `FABRIK_STAGE_COMPLETE`
- `FABRIK_ISSUE_UPDATE_BEGIN` / `FABRIK_ISSUE_UPDATE_END` — Updated issue body from comment processing
- `FABRIK_SUMMARY_BEGIN` / `FABRIK_SUMMARY_END` — Brief summary for issue when detailed output goes to PR

### Context Files

Before each stage invocation, the engine writes context documents to `.fabrik-context/` in the worktree:
- `.fabrik-context/issue.md` — the issue body (spec)
- `.fabrik-context/stage-<Name>.md` — output from prior stages
- `.fabrik-context/pr-description.md` — linked PR description (for `post_to_pr` stages)
- `.fabrik-context/ci-status.md` — PR head SHA and the engine's green-and-complete CI verdict for that head (`green`/`red`/`pending`/`none`/`unknown`), plus `ci_gated`; written when the item has a linked open PR (#1997). The test-running skills skip a redundant local full-suite run only on `green` + `HEAD == head_sha` + clean tree
- `.fabrik-context/codebase-changes.md` — files changed on `origin/<baseBranch>` since the last stage ran (generated by `context.go`; omitted when no prior stage or when SHAs match)

### Concurrency
- Workers dispatch via semaphore (`MaxConcurrent`, default 5)
- `processedSet` protected by `sync.Mutex`
- Worktree creation serialized by mutex (git config isn't concurrent-safe)
- In-flight issues tracked via `sync.Map` to prevent duplicate dispatch

### Worktrees
- Each managed repo is always bare-cloned to `.fabrik/repos/<owner>-<repo>.git` on first access
- Each issue gets `.fabrik/worktrees/<owner>-<repo>/issue-N/` on branch `fabrik/issue-N`
- `fabrikDir` (where `.fabrik/` config, stages, and plugin live) is always `os.Getwd()`
- NEVER destroy worktrees with existing content — they may have partial work
- `updateWorktreeFromMain` fetches and merges origin/main; leaves conflicts for Claude
- Dirty worktrees (uncommitted changes) skip the update

### PR Lifecycle
- Implement creates draft PR with `Closes #N` in body (links PR to issue)
- `closedByPullRequestsReferences` in GraphQL traverses issue → linked PRs → PR comments
- `post_to_pr` stages post detailed output on PR, summary on issue
- PR marked ready after Implement completes (triggers external review bots)

### Claude Subprocess Environment
- Every Claude worker invocation's environment is scrubbed of the Anthropic/Claude-Code auth namespace by default (`ANTHROPIC_*` wildcard plus an enumerated `CLAUDE_CODE_*` auth-selector list) so no ambient credential can silently redirect a stage from subscription billing to metered API billing
- `FABRIK_ANTHROPIC_API_KEY` is the only supported opt-in for API billing (translated to `ANTHROPIC_API_KEY`); `FABRIK_ANTHROPIC_ENV_PASSTHROUGH` is a narrow, explicitly-named allow-list escape hatch for the long tail (Bedrock/Vertex selectors, etc.) — neither is itself forwarded to the worker
- `apiKeyHelper` (a `settings.json` key, not an env var) is refused outright: hard-fail at startup if present anywhere in the resolved settings chain, and per-invocation if present in a worktree's own `.claude/settings.json` or `settings.local.json`
- `GH_HOST` is emitted alongside `GH_TOKEN`/`GITHUB_TOKEN` when a GHES host is configured (`ghes_host` / `FABRIK_GHES_HOST`), so a stage worker's ambient `gh` invocations (e.g. `fabrik-validate`'s Pre-Completion Gate) target the same GitHub instance as the engine; omitted entirely when no GHES host is configured. It is a Fabrik-computed override, not part of the Anthropic auth namespace, so it is never subject to the scrub/passthrough machinery above. See ADR-1391.
- `GH_TOKEN`/`GITHUB_TOKEN`'s *source* depends on the engine's own authentication mode (#1713): in PAT mode (`Config.Token`, the default) it is the configured token verbatim, exactly as before. Under GitHub App auth (`github_app_id`/`github_app_private_key_path`/`github_app_installation_id` all set — see `docs/USER_GUIDE.md`'s "GitHub App Authentication") there is no static token to copy; `claudeGHTokenOverrideFn` (`engine/claude.go`) instead reads the engine's own minted `*gh.Client`'s current token live, at each invocation's env-build time — riding the same background refresh loop (`Reconciler.RunRefreshLoops`, started in `engine/poll.go`'s `Run()`) that keeps the engine's own API calls fresh. Known gap: a single invocation whose wall time exceeds the installation token's ~1h lifetime can still see a now-expired value for its remaining `gh` calls, since a running child process's env vars can't be updated after the fact — not fully solved, see ADR-1713.
- Git credentials under GitHub App auth (#1846): with HTTPS git (no `git_ssh`, no global HTTPS→SSH rewrite), `setUpAppGitCredential` (`engine/app_git_credential.go`, called from `Run()`) injects a `credential.https://github.com.helper` into the engine's own process environment via `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_<n>`/`GIT_CONFIG_VALUE_<n>` — an empty reset entry (clearing host helpers) then a marked helper reading `.fabrik/state/github-app-git-token`, which `runAppGitTokenWriter` rewrites on token rotation. Engine git and worker git both inherit it via `os.Environ()`, so pushes go out as the installation with no per-call-site change, and a long invocation survives token rotation (git only — `GH_TOKEN` keeps ADR-1713's gap). Requires `contents:write`, added to `setUpGitHubAppAuth`'s fail-hard grant check only in HTTPS mode. Every startup strips a previous exec's marked entries first, so SIGHUP/self-upgrade never stack helpers or leave one behind after a switch to PAT/SSH. Supersedes ADR-1756's `RefuseHTTPSWorkerGitUnderAppAuth` refusal. See ADR-1846.
- **Fabrik daemon-secret scrub (#2027):** `.env` is loaded into the daemon's process env (`config.LoadDotenv`) and the worker env is built from `os.Environ()`, so `buildClaudeEnv` also appends exact-name removal sentinels (never a `FABRIK_*` wildcard) for every daemon-only variable classified in `internal/workerenv` — `FABRIK_TOKEN`, `FABRIK_GITHUB_APP_ID`/`_INSTALLATION_ID`/`_PRIVATE_KEY_PATH`, `FABRIK_GITHUB_WEBHOOK_SECRET`, `FABRIK_REVIEWER_TOKEN`, the Hookdeck pair *and the variables they name* (resolved once in `New()` into `claudeWorkerEnv`), and every other engine-read `FABRIK_*` knob. **Default is scrubbed**: only the five engine-set worker facts are forwarded, and `TestEveryFabrikLiteralIsClassified` fails when a `FABRIK_*` literal in the engine sources is unclassified — so a new variable must be added to `workerenv.Scrubbed` (or `EngineSet`/`NotEnv` with a reason). `GH_TOKEN`/`GITHUB_TOKEN`/`GH_HOST` and the ADR-1846 `GIT_CONFIG_*` entries are `Protected` and never scrubbed, so a worker still has App-token-only git and `gh`; in PAT mode only the `FABRIK_TOKEN` variable is removed. The named opt-in is `FABRIK_WORKER_ENV_PASSTHROUGH` (exact scrubbed names; implemented as "don't emit the sentinel", so it cannot override `GH_TOKEN`; itself never forwarded; `[startup]` notice). Tests are hermetic against all of this via `internal/testenv` (`Isolate`/`IsolateGit`/`ScrubProcess`; `cmd` and `engine` `TestMain` call `ScrubProcess`), and `scripts/ci/worker-shaped-test.sh` runs the whole suite in a worker-shaped env, as CI's `worker-shaped` job in `.github/workflows/ci.yml`. See ADR-2027.
- See `docs/USER_GUIDE.md`'s "Anthropic Auth Namespace Scrub & `apiKeyHelper` Refusal" and "GitHub App Authentication", `docs/stage-lifecycle.md`'s "Worker Environment: Anthropic Auth Namespace Scrub" for full detail, and ADR-1346, ADR-1713

## Important Conventions

- **Don't commit directly to main from worktrees** — always work on the issue branch
- **Every PR must include `Closes #N`** in the body so Fabrik can discover PR comments
- **Commit frequently** during implementation — preserves progress if session is interrupted
- **Rebase onto the latest base branch — but only when actually behind it.** Check first (e.g. `git rev-list --count HEAD..origin/<base>` — `0` means skip; rebasing an up-to-date branch is pure churn that only replays commits and changes their SHAs). Do this in Review and Validate stages before signaling completion, against the default branch or the branch specified by `base:<branch>` label. If the rebase produces commits that don't match the remote, that's expected — rebasing always rewrites SHAs — so push them (`git push --force-with-lease`). This is safe even though the engine itself may also write to the issue branch (its own worktree-push helper, or a WIP commit pushed between your fetch and your push): a lease rejection from that just means the remote moved — the correct response is to retry, never to force past it. **Never `git reset --hard` the branch back to the remote tip to resolve that mismatch** — the local branch is correctly ahead after a rebase, and resetting it discards the rebase (and any commits on it) with no way to recover. If that push is rejected (the remote moved since your fetch), re-fetch, repeat the behind-check, rebase again, and push again — if it's rejected a second time, stop and report it rather than forcing (never `git push --force`) or resetting. If you narrate a worktree-state change in stage output, describe only what you actually did — never assert an external cause (e.g. "reverted") that you haven't established.
- **Check `git status` first** in any stage — there may be uncommitted work from a previous session
- **Labels are state**: `fabrik:locked:<user>`, `fabrik:editing`, `fabrik:paused`, `fabrik:awaiting-input`, `fabrik:awaiting-review`, `fabrik:awaiting-ci`, `fabrik:awaiting-done`, `fabrik:awaiting-member-close`, `fabrik:awaiting-close`, `fabrik:awaiting-pr-ready`, `fabrik:awaiting-advance`, `fabrik:awaiting-runaway-alert`, `fabrik:awaiting-landing-verification`, `fabrik:credited-pr:<N>`, `fabrik:landing-verification-failed`, `fabrik:awaiting-placement`, `fabrik:blocked`, `fabrik:rebase-needed`, `fabrik:bot-reprompted`, `fabrik:children-spawned`, `fabrik:spawned-child:<index>:<number>`, `fabrik:sub-issue`, `fabrik:claude-limit`, `fabrik:clear-claude-limit`, `fabrik:api-key-helper-detected`, `fabrik:tools-denied`, `fabrik:toolchain-stale`, `fabrik:nondefault-base-pr-noted`, `stage:<name>:in_progress`, `stage:<name>:complete`, `stage:<name>:failed`, `model:<name>`, `effort:<level>`, `review-authority:<mode>`, `expected-reviewers:<mode>`, `fabrik:yolo`, `fabrik:cruise`, `fabrik:unrestricted`, `fabrik:extend-turns`, `base:<branch>`, `fabrik:revalidate`
  - `model:<name>` — set by user to select a specific model for this issue (e.g. `model:opus`)
  - `effort:<level>` — set by user to override the stage's configured thinking effort for this issue only; valid values: `low`, `medium`, `high`, `max`; if multiple `effort:` labels are present, precedence is `max > high > medium > low`
  - `review-authority:<mode>` — set by user to override the stage's configured `review_authority` (ADR-1250) for this issue only; valid values: `advisory`, `authoritative`; only meaningful alongside `wait_for_reviews: true` — it does not change whether the review gate applies, only the verdict-strictness once the gate is active. No `review-authority:` label → stage YAML `review_authority` governs (unchanged default). Exactly one recognized label → it overrides the stage config for this issue only. Both `review-authority:advisory` and `review-authority:authoritative` present → resolves to `authoritative` (the more restrictive value), logging a warning — mirroring `effort:<level>`'s "pick deterministically, don't arbitrate" convention rather than `model:<name>`'s "first wins" convention. Any `review-authority:` label whose suffix is not exactly `advisory` or `authoritative` (typo, casing, unknown value) → ignored with a logged warning, falls back to stage config — never a hard failure, never a silent escalation to authoritative. Resolved by the shared `effectiveReviewAuthority` helper, which `checkReviewGate` (the advance gate) and `reviewGateBlocksLanding` (the landing gate) both consult identically, so the two gates can never disagree on the same issue. `yolo`/`cruise` never bypass whatever authority resolves to — they control merge/advance timing once the resolved gate is satisfied, never the gate's clearing condition. See ADR-1250, ADR-1261.
  - `expected-reviewers:<mode>` — set by user to override the stage's configured `expected_reviewers` (ADR-1283) for this issue only; valid values: `none`, `declared`; only meaningful alongside `wait_for_reviews: true` — it does not change whether the review gate applies, only which reviewers are expected once the gate is active. No `expected-reviewers:` label → stage YAML `expected_reviewers` governs (unchanged default, nil stays nil). Exactly one recognized label → it overrides the stage config for this issue only. `expected-reviewers:none` resolves to `&[]string{}` (enables the FR-2 fast-advance path). `expected-reviewers:declared` resolves to a fixed synthetic reviewer identity (`e2e-synthetic-declared-reviewer`) intended for testing/e2e use — it never posts a real review, so applying it to a production issue runs out the full re-prompt ladder before pausing. Both labels present → resolves to `declared` (the more restrictive value — it imposes waiting, unlike `none`'s immediate advance), logging a warning — same "pick deterministically, don't arbitrate" convention as `review-authority:<mode>`. Any `expected-reviewers:` label whose suffix is not exactly `none` or `declared` (typo, casing, unknown value) → ignored with a logged warning, falls back to stage config — never a hard failure, never a silent escalation to `declared`. Resolved by the shared `effectiveExpectedReviewers` helper, which `checkReviewGate`, `reviewGateBlocksLanding`, and `pauseForReviewTimeout`'s FR-4 status message all consult identically, so the two gates and the pause message can never disagree on the same issue. See ADR-1283, #1304.
  - `fabrik:yolo` — set by user to force auto-advance even when `auto_advance: false` in stage YAML; also triggers auto-merge of the linked PR when Validate completes
  - `fabrik:cruise` — set by user to auto-advance through all stages without auto-merging the PR or advancing to Done at Validate completion; if both cruise and yolo are present, **cruise takes precedence** — the PR is not auto-merged and the issue does not advance to Done, exactly as with cruise alone. Both end-of-Validate guards (`engine/stages.go`) test the raw cruise label rather than `cruiseActive`, so yolo cannot override either decision. Cruise is the conservative label: adding yolo to a cruise issue never widens automation.
  - `fabrik:paused` / `fabrik:awaiting-input` — the engine's pause pair (`awaiting-input` always co-occurs with `paused`). A paused item is resumed only by a **human** comment (`filterHuman`, ADR-069) created **at or after the latest `fabrik:paused` `labeled` event** — decided by the one shared predicate `resumeAuthorised` (`engine/comments.go`), used by `itemNeedsWork` and both `processItem` resume gates so admission and resume cannot disagree. A comment that predates the pause never resumes it, so an unprocessable comment lifts a pause at most once instead of every poll (#1813 — the #1752 loop that zeroed the comment breakers ten times over); bot chatter never resumes. The anchor is read live via `FetchLabelAppliedAt` (never the record-on-write cache — a label removed in the UI would leave a stale early entry) and lives in GitHub's event log, so it survives restarts. **Every indeterminate input resumes** (fetch error, no event, zero `CreatedAt`, equal timestamps) — a pause nobody can lift is the failure mode to avoid. An authorised resume still hands the full raw `findNewComments` set to `processComments`. See ADR-1813, `docs/state-machine.md` §4.4.
  - `fabrik:awaiting-review` — set by engine when a stage with `wait_for_reviews: true` completes and outstanding PR reviewer requests remain; cleared when all reviewers submit or `FABRIK_REVIEW_WAIT_TIMEOUT` elapses. Applied from three idempotent, non-conflicting sites: `handleStageComplete` (optimistic seeding, only when `wait_for_ci: false`), `checkReviewGate` (catch-up loop Phase 1 — owns the bot re-prompt ladder and the timeout), and `reviewGateBlocksLanding` via `attemptMergeOnValidate` (the landing-decision gate — blocks and labels only, never escalates). The landing gate exists because Phase 1's `handleReviewGate` skips itself on the frozen `hasComplete` in the very poll pass that clears CI, and Phase 2 reaches the landing decision in that same iteration; it re-reads review state live (`FetchPRReviews`/`FetchPRReviewRequests`) rather than trusting the item snapshot, sits ahead of the `merge_train` fork so both modes are gated identically, and blocks conservatively when a review fetch errors. See ADR-1216 and `docs/state-machine.md` §6.6.6. **Feedback vs. label (#1953):** `handleReviewGate`'s gate half (`checkReviewGate` — the label write and timeout) is what stays skipped while `!hasComplete` (#617's stale-snapshot concern); its feedback *detection and dispatch* half runs in every state, so review feedback arriving mid-run or during the CI wait is dispatched as a `review-reinvoke`, and `feedbackGateBlocks` (`engine/feedback_gate.go`, superseding the comment-only #1862 gate) holds every advance and landing while any comment, unresolved review thread or unaddressed review body is unprocessed. See ADR-1953-a.
  - `fabrik:bot-reprompted` — single fixed label (22 chars); set by engine after Phase 1 of the bot-reviewer escalation ladder fires (1× `ReviewWaitTimeout` when `reviewGateAllBots` is true — either every outstanding *requested* reviewer is a bot, or nothing was requested and a stage-declared `expected_reviewers` identity (ADR-1283) has not yet responded); serves as idempotency guard for Phase 1 and timing anchor for Phase 2; cleared when the gate cycle ends (bot responds, Phase 2 fires, or gate clears naturally). Never persists beyond the gate cycle. **Historical note:** before `expected_reviewers` (ADR-1283), `reviewGateAllBots` was unconditionally `false` whenever nothing was formally requested — which every real self-submitting bot (Pruefer, Gemini, CodeRabbit, Copilot) satisfies, since none of them are ever formally requested. This label had therefore never fired in production. Declaring `expected_reviewers` on a stage is what makes it reachable.
  - `fabrik:awaiting-ci` — set by engine when a stage with `wait_for_ci: true` emits `FABRIK_STAGE_COMPLETE`; **`stage:<name>:complete` is NOT added at that point** — it is deferred until CI passes (conjunctive gate). While this label is present, the dispatcher will not re-invoke the stage (only the catch-up loop evaluates CI). Cleared by the engine when all CI checks pass; also applied on confirmed CI failure to signal the CI-fix reinvocation path. While the label is present the review *gate* (`checkReviewGate`) is not evaluated, but `settleAwaitingCIScan`'s handler chain still detects and dispatches unprocessed review feedback (#1953) before the CI gate can clear.
  - `fabrik:awaiting-done` — set by engine as the very first mutation in `handleNoWorkNeeded`, the instant a stage emits `FABRIK_STAGE_COMPLETE` + `FABRIK_NO_WORK_NEEDED`, so the decision survives even if the subsequent board move to Done or issue close fails (e.g. rate-limit exhaustion) or the engine restarts. While present, dispatch is suppressed for every non-cleanup stage regardless of board column. Retried every poll by an unconditional settle scan until the Done move and issue close both succeed, at which point the label is cleared; after `MaxRetries` failed settle passes the issue is escalated instead (`fabrik:paused` added, `fabrik:awaiting-done` removed, explanatory comment posted) — see ADR-060.
  - `fabrik:awaiting-member-close` — set by `landSingleton` (the merge-train one-at-a-time landing path) when its member-issue `CloseIssue` call fails, after the PR merge, Done-move, and member-PR close have already happened. Retried every poll by an unconditional settle scan (`settleMergeTrainMemberCloses`, independent of `merge_train: on/off` and of `itemMayNeedWork`/`itemNeedsWork` dispatch — the item has already reached Done by the time this label matters) until the issue is confirmed closed (by us or by GitHub's own `Closes #N` auto-close), at which point the label is cleared; after `MaxRetries` failed attempts the issue is escalated instead (`fabrik:paused` added, `fabrik:awaiting-member-close` removed, explanatory comment posted) — see ADR-061. Scoped to `landSingleton` only; the analogous call in `landMergeTrainBatch` is a separate, deliberately out-of-scope follow-up.
  - `fabrik:awaiting-close` — set by `closeIssueIfNonDefaultBase` (ADR-1096's engine-initiated explicit close for a PR merged onto a non-default `base:<branch>`) when its `CloseIssue` call fails, after the caller's Done-advance has already happened. Retried every poll by an unconditional settle scan (`settleNonDefaultBaseCloses`, independent of `itemMayNeedWork`/`itemNeedsWork` dispatch — the item has already reached Done by the time this label matters) until the issue is confirmed closed (by us or by any other actor), at which point the label is cleared; after `MaxRetries` failed attempts the issue is escalated instead (`fabrik:paused` added, `fabrik:awaiting-close` removed, explanatory comment naming the merged PR posted) — see ADR-1097. Structurally identical to `fabrik:awaiting-member-close`/ADR-061. **Also used on the default base (#1962, ADR-1962):** GitHub's `Closes #N` auto-close silently stopped working on 2026-09-30, so `guardDefaultBaseAutoClose` live-reads the issue at the landing. If the issue is still open or unreadable, it applies this marker, and the same settle scan closes it on a later poll, posting "🏭 **Fabrik — closed after merge**" and naming the PR. A late GitHub auto-close clears the marker silently. The review gate's broken-linkage pause (`handleBrokenReviewLinkage`) likewise now confirms against the PR body (`FetchPRClosingIssues`) on every path, never GitHub's link field.
  - `fabrik:awaiting-pr-ready` — set by `markPRReady` (`engine/pr.go`) inline in its own two failure branches — a non-transient `client.MarkPRReady` error, or exhaustion of its existing in-process 3-attempt retry (#599) — after a stage configured with `mark_pr_ready_on_complete: true` completes but its draft PR never transitioned to ready-for-review. No signature change and no call-site changes were needed: `markPRReady` already had every value the marker write needs in scope at both failure points. Retried every poll by an unconditional settle scan (`settlePRReadyScan`, `engine/pr_ready_settle.go`, independent of `itemMayNeedWork`/`itemNeedsWork` dispatch) that re-resolves the PR live each pass and clears the marker without another API call once the PR is found already not-draft, closed, merged, or missing entirely; otherwise it retries `MarkPRReady` (safe regardless — GitHub's mutation is a documented no-op success on an already-ready PR). `markPRReady`'s own success path also clears a stale marker directly, without waiting for the settle scan. After `MaxRetries` failed settle attempts the issue is escalated instead (`fabrik:paused` added, `fabrik:awaiting-pr-ready` removed, explanatory comment naming the draft PR and the manual `gh pr ready <N>` fix posted) — see ADR-1582. **Unlike most of its `fabrik:awaiting-*` siblings, this marker is not terminal-only:** it can be applied while the item is still mid-pipeline (e.g. `mark_pr_ready_on_complete: true` on a non-final stage), and the item keeps advancing through later stages normally while it's outstanding — nothing about a later stage's dispatch depends on the PR being ready, and gating stage completion on this succeeding was explicitly out of scope. Structurally modeled on `fabrik:awaiting-close`/ADR-1097, the closest precedent.
  - `fabrik:nondefault-base-pr-noted` — set by `noteNonDefaultBasePRLinkage` after posting a one-time comment naming a `base:<branch>` item's discovered PR and explaining that GitHub creates no Development-panel issue↔PR link at all for a PR targeting a non-default base branch — not merely no auto-close (that half is `fabrik:awaiting-close` above; this label is its purely human-visible counterpart). Applied unconditionally right after the post attempt (mirroring `fabrik:api-key-helper-detected`'s no-retry shape), not gated on the comment actually succeeding — deliberately lighter than `fabrik:awaiting-close`/ADR-1097's retry/escalation machinery, since a missed one-time informational comment has no durable outstanding action to retry toward and nothing downstream depends on its delivery. Retried-in-detection-only every poll by an unconditional settle scan (`settleNonDefaultBaseLinkageNotice`, sourced directly from `board.Items`, independent of `itemMayNeedWork`/`itemNeedsWork` dispatch and of the item's board column) until the label's own presence short-circuits it. Never applied to a default-base item — `itemHasBaseLabel` and the `base == def` comparison (identical to `closeIssueIfNonDefaultBase`'s) both gate it out. See ADR-1649, #1649/#1646.
  - `fabrik:awaiting-advance` — set by `recordAdvanceOutcome` when a terminal advance (`advanceToNextStage`, called from `advanceValidateTerminalItem`'s merged-PR path or `advanceConvergedPRToDone`) fails to move the project-board Status forward — most commonly a missing target Status option — after every other side effect of the caller has already run. A one-time explanatory comment naming the failing stage and the underlying error is posted on the absent→present transition only. Retried every poll by an unconditional settle scan (`settleAwaitingAdvanceScan`, independent of `itemMayNeedWork`/`itemNeedsWork` dispatch — the item's own stage is already gate-complete by the time this label matters) until the advance succeeds (e.g. the missing Status option is added — no engine restart needed), at which point the label is cleared; after `MaxRetries` failed attempts the issue is escalated instead (`fabrik:paused` added, `fabrik:awaiting-advance` removed, explanatory comment posted) — see ADR-1422. Structurally identical to `fabrik:awaiting-close`/ADR-1097.
  - `fabrik:awaiting-runaway-alert` — set by `markRunawayAlertOutstanding` when the merge-train runaway guard's `fireRunawayGuard` (ADR-059 D8) pauses a member (`fabrik:paused` + `fabrik:awaiting-input`, applied unconditionally) but its `AddComment` alert call fails. Unlike its siblings above, `fabrik:paused` co-occurs with this marker from the very first application — the pause never depends on the comment succeeding — so its settle scan does not gate on `fabrik:paused`'s absence (doing so would make it a permanent no-op). Retried every poll by an unconditional settle scan (`settleRunawayGuardAlertScan`, independent of `merge_train: on/off`, sourced from raw `board.Items` rather than `groupQueuedByRepo` — which excludes `fabrik:paused` members, exactly the items this scan exists to find) until the alert comment posts successfully, at which point the label is cleared; after `MaxRetries` failed attempts a fallback comment carrying the same explanation is attempted instead, and the marker is removed **only if that fallback comment itself succeeds** (`fabrik:paused` remains either way) — a persistently failing `AddComment` (not just a transient one) leaves the marker in place so the settle scan keeps retrying indefinitely, rather than silently erasing the only remaining signal that the member was never actually alerted (see ADR-1533). `fireRunawayGuard` itself is also mutex-serialized (`mergeTrainRunawayMu`) with a per-episode idempotency set (`mergeTrainRunawayAlerted`, keyed by trial count so an operator-driven resume that trips the guard again still produces a fresh alert, cleared wholesale by `resetTrialCounter`) so a member appearing in two racing calls (its three call sites can run concurrently — worker goroutine vs. poll goroutine) is never double-alerted.
  - `fabrik:awaiting-landing-verification` — set by engine immediately after a Done transition attributable to a merge (merge-train batch or singleton landing, the merge-train singleton fast path, or the ordinary auto-merge path) succeeds — never unconditionally the way `fabrik:awaiting-close`'s `closeIssueIfNonDefaultBase` call is, since this marker's entire purpose is to verify a Done transition that must have actually happened. Read by the per-poll settle scan `settleLandingVerification` (`engine/landing_verification_settle.go`), which asserts the *merge-state of the credited PR* — not the item's own branch-tip ancestry to base, which produces false positives whenever a branch was rebased onto a later base after already landing (confirmed against #1573/#1523/#1520) and is structurally never an ancestor under `SQUASH`/`REBASE` merge strategies regardless of drift. Two regimes: a **confirmed failure** (credited PR resolves and is definitively not merged) fires `failLandingVerification` immediately — reopens the issue, moves the board Status back to `Validate`, applies `fabrik:landing-verification-failed`, removes this label and any `fabrik:credited-pr:<N>`, and posts a comment naming the branch/base/credited PR — never gated by the retry budget. An **inconclusive** result (API error, or no crediting reference discoverable at all — no `fabrik:credited-pr:<N>` label and no linked PR) goes through the same `recordSettleRetry`/`escalateSettle` idiom as every other settle-scan sibling, bounded by `MaxRetries`, escalating to `fabrik:paused` — never reopens the issue on ambiguity. Cleared on a confirmed merge. This is a backstop, not a fix — it detects and reverses a false `COMPLETED` within a poll cycle, it does not prevent one (that's #1615). See ADR-1616.
  - `fabrik:credited-pr:<N>` — set by engine alongside `fabrik:awaiting-landing-verification`, but only by the two merge-train landing paths (`landMergeTrainBatch`, `landSingleton`): it records the integration/singleton PR credited for the Done transition, since that PR is distinct from the member's own PR (which stays closed-not-merged) and can't be rediscovered later via `FetchLinkedPR` the way the ordinary auto-merge path's credited PR can. Read by `settleLandingVerification` to resolve which PR's merge state to check; absent → the scan falls back to `FetchLinkedPR`, which is correct only for the ordinary auto-merge path (whose credited PR *is* the item's own linked PR). For a merge-train item that fallback would resolve the member's own closed-not-merged PR and fire an immediate **false** confirmed-failure against a correctly-landed issue — so the two merge-train landing paths write both labels via `markCreditedLanding`, which applies this label **first with its error checked** and applies `fabrik:awaiting-landing-verification` only if it landed. A failed write here therefore leaves the landing *unverified* (logged loudly, the pre-#1616 status quo) rather than marked-and-unresolvable: not verifying is a coverage gap, falsely reversing a good landing is a regression. Removed whenever `fabrik:awaiting-landing-verification` is cleared, on escalation, or when the item is confirmed a landing-verification failure.
  - `fabrik:landing-verification-failed` — set by engine's `failLandingVerification` only on a confirmed landing-verification failure (see `fabrik:awaiting-landing-verification` above), alongside reopening the issue and moving it back to Validate. A distinguishing, human-gated label — not self-clearing — so an operator can tell this apart from an ordinary stage failure at a glance. Remove manually once the credited PR is re-landed and re-verified.
  - `fabrik:unrestricted` — passes `--dangerously-skip-permissions` instead of `--permission-mode dontAsk`; bypasses the default tool allowlist entirely. Use only when a stage needs tools outside the default set (e.g. non-standard toolchains). **Caution:** removes all tool restrictions.
  - `fabrik:extend-turns` — set by user as a manual override to pre-grant 2× the stage's `max_turns` budget for every invocation while the label is present; persists across all stages until the Done stage's cleanup runs (it is removed there, not on each individual stage completion); no-op when `max_turns == 0` (unlimited); subsequent extensions beyond 2× still require automatic progress detection; use as a safety valve when progress detection misfires — apply once and it covers all remaining stages
  - `base:<branch>` — set by user to override the worktree base branch for this issue; Fabrik will fork from, rebase onto, and target PRs at `<branch>` instead of the repository default; must be set before Research; multiple `base:` labels use the first and logs a warning; if the branch does not exist on the remote, Fabrik falls back to the default and posts a comment
  - `fabrik:blocked` — set by engine in `checkDependencies` when the issue has unresolved blocking dependencies (issues referenced via GraphQL `blockedBy`); cleared idempotently when all dependencies are resolved; processing is suspended while the label is present. On resume (the item already carries this label), `checkDependencies` re-reads `BlockedBy` live rather than trusting the cached snapshot — unconditionally on `alreadyBlocked`, not only when the cached list happens to be non-empty (ADR-1419) — so a stale-*empty* cache (the shape a bypassed engine spawn produces: a stage agent calling `gh issue create` directly, never creating a `blockedBy` edge) cannot cause an incorrect unblock.
  - `fabrik:rebase-needed` — set by engine at Validate when `attemptMergeOnValidate` returns `ErrNotMergeable` (the linked PR no longer cleanly merges onto its base branch); engine dispatches `dispatchRebaseReinvoke` to retry; cleared on successful rebase; at `MaxRebaseCycles` Fabrik falls through to `pauseForRebaseCycleLimit` and the issue is paused for human intervention
  - `fabrik:children-spawned` — set by the shared `spawnChildren` (`engine/spawn.go`) after all `FABRIK_SPAWN_CHILD_*` children in one batch are successfully created, board-servability-checked, assigned, added to the project board, and linked as `blockedBy` of the parent — regardless of whether Plan (via `preImplement`), Review, or Validate declared the spawn (ADR-1419, see below). For Plan-declared spawns this also serves as `preImplement`'s idempotency guard — while present, `preImplement` is a no-op; remove manually (and close children created under the completed spawn) to trigger a fresh spawn. A mid-flight Review/Validate spawn needs no equivalent guard (each dispatch's output is parsed exactly once, never replayed) but still applies this label on success.
  - `fabrik:spawned-child:<blockIndex>:<childNumber>` — set by `spawnChildren` on the **parent**, immediately after each spawn block's child issue is successfully created (before any of the per-child steps that follow), recording that block's already-created child by 1-based block index and issue number (the owner/repo is never stored — it's always re-derivable from the same immutable Plan comment a retry reparses). The only restart-surviving record that a given block's child already exists — `itemstate.Store` is in-memory only — so a retried `spawnChildren` (operator un-pause, or an engine restart between the fault and the retry) recognizes and resumes an already-created child instead of duplicating it: `CreateIssue` is skipped in favor of resolving the child via `FetchProjectItem`, and `AddProjectV2ItemById`/`AddBlockedByIssue` check first (`LookupIssueProjectItem`/a live `BlockedBy` read) rather than re-running unconditionally. Board-status placement is itself skipped on resume when the child already has a non-empty Status, to avoid clobbering progress the child may have made under its own pipeline while the parent sat paused. Best-effort write (`addLabelChecked`, logged not fatal); removed on every marker this call knows about once the full batch succeeds, right before `fabrik:children-spawned` is applied — steady state carries none of these. A recorded child that can no longer be resolved pauses the parent, naming the specific label to remove to force re-creation of that one block. **Scoped to the Plan/Implement spawn origin only** (`spawnChildren`'s `resumable` parameter) — the Review/Validate mid-flight spawn origin (§6.7.2) never reads, writes, or leaves behind this marker, since its block list comes from a fresh Claude dispatch's own `output` rather than an immutable stored comment, and is therefore not guaranteed stable across a retry that redispatches Claude. See ADR-1583.
  - `fabrik:sub-issue` — applied by `spawnChildren` to each spawned child issue, regardless of origin stage; informational only (human-visible filtering); carries no engine-gate semantics
  - **Cross-repo spawn board-servability (ADR-1419):** for any spawn (Plan, Review, or Validate), `spawnChildren` first checks whether *this instance's own* `repo:`/`project:` config actually covers each target repo — a multi-repo instance (`repo:` unset) already serves any repo its board carries; a `repo:`-scoped instance whose repo doesn't match the target has no board to register the child on. Rather than silently registering the child onto this instance's own (wrong) board and leaving it unassigned — the original failure mode — the spawn now fails loud: `fabrik:paused` is added to the parent with an explanatory comment naming the unservable target, and no children are created for that batch. Every spawned child is unconditionally assigned to `cfg.User` (folded into the same `CreateIssue` call, so a bad `user:` value fails loud through that one already-fail-loud path). `FABRIK_SPAWN_CHILD_BEGIN/END` recognition is not exclusive to Plan: Review and Validate parse it directly from their own stage output (mirroring the `FABRIK_PR_CREATE` marker precedent) as a sanctioned route for a stage that discovers a blocker mid-flight, instead of calling `gh issue create` directly — which the engine would never observe (no board registration, no assignee, no `blocked_by` edge). See `docs/state-machine.md` §6.7/§6.7.2 and [ADR-1419](adrs/1419-cross-repo-spawn-servability-and-midflight-recognition.md).
  - `fabrik:awaiting-placement` — set on a spawned **child** issue by `spawnChildren` when its initial project-board Status placement fails (call error, missing status-field metadata, or no suitable column found) — the child, board item, and `blockedBy` link already exist by this point, so this is recoverable in place rather than a spawn-abort condition. Retried every poll by a settle scan sourced directly from `board.Items` (not `deepFetchCandidates`, which a stranded child — sitting in a column with no configured stage — never reaches). Cleared on successful placement, or when the settle scan observes the child has been closed (no further placement is needed). After `MaxRetries` failed settle passes the child is escalated instead (`fabrik:paused` added, `fabrik:awaiting-placement` removed, explanatory comment posted on the child, plus a best-effort comment on the parent) — see ADR-062.
  - `fabrik:revalidate` — set by operator to force re-entry of the Validate stage; engine removes `stage:Validate:complete`, `stage:Validate:failed`, `fabrik:paused`, `fabrik:awaiting-input`, `fabrik:awaiting-ci`, `fabrik:auto-merge-enabled`, and the trigger label itself; Validate then dispatches on the next poll cycle; applied to non-Validate issues: only the trigger label is removed with a warning; safe to apply while Validate is in-flight (held until worker exits)
  - `fabrik:claude-limit` — set by engine when a Claude invocation exits because the account's usage limit was hit, detected structurally from the CLI's own result object — `terminal_reason == "blocking_limit"`, or `terminal_reason == "api_error"` with `api_error_status == 429` (ADR-1811; a session limit the CLI reports as an API error) — never from output prose a stage may have written; the suspension's end instant likewise comes from the CLI's structured `rate_limit_event` `unifiedWindows.*.resetsAt` (latest reset among windows with `utilization` ≥ 1, clamped to 8 days, 1h fallback with a named reason when absent/zero/malformed/past — ADR-1815, `engine/usage_limit_reset.go`) (distinct from GitHub's own "rate limit" terminology used elsewhere in this doc for the GraphQL budget — see `engine/backoff.go`/`engine/terminal.go`); the stage never ran, so `StageAttempted` is recorded (the normal dispatch cooldown applies) but `StageRetryIncremented` is not — the hit does not count against `max_retries`, and neither `stage:<name>:failed` nor `fabrik:paused` is applied. An explanatory comment is posted once per detection episode, gated on the label's own absence, mirroring `fabrik:awaiting-ci`'s non-spamming behavior. Cleared per-issue on that issue's next invocation that is not itself classified as a usage-limit exit, and account-wide by `settleClaudeLimitLabelSweep` (`engine/claude_limit_settle.go`), a per-poll settle scan that best-effort-removes the label from every open item once `claudeSuspendedUntilTime` reports the account-wide suspension has lifted — so an issue that is paused, blocked, or simply not redispatched no longer keeps the label indefinitely after the suspension has already ended (the same durable-state leak as #1135's orphaned `stage:*:in_progress` labels). See ADR-1119, ADR-1183.
  - `fabrik:clear-claude-limit` — operator-applied to any open board item to clear an active account-wide Claude usage-limit suspension without restarting the engine. Read each poll by `settleClaudeLimitClearRequests` (`engine/claude_limit_settle.go`), which calls `clearClaudeSuspension` and removes the label from every item carrying it — a one-shot command with no retry counter, mirroring the `fabrik:revalidate` idiom. Not scoped to items also carrying `fabrik:claude-limit`: the suspension it clears is account-wide, not per-issue. See ADR-1183.
  - `fabrik:api-key-helper-detected` — set by engine when a stage invocation is skipped because the worktree's own `.claude/settings.json` or `settings.local.json` sets `apiKeyHelper` (a repo-resident setting Fabrik cannot see until the worktree exists — the startup-time preflight covers only the managed-policy/user/`fabrikDir`-project layers). Mirrors `fabrik:claude-limit`'s "stage never ran" shape exactly: `StageAttempted` is recorded (the normal dispatch cooldown applies) but `StageRetryIncremented` is not — the detection does not count against `max_retries`, and neither `stage:<name>:failed` nor `fabrik:paused` is applied. An explanatory comment naming the offending file is posted once per detection episode, gated on the label's own absence. Cleared on the next invocation that is not itself classified as a usage-limit exit or an `apiKeyHelper` detection — a human removing `apiKeyHelper` from the worktree file is enough to self-resolve; unlike `fabrik:claude-limit` there is no account-wide settle sweep, since the condition is inherently per-worktree. See ADR-1346, R13.
  - `fabrik:tools-denied` — set by engine when a Claude invocation's tool call(s) are denied by the CLI's own permission layer (detected structurally in `interpretClaudeResult`'s clean-exit path from a non-empty `resp.PermissionDenials` array, gated on `!completed` — never from output prose; a blocked worker is not a failed stage). Applies identically regardless of invocation type: the stage-dispatch path (`finalizeStageOutcome`) and the reinvoke/comment-review family (`processComments` — ordinary comment review, `ci-fix-reinvoke`, review-reinvoke) both classify via the shared `recordToolsDeniedDetection` helper and accumulate against the same per-stage `ToolsDeniedRetries` counter (#1704) — a mode denial cannot loop indefinitely just because it landed on a reinvoke path rather than the main stage dispatch, and on the comment path this classification bypasses the comment-processing circuit breaker (§4.6) entirely rather than being bounded by its frequency-based thresholds. Structurally unlike `fabrik:claude-limit`/`fabrik:api-key-helper-detected`: the CLI exits cleanly and real work may have happened before the denial, so this does NOT short-circuit `finalizeStageOutcome`/`processComments` — `commitWIP`, the branch push, and `markCommentsSeenByStage` all still run, mirroring `claudeTurnLimitError`/`claudeResumeFailureError`'s continue-processing shape. `StageAttempted` is recorded (the normal dispatch cooldown applies) but `StageRetryIncremented` is not — does not count against `max_retries`. Bounded instead by its own `ToolsDeniedRetries`/`MaxToolsDeniedRetries` counter (default 3, `--max-tools-denied-retries`/`FABRIK_MAX_TOOLS_DENIED_RETRIES`); at the bound, `pauseForToolsDeniedLimit` applies `fabrik:paused` + `fabrik:awaiting-input` — never `stage:<name>:failed`, since the condition is never treated as a stage failure even at the bound. **Each denial is scoped to the specific command that was denied, not the tool for the rest of the session** — a later, differently-shaped call to the same tool is unaffected (confirmed by direct observation in #1741, contradicting the "by strong inference" allowlist reasoning of ADR-1523/ADR-1704 — see the superseding ADR-1775). Both the explanatory comment (`recordToolsDeniedDetection`) and the escalation comment (`pauseForToolsDeniedLimit`) decode and name the first denied command when the CLI's `tool_input` makes one available (`classifyToolsDenied`/`claudeerr.ToolsDeniedError.Denials`, Bash only — no captured evidence for other tools' `tool_input` shapes), truncated and newline/backtick-sanitized for safe inline rendering; absent or non-Bash `tool_input` degrades to tool-name-only wording. Remediation is ordered accordingly: try re-running the step as separate, simpler commands, or add a matching `allowed_tools` rule, first; `fabrik:unrestricted` is named only as a last resort, with its trade-off retained (removes all tool restrictions, not just the denied one) — never as the headline fix. An explanatory comment naming the denied tool(s)/command is posted once per detection episode, gated on the label's own absence. Cleared on the next invocation not itself classified as tools-denied — self-resolving per-worktree like `fabrik:api-key-helper-detected`, with no account-wide settle sweep, since the cause is always local to one worktree's environment. Because classification is a non-nil `error` from `interpretClaudeResult`, `blockedOnInput := err == nil && ...` is structurally unreachable for a detected denial — the outcome is identical whether or not the worker also emits `FABRIK_BLOCKED_ON_INPUT`. See ADR-1523, ADR-1704, ADR-1775.
  - `fabrik:toolchain-stale` — set by `checkToolchainDrift` (`engine/toolchain.go`) when a worktree declares a toolchain version (`.nvmrc`, `package.json` `engines.node`, `go.mod` `toolchain`/`go` directive, or `.tool-versions`) that the version actually resolved on the daemon's own inherited `PATH` (e.g. `node --version`, `go version`) does not satisfy — the #1786 fix for a long-lived daemon silently pinning every worker to whatever toolchain was current when its hosting shell started, with no signal, restarting `fabrik` alone does not help since it re-inherits the same `PATH` from the same parent shell. Checked at both invocation paths (`runInvocationWithExtension` for stage dispatch, `processComments` for comment review), immediately before Claude is invoked. Structurally unlike `fabrik:claude-limit`/`fabrik:api-key-helper-detected`: detection never returns an error and never skips the invocation — this is warn-and-continue, not a gate, since re-resolving `PATH` or driving a version manager (`nvm use`, `asdf install`, etc.) is explicitly out of scope (there is nothing for Fabrik to do about a detected mismatch except tell someone). `StageAttempted`/`StageRetryIncremented`/`max_retries` bookkeeping is entirely untouched. Comparison is deliberately narrow and fails closed on ambiguity: `.nvmrc`/`.tool-versions`/`engines.node` are compared at major-version granularity only (an alias like `lts/*`, or a complex semver range, is "not comparable" — silence, never a false-positive warning), `go.mod`'s `toolchain`/`go` directive at major.minor granularity using minimum-version semantics (a floor, not a pin — and largely superseded in the common case by Go's own `GOTOOLCHAIN=auto` self-correction). A binary entirely absent from `PATH` is also "cannot compare," never a mismatch. A successful resolution is memoized process-wide per tool for the daemon's own lifetime (`resolveToolVersion`) — sound specifically because the bug this label exists to catch is that this `PATH` cannot change without a restart — so the cost of repeated invocations is a cache hit, not a repeated subprocess; a resolution *failure* (timeout, transient exec error) is deliberately never cached, since a failure carries no such invariance guarantee — caching it would permanently and silently disable detection for that tool after a single bad moment. On a detected mismatch, gated on the label's own absence (so the warning fires once per issue, not once per invocation — R5): an explanatory comment naming every mismatched declaration (source, declared version, resolved version) is posted and the label applied. Clears automatically once a later invocation observes no comparable mismatch (the declaration file is fixed, or the daemon is restarted with a corrected `PATH`) — no manual removal needed, no account-wide settle sweep (the condition is inherently per-worktree). See ADR-1786.
  - **`fabrik:non-default-base-excluded` (removed, #1648):** ADR-1647's interim exclusion of `base:<branch>` Queued members from merge-train batching has been superseded. The train now partitions Queued members by resolved base branch and runs one independent train per (repo, base) partition — a `base:<branch>` member is batched into its own partition rather than skipped. See "Merge-Train Batches Partitioned Per (Repo, Base)" below and ADR-1648.

## Canonical Documentation

These files are the authoritative as-built specifications for Fabrik's engine behavior. They must be kept in sync with the code — any PR that changes behavior in the areas they cover must update the corresponding doc in the same change set.

- **`docs/state-machine.md`** — As-built specification for: engine state transitions, label semantics, `FABRIK_*` marker handling, comment processing lifecycle, review gate and review reinvoke, PR lifecycle coupling, progress-based turn extension, and guard/filter behavior in `itemMayNeedWork` / `itemNeedsWork`.
- **`docs/stage-lifecycle.md`** — As-built specification for the per-invocation lifecycle: what happens before, during, and after a single Claude invocation (context files, worktree setup, Claude invocation, progress baseline snapshot, extension loop, output handling).

These are **as-built docs** — they describe what the engine currently does. They are distinct from `adrs/*.md`, which record architectural decisions and design rationale, not current state. Do not put state-machine content into ADRs or vice versa.

### ADR numbering

**New ADRs are numbered after the issue they come from**, not sequentially: an ADR for issue #1089 is `adrs/1089-kebab-title.md` with the heading `# ADR 1089: Title`. This matches `specs/` (`specs/895-conjunctive-ci-review-gate/`).

Do **not** pick "the next free number." Several issues are normally in flight at once and whichever merges first takes the number, so a sequential choice collides with a sibling branch — and git merges it cleanly, because the filenames differ. Nothing catches it. The number can also go stale while the PR waits in Review or Validate, after it was verified as free. Four such collisions occurred in a single day on 2026-07-26 before this convention was adopted.

`001`–`073` are legacy sequential numbers: leave them as they are, and never reuse or renumber them. Issue numbers are far above that range, so new ADRs cannot collide with legacy ones. If a single issue needs two ADRs, suffix them (`1089-a-...`, `1089-b-...`).

PRs introducing new as-built behavioral docs should also add an entry here.

## Handling Community Bug Reports

**Never run a community- or human-filed bug report through the Fabrik pipeline directly.** The Specify stage rewrites the issue body (`FABRIK_ISSUE_UPDATE_BEGIN` / `FABRIK_ISSUE_UPDATE_END`), so pipelining a report would overwrite the reporter's repro and diagnosis with a bot-authored spec — and the pipeline machinery (👀/🚀 reactions, per-stage comments, label churn) would spam the reporter's thread. Report and work are different artifacts: the report is human-owned triage/discussion; the work is bot-driven engineering.

Instead:

- **Keep the report as the canonical thread** — human-owned. Confirm the repro there, then comment linking to the work issue; keep it open until a **release containing the fix has shipped**, then close it by hand with a comment naming that release.
- **Create a separate spec-kit WORK issue** (authored as the bot identity, on the engine project board) that restates the report as Problem / Requirements / Scope / Acceptance and references it. **One report maps to 1..N work issues.**
- **Linkage:** the work issue's PR carries `Closes #<work-issue>` (Fabrik's own discovery relies on it) and mentions the report **by bare number only**.
  - **Never put a closing keyword (`Closes`/`Fixes`/`Resolves`) near a report's number.** GitHub would close the report on **merge** — typically weeks before the fix is **released** — leaving the reporter a silently-closed thread and a fix they cannot yet install. This is not hypothetical: a PR once carried a closing keyword for a report alongside `Closes` for its work issue, and merging closed the community report two seconds later, unexplained and unreleased.
  - **Spec wording must be explicit**: *"mention #N in the PR body; do NOT use a closing keyword (`Closes`/`Fixes`/`Resolves`)"*. Saying merely "reference #N" is read by the Implement stage as licence to use one.
  - **The keyword fires inside a negation too** — GitHub parses adjacency, not grammar. A PR body disclaiming the link (*"this does not \<keyword\> #N's actual subject"*) still matched and auto-closed that report as COMPLETED, stamping a declined report as shipped. Safe phrasings: *"#N is out of scope here"*, *"this does not address #N's subject"*, *"mentioned for context: #N"*.
  - **Reports are closed by hand**, with a comment naming the release — never by a PR.
- **Multi-part fixes:** create a **chain of self-contained spec-kit work issues** (`blockedBy`-linked, **no epic/tracking issue**), all referencing the report. Do **not** rely on the in-pipeline child-spawn (`FABRIK_SPAWN_CHILD`) for a *known* decomposition — that path is for decomposition Plan *discovers* mid-flight; pre-decompose into chained issues when you already know the shape.
- **Exception:** only pipeline the issue itself when it is your own internal issue, already spec-kit-shaped, a single fix, and reshaping it is acceptable. Community-filed reports are always handled as a separate work issue.

**Board separation:** community reports belong on a separate, **public** triage/roadmap board with coarse columns — **Triage → Accepted → In Progress → Merged → Shipped → Declined** — giving the community a clean "reported → shipping" view. The engine work board stays private — it is thick with operational machinery (`fabrik:locked`, `stage:<name>:in_progress`, bot churn) that is noisy in public. A GitHub issue can belong to both boards at once (coarse on the public board, fine-grained on the engine board); keep the public board coarse to avoid status-sync overhead.

**`Merged` is not `Shipped`.** Fabrik reaches users through **releases** (`go install` / release download), not merged `main`. A merged fix is therefore **Merged** (in `main`, not yet available — build from source to get it early), and only moves to **Shipped** when a **release is actually cut** that includes it (note the release version). Never mark a report Shipped on merge — that implies an availability the community can't get yet.

## Startup Board Validation

On every startup, Fabrik fetches the project board and compares stage names to board columns. If any non-cleanup stage is missing from the board, Fabrik exits with a detailed error message listing the mismatched names. Extra board columns (without a matching stage) produce a warning but don't block startup. This catches mismatches between stage YAML config and the GitHub Project board configuration early.

## Common Issues

- **Startup board validation failure**: Stage names in `.fabrik/stages/*.yaml` must match the column names on your GitHub Project board exactly. Check both for typos.
- **Max turns exceeded**: Increase `max_turns` in stage YAML or split the issue
- **Merge conflicts**: Left as conflict markers for Claude to resolve — check `git status`
- **Stale worktree**: `updateWorktreeFromMain` runs on each stage invocation; skip if dirty
- **SSH key expired**: `ssh-add ~/.ssh/<key>` — git operations fail silently with warning
- **processedSet is in-memory**: Rocket reactions provide durable "already processed" state across restarts
- **Stage drift warning at startup**: `[startup] warning: .fabrik/stages/<file>.yaml is missing fields present in v<version> defaults: <keys>` means your stage YAML predates fields added in a newer binary. The check is value-aware: a missing key is only reported when adding it would actually change the stage's effective behavior — a key whose embedded-default value is behaviorally identical to omission (e.g. `kill_grace: {sigint: 10s, sigterm: 10s}`, `completion: {type: claude}`) is never flagged. Run `fabrik refresh-stages` to preview what would be added, then `fabrik refresh-stages --apply` to add the missing keys (it uses the same value-aware comparison, so it never offers a key drift considers a no-op). Review with `git diff`, then commit. The warning is informational — the engine will still run with your existing config, but you may be missing new behavioral options (e.g. `wait_for_ci`, `wait_for_reviews`).

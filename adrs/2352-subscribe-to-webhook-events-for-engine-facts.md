# ADR 2352: Subscribe to the webhook events for facts the engine uses

## Status

Accepted. Extends ADR 034 (delta handlers) and ADR 2348 (observed-at ordering); follows ADR 2351 (transport-neutral intake) and ADR 2383 (fixture-driven payload decode).

## Context

The engine reads facts that no webhook it subscribed to carried: whether a review thread is resolved, a comment's current text or existence, a label's or milestone's name, and sub-issue links. They reached the item Store only through a deep fetch or a live read, and the cache freshness rule (ADR 2180) can keep a stale copy until the next probe notices a difference. `issue_comment` and `pull_request_review_comment` `edited`/`deleted` were subscribed but ignored. This must land before a second webhook source (#2143) so that source does not inherit the blind spots.

Real deliveries were captured (`boardcache/testdata/webhooks/`) and changed the scope: GitHub sends no `projects_v2` event when a Status option is renamed; `sub_issues` sends two deliveries per change (one per endpoint); and the objects embedded in a delivery reflect when GitHub rendered it, not the action (a `label_created` already carries the renamed name; `sub_issues_summary` reads the same on add and remove).

## Decision

- **Events.** The default list gains `sub_issues`, `pull_request_review_thread`, `label` and `milestone`. `projects_v2` is not subscribed: it carries project title, description, closed and deleted, none of which the engine reads, and not Status-option renames, which stay learned by reconcile.
- **Keys.** Handlers use `action`, IDs and `changes.*.from` only. Embedded names, counts and summaries are never used to infer the action. Payloads are declared field by field with lenient scalars (ADR 2383).
- **No fetch on the apply path.** Handlers use `Peek`, `Scan` or `GetByPRKey`, never `Get`, `ensureIssueInStore` or `resolveOrHealPRLinkage`. A subject the Store does not hold (item, thread, comment, label, milestone) is ignored with at most one log line; reconcile and the deep fetch stay the fallback. A test fails if the Store's fallback fetcher or any read client method is reached.
- **Comments.** An edit replaces `Body` only; author, creation time, reactions and processed state are untouched, and the poll is woken only if the body changed. A delete removes the comment. Issue comments resolve their item with `Peek`, then through the PR index for a comment on a PR's conversation tab. Review comments route through `GetByPRKey`.
- **Review threads.** `LinkedPR.ThreadComments` holds unresolved threads only, so `resolved` removes the thread's comments and raises `ResolvedThreadCount` only when something was removed (a replay, or an unknown thread, changes nothing; the 50-thread fetch cap makes "unknown" ambiguous). `unresolved` invalidates the item's deep cache instead of rebuilding the comments from the delivery, because the payload has neither `isOutdated` nor reactions; one refetch on a rare event. Neither stamps `linkedPRFetchedAt` (ADR 1551).
- **Label and milestone fan-out.** `RepoLabelChanged` and `RepoMilestoneChanged` are multi-item Store mutations routed in `Store.Apply`, one lock acquisition per item and one `Change` per changed item, observers notified outside the lock. A label rename is in place and never duplicates a label the item already carries; a delete removes it. A rename emits no `LabelDeltas`, so a repository-wide rename does not raise one channel event per item, but it does raise `LabelsChanged` (wakes the poll). Milestones are matched by `milestone.number` in the repository, never by title (titles collide; `changes.title.from` is not used to find items). A rename of an engine-state label (`fabrik:*`, `stage:*`) is applied as data like any other, until the next fetch.
- **Sub-issue links.** `ItemState.SubIssues` on the parent and `ParentIssue` on the child, each set from either delivery of a change (both deliveries carry both endpoints), idempotent set add/remove. A change is applied once whichever delivery arrives first, or twice, or alone. Informational: a new `SubIssueLinksChanged` flag outside `wakeChFlags` and `cycleSetFlags`. No fetch populates these fields, so absence means "not heard of".
- **Ordering (ADR 2348).** New per-subject records, `comment:<id>` (edit, by `comment.updated_at`), `thread:<node id>` (by the delivery's `updated_at`, which real captures carry with a non-UTC offset) and `sublink:<repo#n>` (receipt time), expire after 10 minutes like per-label records so the map stays bounded. Label and milestone fan-outs use the receipt time and the existing `label:<name>` and `milestone` records, because a milestone's own `updated_at` is not comparable with the issue-level time recorded in `milestone`. A stale or replayed delivery is dropped silently. A late `added` replay can still look newer than a `removed` by receipt time; that is the same documented limit as for label echoes, and the next fetch corrects it.
- **Rejected events.** A hook that refuses one of the new events must not trip the 422 circuit breaker that disables webhook mode. `optionalWebhookEvents` (`projects_v2_item` plus the four new events) generalises the existing `projects_v2_item` recovery: a stderr line with a rejection phrase naming an optional event as a whole word drops only that event (several in one message are dropped together) and restarts. The time-based quick-exit fallback is unchanged and still concerns `projects_v2_item` only.
- **Rollout.** `gh webhook forward` recreates its hook with the new list on every start. A hook the operator created (organisation or repository, a GitHub App subscription, a Hookdeck source) keeps its events until the operator adds the four; the engine cannot detect their absence. Documented in the User Guide.

## Consequences

- Resolving a review thread, editing or deleting a comment, renaming or deleting a label and retitling or deleting a milestone reach the Store from the webhook alone, with no refetch. The feedback gate itself still reads live (ADR 1953-a); the cache-backed readers it did not cover (dispatcher view, channel settle events, local API) now agree with it sooner.
- A repository-wide label rename wakes every cached item carrying the label in one apply. No network call, bounded by the number of cached items.
- Review-comment `edited`/`deleted` have no captured delivery; their tests derive the shape from the captured thread comment and say so.
- Hookdeck, existing hooks and App subscriptions need the operator to extend them to benefit.

# ADR 2122: Overseer PR facts and CI verdict for every linked open PR

Status: accepted (#2122). Extends [ADR-1966-a](1966-a-fabrik-mcp-read-api.md); the as-built description is `docs/state-machine.md` §7.13.

## Context

`fabrik_status` answers from the daemon's in-memory state and reports `unknown` for anything the daemon does not hold. For a linked PR it held the number and the head SHA on every poll, but the PR's state, draft flag, mergeability and CI verdict only when something else had asked GitHub for them: a `pull_request` or `check_run` webhook, or a CI gate reading the PR. Outside a gate, on a poll-only deployment, an item in Implement or Review therefore showed `pr_state`, `draft`, `mergeable` and `ci` as `unknown` while the PR's "Test and vet" check was failing (observed on #2112/PR #2118 and #2110/PR #2117, 2026-10-11).

The local API's own `ciVerdict(runs)` was also not the gates' answer: it kept a superseded failed run next to its green rerun (so a rerun still read `red`), treated `cancelled`/`stale` as red where the gates treat them as ready, and had neither required contexts nor the check-suite hold.

## Decision

1. **Separate poll-side records.** `LinkedPRState` gains `Facts` (state, draft, merged, mergeable, mergeable state, the head they were read for, `ObservedAt`) and `CIVerdict` (verdict, the head it was computed for, failing check names, a fingerprint of the latest-per-name runs, `ObservedAt`). They are **not** the legacy `State`/`Draft`/`Merged`/`Mergeable`/`MergeableState`/`CheckRuns` fields. `Mergeable`/`MergeableState` were never written by any mutation, and `FetchLinkedPR` serves them from the store on a cache hit; populating them would change what the gates see (out of scope). Nothing a gate reads is written by the new mutations.
2. **Facts come from the board probe.** The per-poll probe query's linked-PR node selects the scalars `state isDraft merged mergeable mergeStateStatus` (no connection added); `runProbeAndDeepFetch` applies them with `FromProbe(PRFactsObserved)`. `mergeable`/`mergeStateStatus` UNKNOWN map to nil/empty, never to "conflicting". For a PR the probe cannot see (`closedByPullRequestsReferences` omits PRs on a non-default base, i.e. `base:<branch>` items) or whose facts the probe did not stamp in the current poll, `settlePRFacts` falls back to one REST `FetchPRDetails`, capped at 5 per poll.
3. **The verdict is the gates' verdict, computed poll-side.** `settlePRFacts` (poll goroutine) reads the head's check runs live through `e.client.FetchCheckRuns` and classifies them with `ciStatusVerdictFor`, which is `classifyLandingCI` unmodified. `classifyLandingCI` makes live reads (required contexts, check suites), so it can only run on the poll goroutine; the local API stores nothing but the result. The old `RefreshCheckRunsLive` named in the issue no longer exists (#2180 removed it); the refresher does not reuse the cached `FetchCheckRuns` semantics (ADR 2180) either. The check runs are read live (`e.client`, nothing written to the Store, so what the gates see is unchanged), not through the cache, because a cached READY set is trusted for ever and nothing on a poll-only deployment refreshes it. A green verdict is restamped without a read only for `prFactsGreenRecheck` (5 minutes) after the last live read (`CIVerdictRecord.LiveReadAt`), whether or not the Store's cached runs are populated (on a poll-only deployment they are empty; when a webhook or gate filled them they must still match the verdict's fingerprint), after which it is re-read, so a check rerun that fails on the same head surfaces; at most 8 evaluations that can cost a GitHub read run per poll, and an item past the budget ages into stale rather than being refreshed. The least recently attempted item goes first (an in-memory attempt stamp, so a failing read or a merged PR rotates to the back instead of holding the front), and a PR already known merged/closed is not re-read by REST inside the recheck window, so a shortfall rotates. The refresher's evaluation is its own read, not shared with a CI gate: for an item that also carries `fabrik:awaiting-ci` a would-be-green head costs one `FetchCheckSuites` per poll from the gate and one from the refresher (the `ci_suite_gate` sim test, which counts the gate's own reads, runs with the refresher disabled for that reason).
4. **Quiet writes.** The new mutations return `PRFactsChanged`, not a wake flag (no poll-wake loop); they never call `SelfWriteObserved`, never move `LastSeenPRUpdatedAt`/`LinkedPRUpdatedAt` (ADR 2180) and never touch `LastCIProgressAt` (ADR 2059/1410). The refresher's own check-run read goes through the raw client and writes nothing to the Store (`CheckRuns` and `LastCIProgressAt` stay with the gates and the `check_run` webhook path).
5. **A verdict is for one head.** It is dropped on write if its head is not the item's current head, cleared by `PRHeadSHAUpdated` on a genuine head change, cleared for a merged or closed PR, and the renderer shows it only when it equals `head_sha`. The engine-recorded head (probe, webhook, reconcile) can lag a push while the facts already name the new one, so when both heads are known and disagree there is **no agreed head** (`LinkedPRState.AgreedHead()`): nothing is read or evaluated for either, any recorded verdict is dropped, and the API and attention say `unknown` until they agree, because neither side is known to be the newer and a green for a head the PR has moved past is the worst thing this view could show.
6. **Freshness is reported, not hidden.** Each group has `*_as_of` and `*_stale`; stale means older than one poll interval, taken as the larger of the configured interval and the poll ticker's effective period (so a deliberate back-off is not stale). A stale value keeps its content and is flagged; a value never observed is `unknown`, which is neither stale nor defaulted.
7. **`ciVerdict(runs)` is deleted.** There is one definition of red.
8. **Attention gets an overlay, not a state.** `overlayCI` adds the reason `ci:red`, a summary prefix naming the failing checks and `Result.CIFailing`; it ranks the item (`RankCIRed` = 4, below every state that needs a decision) only when no worker is running and the PR is not a draft. A running `ci-fix-reinvoke` reads "addressing it"; any other worker kind reads "is running" and is not claimed to address CI. Existing rows, including every pause, escalation, suspended and `fabrik:awaiting-ci` classification, are unchanged (FR-011). A verdict older than one full refresh rotation (`ceil(candidates that can spend check budget / check budget)` polls; merged/closed PRs and greens read live within the recheck window do not count, `Engine.prFactsRotation`) is not surfaced; within a rotation a red for the unchanged head stays, so a board with more PRs that can spend the check budget than it covers does not flicker (the status tool still flags `ci_stale` after one poll interval). This only changes what is reported; no gate and no dispatch decision reads it (FR-012). No channel event is added.

## Cost

GraphQL: the probe query's cost, measured with `rateLimit(dryRun: true)` against the live board, is 1 point per 100-item page both before and after (the five fields are scalars on a node the query already selects). REST, per evaluation (nothing is memoised): one `check-runs` read (`e.client`, live); when the runs classify as ready, `classifyLandingCI` adds one uncached `check-suites` read (`ciSuiteHold`) and, when a required context has no check run, a combined-status read (`classifyRequiredContexts`), so an evaluation costs 1 to 3 REST calls. A green verdict is restamped without any read for 5 minutes after its last live read, so a stable green PR costs one evaluation per 5 minutes. Everything else is evaluated every poll it is reached: a red, pending or check-less open PR, and a ready set that `allCheckRunsPassed` demotes to pending because the latest run of some check is `skipped` or `cancelled` (it never takes the free restamp, which is green-only, and so spends budget on every poll). The cap bounds all of it: at most 8 evaluations per poll (so at most 24 REST calls), plus at most 5 REST PR-detail reads per poll for items the probe cannot see. A deployment with no open linked PRs adds nothing.

## Consequences

- The local-API files still read the Store only; `TestLocalAPISourceDoesNotReachGitHub` is unchanged. `settlePRFacts` lives in `engine/pr_facts.go`, outside that scan, like `settleDecisionAnchors`.
- `unknown` now means "not read since the daemon started"; right after a restart the values fill in over the first one or two polls.
- Webhooks do not write the verdict; with webhooks the check-run cache is warmer (so more heads take the free restamp path), but the verdict is recomputed on the next poll, so freshness is bounded by the poll interval either way.
- Known limitation: for a PR the probe cannot see (a `base:<branch>` PR) the facts' head comes from the REST fallback and the engine-recorded head only from the engine's other paths (webhook, reconcile, a gate's PR read). After a push the two can disagree until one of those paths records the new head, and `ci` is `unknown` meanwhile (honest, never a false green; `TestSettlePRFacts_DisagreeingHeadsMeanNoVerdict` pins it with the REST fallback naming the newer head). The refresher deliberately does not write the engine's head or pick the newer side, because a head recorded ahead of the engine's own paths reads as a push to the Validate SHA-invalidation scan. Resolving it needs the engine to learn the head itself, which is out of scope here.
- Red on a draft PR is common while a stage is still pushing; the overlay reports it but does not rank it.
- Rejected: `statusCheckRollup` on the probe (two more connections per PR node, mixes commit statuses with check runs, and carries no check-run id, so it cannot feed the gates' latest-per-name classifier); populating the gate-read `Mergeable`/`MergeableState`; a new ranked attention state.

## Addendum: the refresher never writes the head SHA

The REST facts fallback (a `base:<branch>` PR, or an engine without the board probe) reads the PR's head SHA but never writes it to `LinkedPRState.HeadSHA`. That field feeds the gates' Validate SHA-invalidation scan (`ValidateCompletedSHA` is compared with it), and a head recorded by an overseer-only refresher ahead of the engine's own paths read as a push after Validate completed (found by `TestYoloRemovedMidValidateBlocksMerge_NoWaitForCI`). The overseer view uses `LinkedPRState.ObservedHead()` instead: the engine-recorded head, else the head the facts were read for. The verdict is keyed to that head, `CIVerdictObserved` and the renderers compare against it, and `PRHeadSHAUpdated` drops a verdict whose head differs from the head the engine records, so a verdict never outlives its head.

# ADR 2096: Expired cooldowns are consumed on admission; merge-gate claims record a short cooldown; the paused backstop fetches once per baseline

**Status:** Accepted
**Date:** 2026-10-10
**Issue:** [#2096](https://github.com/handarbeit/fabrik/issues/2096)
**Related reports (mentioned for context):** #1943, #2062; original backstop #1944.

## Context

`selectDeepFetchCandidates` decides each poll which board items get a live look. Its cooldown test treated *any* expired `CooldownAt` entry as "admit this item", and nothing ever removed an entry (`CooldownRecorded` only sets). Two reports were the two faces of that one defect:

- **Too slow (#1943).** The merge gate claims a Validate-complete yolo item as `PRMergeUnsettled` / `PRMergeQueued` and records no cooldown. The poll defer then stamps `periodic-re-eval` at `10 × PollSeconds` (30 minutes at `poll: 180`), no `fabrik:awaiting-ci` exists to route the item through the dedicated settle scan (ADR-1270), and CI completion moves neither a label nor the issue's `updatedAt`. Nothing re-admits it until the periodic interval lapses.
- **Too eager (#2062).** Because an expired entry stays in the map for ever, once *any* reason (`dep-blocked`, `review-blocked`, `feedback-pending`, `spawn-*`, a past `periodic-re-eval`) had expired, `HasExpiredCooldown` was true on every later poll — even while the freshly re-stamped `periodic-re-eval` was active. The item was admitted every poll, and for a paused item the #1944 backstop became a live fetch per poll for the whole `recentBaseline` window. The fetch re-anchors the baseline to GitHub's `updatedAt`, which for a fresh pause is the pause write, so the window did not end after the first fetch either.

The obvious fix for #1943 — a short cooldown on the merge-gate claim — would, with the sticky expiry intact, admit the item on every poll for ever after the first expiry. The two had to be fixed together.

## Decision

1. **An expired cooldown admits once, then is consumed (Option A).** `ExpiredCooldownsConsumed` deletes every non-zero expired entry except `archive-eligible-at`. `selectDeepFetchCandidates` applies it for every non-cleanup, in-store item once the pre-filter has admitted it — including the `cycleSet` path, so an expiry coinciding with another admission reason is still used up. `HasExpiredCooldown` therefore reports only expiries the engine has not yet acted on (it also ignores `archive-eligible-at`, which is never a gate).
   - *Rejected: a "last admission" marker (Option B).* It would keep dead entries, need a new `ItemState` field and a default for items with no marker, and still need the periodic re-arm below. Every non-admission reader only tests `now.Before(t)`, so none needs the entry to persist.
2. **Reader audit.** Every `CooldownAt` reader outside admission (`dep-blocked` in `item.go`, `spawn-resume-deferred` / `spawn-recovery-deferred` in `spawn.go`) tests `!IsZero && now.Before(t)`; a deleted entry reads as zero, which is not before now — identical result for an expired entry. `archive-eligible-at` is an absolute "eligible since" cache read only for cleanup-stage items; it is never consumed, and cleanup-stage items skip consumption anyway. `attention` and the local API already filtered expired entries out; only a comment went stale.
3. **The periodic safety net is re-armed explicitly.** Admission used to keep an item alive through the sticky entry. Now: (a) an item admitted and fetched is re-stamped by the existing poll defer; (b) an item admitted but dropped before joining `deepFetchCandidates` — `itemMayNeedWork` false, or `DeepFetchFailed` — gets `rearmPeriodicReEval` (`periodic-re-eval = now + githubRecheckInterval()`, matching the deep-fetch-failure back-off); (c) an item advanced during the poll is skipped by the defer on purpose (#544, the new stage must dispatch next poll) and needs nothing further: its `StatusChanged` change puts it in `cycleSet` (`LocalStatusUpdated`), which is what always admitted an advanced item that had no cooldown entry. A *failed* advance changes no status, so `runCatchUpPhase2` does not add such an item to `advancedItems`: the defer then re-stamps `periodic-re-eval`, which retries it at the periodic interval (previously the sticky expired entry retried it every poll). *Rejected: an already-expired `stage-advanced` marker.* It looked like a safe stand-in for the sticky entry, but `advancedItems` also collects items whose advance *failed* (the awaiting-advance and closed-Validate settle scans add themselves), and the marker re-admitted those on the very next poll, shifting `TestSettleScan_AwaitingAdvance` — they are retried by their settle scans, not by admission.
4. **Merge-gate claims record `merge-unsettled`.** The `mergeBlocked` branch of `handleMergeAndCIGates` — reached only for `PRMergeUnsettled` and `PRMergeQueued`; a conflict is the separate `mergeConflict` branch and records nothing — stamps `merge-unsettled` at `now + mergeGateRecheckInterval()`. That is `PollSeconds / 2`, floored at 1s. The stamp is written mid-poll, so a full `PollSeconds` would land after the next tick and cost the item an extra poll; half an interval is reliably expired by then while still sitting out early wake-ups. It is deliberately not `githubRecheckInterval()` (the API-cost knob, ADR-1831).
5. **The paused backstop fetches at most once per baseline.** `ItemState.PausedBackstopBaseline` (mutation `PausedBackstopServed`) records the baseline *after* a successful backstop fetch; the backstop case requires `periodicReeval && recentBaseline && baseline != served`. Recording the post-fetch value is what makes one pause cost exactly one fetch: the fetch moves the baseline from the self-write instant to GitHub's `updatedAt`, so keying on the baseline seen at decision time would see a "new" baseline on the very next poll. A later `SelfWriteObserved` is a genuinely new baseline that may mask a new reply and earns exactly one more fetch. A failed fetch records nothing.

## Consequences

- A merge-gate claim costs the three settle reads (`FetchLinkedPR`, mergeable fields, check runs) every poll for as long as the claim lasts, instead of every ten polls — including a human-enqueued `PRMergeQueued` PR sitting in GitHub's queue. The only bound is the existing CI backstop; a `mergeable=null` escalation bound is #1809 and out of scope.
- Items that were admitted every poll because of a stale `dep-blocked` / `review-blocked` / `feedback-pending` / `spawn-*` entry now follow the periodic interval. That is the intended repair; the #488 "at most once per cooldown window" guarantee holds again for them.
- All new state is in memory only. A restart costs at most one extra admission or backstop fetch.
- Any new gate that records a cooldown gets "admits once per expiry" for free, and must not rely on an expired entry persisting. A gate that needs a persistent timestamp must use a dedicated store field (as `LabelAppliedAt` does) or be named in `ExpiredCooldownsConsumed`'s exclusions (as `archive-eligible-at` is).
- Out of scope: giving `mergeable=null` its own escalation bound, naming the blocker in the CI-timeout pause (#1809), applying `fabrik:awaiting-ci` on merge-gate claims, and the length of the periodic interval.

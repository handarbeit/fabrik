# ADR 1953-a: Never advance or land while review feedback or comments are unprocessed

**Status:** Accepted
**Date:** 2026-09-29
**Issue:** [#1953](https://github.com/handarbeit/fabrik/issues/1953)
**Supersedes in part:** ADR-1862's comments-only landing gate (`commentGateBlocksLanding`); the #617 decision to skip `handleReviewGate` entirely while a stage is incomplete.

## Context

On `liminis-context-graph#616` a body-only `COMMENTED` Pruefer review landed while Validate (`wait_for_ci: true`) was running. It was never dispatched: `handleReviewGate` returned immediately while `!hasComplete`, and `stage:Validate:complete` is withheld from stage start until CI is green. When CI cleared, Phase 2 reached `attemptMergeOnValidate` in the same pass; the landing gates checked outstanding reviewers and the authority verdict only, so a `COMMENTED` review cleared them. Stage advance (`handleStageComplete`) had no feedback check at all. The defect was fixed only because a human relayed it as an issue comment.

The `!hasComplete` guard came from #617 — a *stale* `LinkedPRReviewRequests` snapshot re-applied `fabrik:awaiting-review` at Validate-complete — a label-hygiene bug. The fix skipped the whole gate, label write and feedback detection alike. #1045 later made every non-`DISMISSED`/`PENDING` review body actionable, which widened the blind window to exactly the self-submitting-bot case.

## Decision

**Principle:** no stage advances, and no PR lands, while feedback is unprocessed; anti-chatter mechanisms bound how much work feedback causes, never whether it is looked at.

1. **One predicate, `unprocessedFeedback` (`engine/feedback_gate.go`).** Unprocessed issue comments (`findNewComments`), unresolved current-head review threads (`currentHeadReviewThreadComments` — an `isOutdated` thread never holds, #1207) and unaddressed review bodies (`buildReviewBodyCommentsFromReviews`, #1045 actionability, #1555 dedup). It reports what dispatch would act on, so a hold is never placed for something dispatch would ignore. It is read **live** — `FetchItemDetails` on a copy unless the caller already holds a live item, and a REST review read for `base:<branch>` items — never from a frozen `phase1Ctx`.
2. **`feedbackGateBlocks` fails closed (R5).** A non-empty result or any failed read holds, records a `feedback-pending` cooldown so `itemMayNeedWork` re-evaluates the item, and logs `[#N feedback-gate] holding <where> — …` with the feedback IDs (R6). It is consulted at `attemptMergeOnValidate` (both merge-train modes, after `reviewGateBlocksLanding`, and again before the direct-merge fallback), at `handleStageComplete`'s advance, and at `runCatchUpPhase2`'s non-Validate advance. It replaces `commentGateBlocksLanding`; the comment half is unchanged. The gate is deliberately **not** inside `advanceToNextStage`, which is also the terminal Done advance after a merge — holding that would strand landed work. `advanceConvergedPRToDone` runs only after a confirmed merge, so a predicate there could hold nothing; the real gates are auto-merge enable (inside `attemptMergeOnValidate`) and #1207 guard 2.
3. **Split detection from #617's label write (R1).** `handleReviewGate` keeps `checkReviewGate` — the `fabrik:awaiting-review` write and reviewer timeout — gated on `hasComplete`, which is all #617 needed. Feedback detection and `review-reinvoke` dispatch now run in every state, including the `fabrik:awaiting-ci` window (via `settleAwaitingCIScan`'s handler chain) and for stages without `wait_for_reviews`, where bodies were previously never dispatched at all. One definition of "actionable feedback", one dispatch site, shared bounds.
4. **Complete, then reinvoke (R3, decided on the issue).** A stage invocation running when feedback lands finishes normally; nothing is injected. `handleStageComplete` consults the live predicate before advancing; for a `wait_for_ci` stage the CI-wait scan dispatches the reinvoke before the CI gate can clear. A hold keeps `stage:X:complete` — "final" means advance or landing, not the label — and the reinvoke goes through the existing path. **Accepted cost:** the reinvoke's push restarts any CI wait already begun on the old head.
5. **Queued window.** `settleQueuedReviewFindings` also detects unaddressed review bodies and ejects through the existing `ejectQueuedMemberForReviewFindings` / pending-eject route (ADR-1208/1863). `admitTrainMembers` stays fail-open; arrival before admission is covered because a member flagged by the scan is ejected directly if no worker holds it, or consumed by the worker at its first `applyPendingReviewEjects` checkpoint ahead of any trial or landing.
6. **Bounds (R4).** `MaxReviewCycles`, `ReviewBlockedCycles`, the #1555 marker, the no-op and frequency comment breakers and service-notice filtering are unchanged. One addition was required by the convergence proof: with feedback now holding progress, a reinvoke that lands no commit refunds `ReviewCycles` (#1045), and one that emits `FABRIK_STAGE_COMPLETE` counts as progress for both comment breakers, so a reviewer producing a fresh non-actionable body forever never converged. A review reinvoke dispatched while feedback stands between the item and its advance or landing (`feedbackHoldsProgress`: stage incomplete, or yolo/cruise/auto_advance would advance it) is therefore also charged to the never-refunded `ReviewBlockedCycles` counter, as ADR-1518 did for the blocked-gate case. Where nothing is pending behind the feedback, #1045's forgiveness is untouched. `tests/sim/feedback_gate_test.go` proves both shapes end in `fabrik:paused`.
7. **Sim fidelity.** `tests/sim/simgh`'s per-author review collapse skipped every later `COMMENTED`; production skips it only when the stored entry is a formal verdict. Corrected in the sim (and its board projection), per the fidelity-drift policy — the #616 shape (two `COMMENTED` reviews from one bot) was otherwise unrepresentable.

## Consequences

- A reviewer that keeps producing bodies can hold an advance until R4's bounds pause the item, which a human resolves. A silent merge past a real finding was the failure mode to avoid.
- Extra live reads (`FetchItemDetails`, plus a REST review read on `base:<branch>` items) at advance and landing decisions only — not per poll for every item.
- **Residual, not fixed here:** both review reads (`latestReviews`, REST `FetchPRReviews`) collapse to one review per author, so if one reviewer submits two reviews before Fabrik next reads, the earlier body is unreachable, and a `COMMENTED` after that author's formal verdict never surfaces. The predicate guarantees "nothing unprocessed among what GitHub returns". A full-history read would be a separate, larger change. The #616 timeline (reviews ~15 minutes apart) is covered.
- `base:<branch>` items keep their documented asymmetry: bodies come from REST, thread comments remain structurally empty.
- The `feedback-pending` cooldown supersedes `comment-pending`.

# ADR 1833: Deterministic Queued-batch ordering via record-on-write StatusEnteredAt

**Date**: 2026-09-23
**Status**: Accepted
**Issue**: #1833 — merge-train: batch membership is random when Queued exceeds max_batch_size — the in-memory cache returns board items in Go map order

## Context

When more members are Queued than `max_batch_size`, the merge train is supposed to land "the first N by entry order" (ADR-059 D2). In practice, no entry order was ever established: `internal/itemstate/store.go`'s `Store.All()` builds its return slice via `for _, item := range s.items` over a `map[string]*ItemState`, and Go deliberately randomizes map iteration order per `range` execution. `boardcache.CacheImpl.FetchProjectBoard` builds `board.Items` directly from `Store.All()`'s output, `engine/poll.go`'s `groupQueuedByRepo`/`groupQueuedByRepoAndBase` preserved whatever order they received with no sort at any point, and `engine/merge_train.go`'s `capBatch` truncated to the first N — its own doc comment claimed "entry order (ADR-059 D2 / FR-4)" despite no code ever enforcing it.

This was not a latent correctness gap — it was observed causing real production damage. On `verveguy/concept-maps` (2026-09-17, `board_cache_mode: in-memory`), with 13 members Queued and `max_batch_size: 5`, the train logged "landing first 5 by entry order" on every poll, and the five it picked differed each time. Each poll's differing selection abandoned the previous poll's in-flight trial CI (E2E validation takes ~15 minutes; trials rarely survived 3) before it could resolve. Result: 9 refused merges in a row, nothing landed for 3.5 hours. The operator's workaround — raising `max_batch_size` to cover the whole queue — is what later amplified conflict count and bisection depth in the #1821 incident, making this issue upstream of that one: it forced the config that made every red batch expensive.

### Why no cheap, durable "entered Queued" signal exists

The natural fix would be to read a real "time this item's Status last changed to Queued" from GitHub directly, the same way `FetchLabelAppliedAt` (ADR-1314) reads a durable label-applied timestamp from an issue's REST events history. That precedent doesn't transfer: GitHub's REST Issue Events API has no event type for Project v2 status/field changes — classic Projects had `moved_columns_in_project`, Projects v2 exposes no equivalent through this endpoint. GraphQL's project item field-history is not queried anywhere in this codebase today, and probing it was rejected on the same GraphQL-node-budget grounds ADR-1314 rejected it for labels — more so here, since it would need to run per Queued item per poll rather than once per label lifecycle. There is no cheap, durable "time entered Queued" available from GitHub at all.

## Decision

**Record-on-write `StatusEnteredAt`, a sibling application of ADR-1314's `LabelAppliedAt` pattern applied to Status instead of to a label map**, plus an unconditional deterministic sort ascending by `(StatusEnteredAt, Number)` applied inside `groupQueuedByRepo`/`groupQueuedByRepoAndBase`, upstream of `capBatch`.

### Design

- **`internal/itemstate.ItemState.StatusEnteredAt time.Time`** — a new scalar field (not a per-status map like `LabelAppliedAt`; only the *current* Status's entry time is ever read, by the merge train, about Queued specifically — a richer per-status history is an additive change if ever needed). Generic and Queued-agnostic by design: `itemstate` has no notion of which Status name is a merge-train holding stage.
- Stamped with `time.Now()` at each of the five existing, already-gated Status-mutation sites, all of which already guard on `if item.Status != newStatus` for no-op detection — `applyProjectItem`, `applyShallowItem`, `applyProbeItem` (`internal/itemstate/project_apply.go`), and the `LocalStatusUpdated` case and `applyProjectV2ItemEdited` (`internal/itemstate/store.go`). Because the stamp lives inside the same guard, a genuine Status transition is stamped exactly once and untouched by every no-op reconcile in between — this is what makes batch selection stable poll-to-poll, not merely randomized less often. Uses raw `time.Now()`, not an injected clock: unlike `LabelAppliedAt` (where the *engine* explicitly decides to record a second, separate mutation via `e.now()`), every one of these five sites is already inside `itemstate` itself, which is a leaf package with no `engine`/`stages` dependency and already sets other bookkeeping timestamps (`LastDeepFetchAt`) with raw `time.Now()` in exactly this position.
- **`github.ProjectItem.StatusEnteredAt time.Time`** — threaded through from `itemstate.ItemState` via `boardcache.CacheImpl`'s `snapshotToProjectItem`, the one in-memory-cache translation point. The direct-GraphQL `boardcache.GitHubAdapter` pass-through never touches `itemstate.Store` at all, so this field is left at its zero value on that path — deliberate, not an oversight (see Consequences).
- **`engine.sortQueuedGroupsByEntry`** sorts each `queuedRepoGroup`'s items ascending by `(StatusEnteredAt, Number)`. `Number` is unique within a repo, so the comparator is total: the same input permutation always produces the same output order (Acceptance Criterion 1). A zero-value `StatusEnteredAt` sorts before any non-zero time, so items sharing the zero value (the direct-GraphQL degeneration case) fall through entirely to `Number` ordering — deterministic, just not wait-time-ordered.
- `engine.groupQueuedByRepo`'s previous body is split into an unexported `groupQueuedItemsByRepoUnordered` (identical filtering/grouping logic, no sort) plus `sortQueuedGroupsByEntry`; `groupQueuedByRepo` composes the two. `groupQueuedByRepoAndBase` (ADR-1648) calls `groupQueuedItemsByRepoUnordered` directly, partitions by resolved base branch, and only then applies `sortQueuedGroupsByEntry` — sorting strictly after partitioning is what keeps ordering scoped within each `(repo, base)` partition and never crossing a partition boundary (Requirement 4), and it means both of this grouping's consumers (`handleMergeTrainBatch`, `settleQueuedReviewFindings`) see the identical order (Requirement 3) without either caller having to sort anything itself.
- `capBatch` (`engine/merge_train.go`) needed no logic change, only a corrected doc comment: it always performed a plain truncation, and now actually receives the ordering its old comment merely asserted.
- **`Engine.mergeTrainQueueSortDisabledForTest` / `SetMergeTrainQueueSortDisabledForTest`** — a narrow, engine-level test-only seam (mirroring the existing `SetTrainCIPollIntervalForTest`/`SetGitHubAppModeForTest` precedent) that makes `groupQueuedByRepoAndBase` skip the sort and fall through to raw input order. Never set outside tests. Exists to let a test demonstrate the toggle genuinely disables the fix; in practice the churn-reproduction proof below uses the pure `groupQueuedItemsByRepoUnordered` function directly rather than this toggle, for reasons covered under "Non-vacuity proof."

### Why `Store.All()` itself is not sorted

Requirement 1 (batch selection must be deterministic "regardless of what order the underlying board-state source hands back") is satisfied entirely by the explicit `(StatusEnteredAt, Number)` sort inside `groupQueuedByRepo`/`groupQueuedByRepoAndBase` — the merge train does not lean on `Store.All()` returning any particular order. `Store.All()` itself was deliberately left unsorted: every existing consumer of it (`engine/terminal.go`, `engine/startup.go`, `engine/worker_liveness.go`, `engine/observers.go`, `boardcache.go`'s own `Reconcile`/`LightReconcile`) is not currently order-sensitive, and sorting a hot, frequently-called primitive for a property only one caller actually requires — a caller that already establishes its own explicit ordering guarantee — was judged unnecessary scope.

### Non-vacuity proof: why the sim-bed harness (`tests/sim`) could not host this test

The original plan called for an AC3 scenario in `tests/sim`, seeding Queued members via the existing `mergeTrainEnv`/`QueueMember` fixtures and driving repeated polls. Implementation discovered this is structurally infeasible: `tests/sim`'s `Engine` is always constructed via `engine.NewWithDeps`, which wires the bare `boardcache.GitHubAdapter` pass-through directly to `simgh` — deliberately, so sim scenarios exercise engine logic without `boardcache.CacheImpl`'s Reconcile/observer machinery (an existing, pre-#1833 design choice, also documented in `tests/sim/dependency_unblock_test.go`). `simgh`'s own board projection (`tests/sim/simgh/board.go`'s `liveItemRefs`) iterates a plain `[]string` insertion-order slice, not a map — fully deterministic on every call, with or without the new sort. A poll-driven `tests/sim` scenario therefore cannot reproduce the pre-fix churn at all: the toggle would have nothing to disable, since the underlying data source never randomizes in that harness.

The churn-reproduction and stability proofs instead live in `engine/merge_train_queue_churn_test.go`, wired directly to the real `boardcache.CacheImpl` + `itemstate.Store` pairing production actually uses (the same wiring pattern several pre-existing `engine` package tests already use, e.g. `TestGroupQueuedByRepoAndBase_UnhydratedItem_ExcludedNotPinned`). `TestMergeTrainQueueChurn_UnsortedSelectionVariesAcrossCalls` seeds 8 Queued members, then repeatedly calls `CacheImpl.FetchProjectBoard` (which reads the real, map-order-randomized `Store.All()`) and feeds the result through the unsorted `groupQueuedItemsByRepoUnordered` + `capBatch` — the sort "neutralised" by construction, not by a toggle — asserting selection differs across at least one of 40 calls against an unchanged Queued set. `TestMergeTrainQueueChurn_SortedSelectionIsStable` repeats the same setup through the real, sorted `groupQueuedByRepoAndBase`, asserting identical selection across all 40 calls. Both tests passed non-flakily across 20 repeated runs under `-race`. This is a strictly stronger non-vacuity proof than a toggle-gated sim scenario would have been: it exercises genuine Go map-iteration randomization, the actual root cause, rather than a synthetic stand-in for it.

`engine/poll_test.go`'s `TestGroupQueuedByRepo_DeterministicUnderShuffledInput` separately covers Acceptance Criterion 1 with an explicit `rand.Shuffle` over many trials — pure-function coverage independent of any particular board-state source's randomization behavior.

## Accepted Limitations

- **Restart resets the clock.** `Store.Reset` (bootstrap after an engine restart) constructs fresh zero-value `ItemState`s and runs them through `applyProjectItem`, so every item already sitting in Queued at restart time gets `StatusEnteredAt = now` at that moment — a currently-longest-waiting item looks freshly entered until `Number`'s stable tie-break, or the passage of real time, re-differentiates it. This mirrors ADR-1314's own accepted cold-start trade-off for `LabelAppliedAt`, and is still strictly better than the pre-#1833 status quo of fully random per-poll churn.
- **In-process only, no cross-instance visibility** — the same caveat ADR-1314 states explicitly for `LabelAppliedAt`; not a new risk class introduced by this change.
- **Direct-GraphQL (`boardcache.GitHubAdapter`) mode degrades to Number-only ordering, not true wait-time order.** `StatusEnteredAt` is never populated on that path (no cheap durable signal exists — see Context), so every item ties on the zero value and the sort falls through to ascending `Number`. This is a deliberate, visible behavior change from today's undefined GraphQL board-position order to a defined, deterministic issue-number order — strictly more predictable, and exactly what Requirement 1 asks for, but any instance not running `board_cache_mode: in-memory` will see a different (though now-defined) landing order than before this change.

## Related Work

- ADR-059 D2 — "Snapshot-and-batch," the original design intent ("ordered by entry") this issue implements for the first time; not a new decision, a closed implementation gap.
- ADR-1314 — `LabelAppliedAt`'s record-on-write design, the direct precedent and reasoning template this ADR adapts from label timestamps to Status timestamps.
- ADR-1648 — `groupQueuedByRepoAndBase`'s (repo, base) partitioning; unaffected, since the sort runs strictly after partitioning and never crosses a partition boundary.
- ADR-1772 — the "not yet deep-fetched" exclusion guard in `groupQueuedByRepoAndBase`; unaffected, since it removes items from consideration before the sort ever runs.
- #1821 — the downstream incident (large `max_batch_size` amplifying conflict/bisect cost) this issue is upstream of; fixing the churn here removes the operational pressure that forced that workaround, without itself changing `max_batch_size` behavior.

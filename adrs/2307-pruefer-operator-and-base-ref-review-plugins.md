# ADR 2307: Pruefer loads operator review plugins and selects the review skill by `plugin:skill`, with a visible fallback; repo-supplied plugins are deferred to #2366

## Status

Accepted. Extends ADR 2306 decision 4 (the `Skill` grant now names the selected skill) and partially supersedes its decision 8 (a selected skill that does not run falls back instead of failing the review; the default skill still fails it). The rest of ADR 2306, ADR 1446, ADR 1642 and ADR 2192 stands, with the additions below.

**Scope change during review.** The first implementation also loaded plugins the reviewed repo committed under `.pruefer/plugins/<name>/`, read from the PR's base commit through the Trees/Blobs API. The maintainer decided that this change must ship with **no code from the reviewed repo running on the Pruefer host**, and that repo review plugins will instead come from the repo's standard Claude Code plugin declarations in a separate issue, **#2366**. That implementation (the tree reader, its validation and caps, the repo half of the plugin set, the default-branch-only rule and the veto-as-kill-switch wording) was removed from this change and is preserved on the branch `pruefer/repo-plugins-fetch` (head `3e6f75eb`). This ADR describes what ships; the removed design is summarised under "Deferred to #2366".

## Context

After ADR 2306 Pruefer's default review is an embedded plugin skill, but only that one plugin can be loaded. Good review plugins exist (`pr-review-toolkit`'s multi-agent reviewers) and an operator wants to bring them. A repo may also want to choose which skill reviews its PRs.

Trust: content on the PR's base ref was merged by the repo's maintainers, but it is still content from the reviewed repo; running it as code on the Pruefer host (hooks, MCP servers, scripts) is a decision for #2366. The PR head stays untrusted (ADR 1446 C1). Two facts shape the design: the review clone is a depth-1, head-only fetch with no base objects, and `PRDetails` carries only the base branch *name*, not a SHA.

## Decision

1. **One base SHA per review, used for every base-ref read.** `ReviewPR` resolves the base branch with `ResolveRefSHA` (the lightweight `git/ref/heads/<branch>` endpoint, conditional so an unchanged base is a 304) before anything else, and reads the repo config and the guidance skill at that SHA, so they cannot come from different base commits and the SHA a notice names is the one actually read (#2308 builds on it). REST `base.sha` was rejected (it can lag the branch tip); a merge-base was rejected (not what the maintainers merged). If the branch cannot be resolved the reads fall back to the branch name (the pre-2307 behaviour) and the outcome is not conclusive, so it is not memoised (ADR 1952). The extra call is one per `ReviewPR` run; the memo still prevents `ReviewPR` from running for an already-reviewed head, and the unmemoised baseline in the idle-cost test goes from three to four requests per PR.
2. **No code from the reviewed repo is loaded.** The plugin set is the embedded `pruefer-review` plugin plus the operator's `plugins:` directories. Nothing is read from the repo's `.pruefer/plugins/`, no Trees or Blobs endpoint is called, and a static test (`TestNoRepoPluginReaderExists`) fails if a production source in `pruefer/` or `github/` mentions such a reader. Repo-supplied plugins are deferred to #2366.
3. **A fixed, deterministic plugin order.** Embedded `pruefer-review`, then operator `plugins:` in listed order. Names are manifest names (`skillref.Plugin.Version` is new; the manifest `version` is read in `Discover`). `pruefer-review` is reserved: any other plugin declaring it is skipped and reported. For other duplicates the earlier plugin wins and each skipped duplicate is reported, because the catalogue returns the first match and a naive build would be silently order-dependent. Notes about skipped plugins carry no local path (they can reach a posted review).
4. **Operator plugins are used in place.** `~/` is expanded, a relative path resolves against the working directory (as `DefaultConfigPath` does), symlinks are resolved so `--plugin-dir` and the resolver see one path, and no size or symlink limit applies (they are the operator's own files). A missing or unreadable path is reported once per path (process-level dedupe; a path that works again is forgotten so a later breakage reports again). The per-review directory holds only the embedded plugin and is removed on every return path including the fallback re-run.
5. **Selection.** `review_skill` (operator, default `pruefer-review:review`; `LoadConfig` refuses anything that is not a `plugin:skill` pair) is overridden by the repo's base-ref `review_skill` unless `repo_review_skill: false`, which is the operator's veto on a repo choosing a skill. `review_skill` is the sixth recognised repo key and the first that does not narrow; `yamlRepoConfig` stays a separate strict struct, so every operator-only key remains unparseable from a repo file (ADR 1642 AC4, pinned by a test). `selectReviewSkill` is pure. A repo's reference can only resolve against the embedded plugin and the operator's plugins: one naming any other plugin does not resolve and falls back visibly (decision 6). `Config.RepoReviewSkill` defaults to true in `LoadConfig`; the Go zero value is false, which fails safe (the `PatchSkip` convention). An unparseable `PRUEFER_REPO_REVIEW_SKILL` is treated as false (the veto stays on) and logged, so a typo never leaves the repo's choice open.
6. **The visible fallback (R4).** `chooseReviewSkill` decides before any process starts: not a well-formed `plugin:skill` pair (no whitespace, backtick, `*`, `(` or `)`, because the reference is spliced into the `Skill(<ref>)` allow rule), or not resolvable against exactly the plugins passed (qualified-only, so load order never picks a skill), means the default skill runs, with no extra run. A selected skill that resolves but whose run shows it errored on load or was never invoked (`checkSkillRan`, as in ADR 2306) triggers exactly one re-run with the default skill. A failure that is not about the skill (process error, timeout, unparseable or empty output) is not a fallback and posts nothing, as before; the default skill itself not running still fails the review (ADR 2306 decision 8 stands for it). An early abort on a failed `Skill` result would need a streaming parse and was left out: the cost is a second run, bounded by `max_wall_time` per run, with turns and cost summed. The transcript and opened-set come only from the run whose text is posted (ADR 2303).
7. **The posted notice.** `ReviewPR` prepends `> 🏭 **Review skill fallback** — requested `<ref>` at base `<sha>` was not used (<reason>); this review ran `pruefer-review:review`.` A leading blockquote cannot collide with the coverage-line rewrite, which only touches lines starting with its marker. The reference and reason come from repo files, so both are sanitised and rendered in code spans. The reference keeps `[A-Za-z0-9._:/ -]` and is capped at 120 characters; the reason additionally keeps quotes, parentheses, commas and semicolons (harmless inside a code span, and needed to keep the resolver's message and the plugin notes readable) and is capped at 480 (`maxNoticeReasonLen`, larger so those notes are not cut off). Backticks, `@`, `#` and newlines never survive in either; the reason is a fixed phrase or the resolver's message, never skill output or a local path (those go to the log only).
8. **The tool grant.** `buildReviewToolRules` is unchanged in shape: `Skill(<ref>)` for the ref the invocation runs — the selected skill on the first run, the default alone on a fallback run — never a bare `Skill`, and bare `Task` stays. `checkReviewArgsScoped` now takes the allowed refs and accepts only the exact `Skill(<ref>)` rules for them (a wildcard or parenthesis in a ref never becomes an accepted rule).
9. **R6, the environment.** `reviewProcessEnv` already scrubs the `claude` process, and hooks and MCP servers are its descendants, so no new code was needed; the work is proof. A stub `claude` starts an operator fixture plugin's hook and MCP server as children and the test asserts they hold none of the daemon's `GH_*`/`GITHUB_*`/`FABRIK_*`/`PRUEFER_*`/`HOOKDECK_*` names or secret values, and that the same children started from `os.Environ()` do see them (non-vacuity).
10. **Guidance still applies.** `review_guidance` and the repo's `.pruefer/skills/review/SKILL.md` are passed as additional guidance to whichever skill runs, including the fallback. The replace-mode wording ("replaces the skill's criteria") is unchanged: it is skill-agnostic. The repo's guidance file is advisory text, not code, and is unaffected by decision 2.

## Deferred to #2366

Repo-supplied review plugins will be designed in #2366 from the repo's standard Claude Code plugin declarations rather than a bespoke `.pruefer/plugins/` tree. The first implementation, kept on `pruefer/repo-plugins-fetch`, is a reference for it: a Trees/Blobs reader pinned to the base SHA (`FetchTreeAtRef`, `FetchBlob`), validation in Go before anything was written (symlinks, submodules, unclean paths, case collisions, per-plugin and aggregate caps on files and bytes), an in-memory handoff to the invoker, a default-branch-only rule (`base.repo.default_branch`) and the `repo_review_skill: false` veto as a kill switch. Until #2366 lands, no repo code runs on the host and a repo's `review_skill` can name only a skill of the embedded or an operator plugin.

## Live probe (claude 2.1.301)

`TestLiveProbePlugins` (`-tags liveprobe`, `PRUEFER_LIVE_PROBE=1`) ran the production argument and environment builders against a plugin carrying a `SessionStart` hook, an MCP server, an agent and a skill, with the daemon holding secrets:

- Under `--setting-sources ""`, `--plugin-dir` loads the plugin's hook and MCP server (both started and recorded their environment), the skill was invocable by `probeplug:probe`, and the agent was reached through the allowed `Task` tool (the transcript names the tool `Agent`; the bare `Task` allow rule admits it).
- The hook's and the MCP server's environments held none of the daemon's secrets and no `GH_`/`GITHUB_`/`FABRIK_`/`PRUEFER_`/`HOOKDECK_` variable. The CLI adds its own variables for plugin children (`CLAUDE_PLUGIN_ROOT`, `CLAUDECODE`, `CLAUDE_PROJECT_DIR`, …), so the probe asserts the absence of credential and daemon-configuration names rather than applying the exact allowlist.

A different CLI version could change any of this; the unit tests guard the Pruefer side, the probe is the only guard for the CLI side and is opt-in.

## Residual risks

- Operator plugin processes (hooks, MCP servers, scripts) are not bound by the reviewer's path-scoped permission rules, which constrain only Claude's own tools. They run as the daemon's operating-system user with the scrubbed environment and can read any file that user can read, including `.pruefer/app-private-key.pem`. This is accepted: the operator chose the plugin, and a compromised or malicious operator plugin has the same reach as any other software the operator installs on the host. It sits beside ADR 2192's list, which already named MCP configuration as unsuppressed. No code from the reviewed repo is part of this.
- The reviewer's `Read` grant is unchanged (clone and staged diff only), so a plugin skill's own supporting files may not be readable. This is unverified against the CLI; the grant was not widened because this issue keeps the tool grant unchanged.
- The same holds for the `Skill` tool: the grant is `Skill(<ref>)` for the run's own reference only (decision 8, FR-010), so a selected skill that instructs the reviewer to invoke a sibling skill of its plugin may have that call denied under `dontAsk`. `checkSkillRan` requires only a successful call of the selected reference, so the review would complete without the sibling's criteria and without a fallback notice. Unverified against the CLI. The grant is not widened (the spec fixes it to the resolved skill); sub-skills are documented as unsupported, and plugin agents reached through `Task` are the supported way to compose review logic. A live probe of a sibling `Skill` call is a possible follow-up.
- Memoisation (ADR 1952): a changed `review_skill` (repo config) does not re-review a head already reviewed, like a changed repo config or guidance file today.
- One conditional REST call per `ReviewPR` run for the SHA pin.

## Consequences

- `GitHubReviewer` gained `ResolveRefSHA`, required unconditionally for the same structural reason as `FetchFileAtRef`. `github.Client` gained `ResolveRefSHA` only; there is no tree or blob reader.
- `ReviewRequest` carries a plugin-dir list, the requested skill, operator dirs and the base SHA; `ReviewResult` and `ReviewOutcome` carry the fallback.
- New operator settings `plugins`, `review_skill`, `repo_review_skill` (flag, env and YAML, all live-reloadable) and the repo key `review_skill`; documented in `cmd/pruefer/README.md` and `docs/USER_GUIDE.md`.
- Repo-supplied plugins are deferred to #2366. Installing plugins from a marketplace by name, changing which shell commands the reviewer may run and running coded tools over the head tree remain out of scope (the next issue in the chain).

# ADR 2307: Pruefer loads operator and base-ref repo review plugins, selected by `plugin:skill`, with a visible fallback

## Status

Accepted. Extends ADR 2306 decision 4 (the `Skill` grant now names the selected skill) and partially supersedes its decision 8 (a selected skill that does not run falls back instead of failing the review; the default skill still fails it). The rest of ADR 2306, ADR 1446, ADR 1642 and ADR 2192 stands, with the additions below.

## Context

After ADR 2306 Pruefer's default review is an embedded plugin skill, but only that one plugin can be loaded and a repo can only add a text file of guidance. Good review plugins exist (`pr-review-toolkit`'s multi-agent reviewers), and a repo may want its own procedure with sub-skills, agents, hooks or an MCP server.

Trust: content on the PR's base ref was merged by the repo's maintainers and is as trusted as the repo's own CI and the Fabrik workers already running on the machine; the PR head stays untrusted (ADR 1446 C1). Two facts shape the design: the review clone is a depth-1, head-only fetch with no base objects, and `PRDetails` carries only the base branch *name*, not a SHA.

## Decision

1. **One base SHA per review, used for every base-ref read.** `ReviewPR` resolves the base branch with `ResolveRefSHA` (the lightweight `git/ref/heads/<branch>` endpoint, conditional so an unchanged base is a 304) before anything else, and reads the repo config, the guidance skill and the plugin tree at that SHA, so they cannot come from different base commits and the SHA a notice names is the one actually read. REST `base.sha` was rejected (it can lag the branch tip); a merge-base was rejected (not what the maintainers merged). If the branch cannot be resolved the reads fall back to the branch name (the pre-2307 behaviour), no repo plugin loads, and the outcome is not conclusive, so it is not memoised (ADR 1952). The extra call is one per `ReviewPR` run; the memo still prevents `ReviewPR` from running for an already-reviewed head, and the unmemoised baseline in the idle-cost test goes from three to four requests per PR.
2. **The repo plugin tree comes from the Git Trees and Blobs API, never the clone and never `git`.** `FetchTreeAtRef` reads the commit's tree, descends `.pruefer/plugins` with one non-recursive read per segment and lists the subtree once recursively; `FetchBlob` reads each accepted file. Every cap and refusal is decided from tree metadata before a blob is read, there is no archive format to mishandle (`export-ignore`, tar entries), the installation token never appears on a command line, and base history never enters the reviewer's clone. A missing tree is "no repo plugins"; a truncated listing loads none. `repoplugins.go` imports no file-system package, and a test fails if it does.
3. **Validation in Go, before anything is written.** A plugin is skipped whole, and reported, if it holds a symlink, a submodule, a path with an empty, `.` or `..` segment, a backslash or a control byte, two paths that differ only in case, a directory name outside `[A-Za-z0-9._-]` (64 chars), more than 500 files, a file over 1 MiB, more than 4 MiB, or if the repo's plugins together exceed 8 MiB. The caps mirror the existing 32 KB / 64 KB caps on the repo's config and guidance files in kind, not in value; they are constants. The executable bit survives (hooks and MCP scripts need it).
4. **Fetch in `ReviewPR`, write in the invoker.** `ReviewPR` has the client and the SHA; `RealClaudeInvoker.Review` owns the per-review directory and its cleanup. The handoff is an in-memory, capped file set (`ReviewRequest.RepoPlugins`), so no temporary-directory ownership is split. The root now holds `pruefer-review/` and `repo/<name>/`, and is removed on every return path including the fallback re-run.
5. **A fixed, deterministic plugin order.** Embedded `pruefer-review`, then operator `plugins:` in listed order, then repo plugins in directory-name order. Names are manifest names (`skillref.Plugin.Version` is new; the manifest `version` is read in `Discover`). `pruefer-review` is reserved: any other plugin declaring it is skipped and reported. For other duplicates the earlier plugin wins and each skipped duplicate is reported, because the catalogue returns the first match and a naive build would be silently order-dependent. Notes about skipped plugins carry no local path (they can reach a posted review).
6. **Operator plugins are used in place.** `~/` is expanded, a relative path resolves against the working directory (as `DefaultConfigPath` does), symlinks are resolved so `--plugin-dir` and the resolver see one path, and they are exempt from the caps and the symlink refusal (they are the operator's own files). A missing or unreadable path is reported once per path (process-level dedupe; a path that works again is forgotten so a later breakage reports again).
7. **Selection.** `review_skill` (operator, default `pruefer-review:review`; `LoadConfig` refuses anything that is not a `plugin:skill` pair) is overridden by the repo's base-ref `review_skill` unless `repo_review_skill: false`. `review_skill` is the sixth recognised repo key and the first that does not narrow; `yamlRepoConfig` stays a separate strict struct, so every operator-only key remains unparseable from a repo file (ADR 1642 AC4, pinned by a test). `selectReviewSkill` is pure. The veto governs *selection only*: repo plugins still load under `repo_review_skill: false`, because their agents and sub-skills are reachable through `Task` and gating the load would break that. A repo value is not validated up front: a malformed one reaches the resolver, fails and takes the fallback. `Config.RepoReviewSkill` defaults to true in `LoadConfig`; the Go zero value is false, which fails safe (the `PatchSkip` convention).
8. **The visible fallback (R4).** `chooseReviewSkill` decides before any process starts: not a `plugin:skill` pair, or not resolvable against exactly the plugins passed (qualified-only, so load order never picks a repo's skill), means the default skill runs, with no extra run. A selected skill that resolves but whose run shows it errored on load or was never invoked (`checkSkillRan`, as in ADR 2306) triggers exactly one re-run with the default skill. A failure that is not about the skill (process error, timeout, unparseable or empty output) is not a fallback and posts nothing, as before; the default skill itself not running still fails the review (ADR 2306 decision 8 stands for it). An early abort on a failed `Skill` result would need a streaming parse and was left out: the cost is a second run, bounded by `max_wall_time` per run, with turns and cost summed. The transcript and opened-set come only from the run whose text is posted (ADR 2303).
9. **The posted notice.** `ReviewPR` prepends `> 🏭 **Review skill fallback** — requested `<ref>` at base `<sha>` was not used (<reason>); this review ran `pruefer-review:review`.` A leading blockquote cannot collide with the coverage-line rewrite, which only touches lines starting with its marker. The reference and reason come from repo files, so both are sanitised to `[A-Za-z0-9._:/ -]` and rendered in code spans, the reference capped at 120 characters and the reason at 480 (`maxNoticeReasonLen`, larger so the plugin notes explaining why a repo plugin was skipped are not cut off); the reason is a fixed phrase or the resolver's message, never skill output or a local path (those go to the log only).
10. **The tool grant.** `buildReviewToolRules` is unchanged in shape: `Skill(<ref>)` for the ref the invocation runs — the selected skill on the first run, the default alone on a fallback run — never a bare `Skill`, and bare `Task` stays. `checkReviewArgsScoped` now takes the allowed refs and accepts only the exact `Skill(<ref>)` rules for them (a wildcard or parenthesis in a ref never becomes an accepted rule).
11. **R6, the environment.** `reviewProcessEnv` already scrubs the `claude` process, and hooks and MCP servers are its descendants, so no new code was needed; the work is proof. A stub `claude` starts a fixture plugin's hook and MCP server as children and the test asserts they hold none of the daemon's `GH_*`/`GITHUB_*`/`FABRIK_*`/`PRUEFER_*`/`HOOKDECK_*` names or secret values, and that the same children started from `os.Environ()` do see them (non-vacuity).
12. **Guidance still applies.** `review_guidance` and the repo's `.pruefer/skills/review/SKILL.md` are passed as additional guidance to whichever skill runs, including the fallback. The replace-mode wording ("replaces the skill's criteria") is unchanged: it is skill-agnostic.

## Live probe (claude 2.1.301)

`TestLiveProbePlugins` (`-tags liveprobe`, `PRUEFER_LIVE_PROBE=1`) ran the production argument and environment builders against a plugin carrying a `SessionStart` hook, an MCP server, an agent and a skill, with the daemon holding secrets:

- Under `--setting-sources ""`, `--plugin-dir` loads the plugin's hook and MCP server (both started and recorded their environment), the skill was invocable by `probeplug:probe`, and the agent was reached through the allowed `Task` tool (the transcript names the tool `Agent`; the bare `Task` allow rule admits it).
- The hook's and the MCP server's environments held none of the daemon's secrets and no `GH_`/`GITHUB_`/`FABRIK_`/`PRUEFER_`/`HOOKDECK_` variable. The CLI adds its own variables for plugin children (`CLAUDE_PLUGIN_ROOT`, `CLAUDECODE`, `CLAUDE_PROJECT_DIR`, …), so the probe asserts the absence of credential and daemon-configuration names rather than applying the exact allowlist.

A different CLI version could change any of this; the unit tests guard the Pruefer side, the probe is the only guard for the CLI side and is opt-in.

## Residual risks

- Plugin-launched processes (hooks, MCP servers, scripts) are not bound by the reviewer's path-scoped permission rules, which constrain only Claude's own tools. They run as the daemon's operating-system user with the scrubbed environment and can read any file that user can read, including `.pruefer/app-private-key.pem`. This is accepted under the stated trust model (base-ref content equals the repo's CI and the Fabrik workers already on the machine) and sits beside ADR 2192's list, which already named MCP configuration as unsuppressed. The mitigation is that only a base-ref plugin loads, and an operator who does not trust a repo's maintainers should not watch it. There is no per-repo kill switch for repo plugins yet; it is a possible follow-up.
- `repo_review_skill: false` governs selection only; repo plugins still load and their hooks and MCP servers still run. Each review under the veto logs a warning naming the repo plugins that carry them. Gating loading on the veto, or on a separate operator setting, is a possible follow-up; it was not done here because the spec makes the veto a selection control and agents are reached through `Task`.
- The reviewer's `Read` grant is unchanged (clone and staged diff only), so a plugin skill's own supporting files may not be readable. This is unverified against the CLI; the grant was not widened because this issue keeps the tool grant unchanged.
- A malicious or compromised *operator* plugin has the same reach; the operator chose it.
- Memoisation (ADR 1952): a changed base-ref plugin or `review_skill` does not re-review a head already reviewed, like a changed repo config or guidance file today.
- One REST call per `ReviewPR` run for the SHA pin, and, for a repo that has a plugin tree, a tree walk plus one blob call per file. The tree walk is skipped when the base SHA cannot be resolved.

## Consequences

- `GitHubReviewer` gained `ResolveRefSHA`, `FetchTreeAtRef` and `FetchBlob`, required unconditionally for the same structural reason as `FetchFileAtRef`.
- `ReviewRequest` carries a plugin-dir list, the requested skill, operator dirs, repo trees, the base SHA and plugin notes; `ReviewResult` and `ReviewOutcome` carry the fallback.
- New operator settings `plugins`, `review_skill`, `repo_review_skill` (flag, env and YAML, all live-reloadable) and the repo key `review_skill`; documented in `cmd/pruefer/README.md` and `docs/USER_GUIDE.md`.
- Installing plugins from a marketplace by name, changing which shell commands the reviewer may run and running coded tools over the head tree remain out of scope (the next issue in the chain).

# ADR 2144: Webhook delivery replay for direct receivers

**Date**: 2026-10-22
**Status**: Accepted
**Issue**: #2144 — events: replay failed App webhook deliveries on start and reconnect for direct receivers
**Builds on**: ADR 2142 (direct App webhook transport), ADR 2351 (transport-neutral intake and delivery ledger), ADR 043 (reconcile ticker), ADR 2348 (observed-at ordering)
**Amends**: ADR 2142 decision 2/consequences (deliveries sent while the daemon is down are no longer simply lost)
**Chain**: #2081 → #2142 → #2143 (reuses the transport) → this.
**Amended by**: #2143 (decision 8: a failed redelivery is requested once more; a follow-up pass; the tailscale startup grace — see "Amendment" below; decision 9 and the consequences: the replayer is also built by the tailscale start path, ADR 2143 decision 9)

## Context

A direct receiver has no broker buffering deliveries. If the daemon is down or unreachable, GitHub's delivery fails and GitHub does not retry it; the reconcile ticker bounds the cost to one interval, but the event itself is gone. GitHub keeps the App's delivery log and redelivers on request (`GET /app/hook/deliveries`, `POST /app/hook/deliveries/{id}/attempts`, both App-JWT authenticated, which the daemon already holds).

## Decision

1. **A replay pass** (`engine/delivery_replay.go`) lists the App's deliveries, picks the failed ones the engine never received, and asks GitHub to redeliver them. It runs once at startup, in a background goroutine started after the listener is up (it never delays startup, and redeliveries need a listening receiver), and again when the transport's reconnect callback fires. The direct transport never calls that callback (ADR 2142: nothing to reconnect, a failed bind is retried only by a restart), so for `direct` startup is the real trigger; `attachTransportErr` installs a composite handler (reconcile request + replay trigger) so a transport that does signal a reconnect (#2143's `tsnet`) inherits the trigger with no engine change. A new periodic listener re-check was rejected as scope creep that contradicts ADR 2142's "no retry loop".
2. **Replay never applies anything.** It calls the two API endpoints and the ledger's read-only `Seen`; it never touches the transport sink or `intake.Submit` (`TestDeliveryReplayNeverSubmits`). A redelivered copy carries the original `X-GitHub-Delivery`, re-enters through the normal handler and intake and is deduplicated there, so an event that had in fact arrived is applied once.
3. **`Seen` and `Newest` are the only ledger additions, and both are read-only.** `Accept` records the ID, so using it for the check would make the redelivery itself look like a duplicate. `Seen` does not even prune. `Newest` (the latest receipt time) gives the lower bound.
4. **Lower bound** = `max(newest ledger receipt − 5 min, now − 24 h)`, or `now − 1 h` when the ledger is empty. The 5-minute margin covers skew between the ledger's local clock and GitHub's `delivered_at`. Known limitation: a failed delivery older than the newest ledger entry (a failure followed by later successes, then a pass) is left to reconcile; widening to the full 24 h would cost pages for little gain, and the persisted ledger is what makes the bound useful across a restart. The startup pass uses the ledger's newest time as snapshotted when the replayer is built, before the listener accepts anything: GitHub resumes live deliveries the moment the daemon is back, and one accepted before the pass read the ledger would otherwise move "newest" to about now and skip the whole outage. Later (reconnect) passes read the live value.
5. **Classification is client-side.** Failed = `status_code` outside 200–299, including 0 (no response) and 3xx; the API's `status=failure` filter covers only 400–599. Entries are grouped by `guid`: any 2xx attempt (a successful redelivery included) means delivered. `ping` is never redelivered (acknowledged, never applied). The newest failed attempt's delivery id is the one redelivered.
6. **Bounded.** Fixed constants, not configuration (variables only so tests can shrink them): 10 pages × 100 listed, 50 redeliveries per pass, ~250 ms between requests. A 422 (GitHub's spam guard), 401/403/404 or a rate limit ends the pass at once; three consecutive other failures also end it. Capped passes log what was left and report outcome `capped`.
7. **Non-fatal.** Any API error is logged once for the pass and degrades to reconcile-only, with outcome `degraded: …` on the health row. No `warnings` panel entry: the spec asks for a log line, the row is visible in `fabrik_health`, and the endpoints need no extra App permission, so this is rare. A Reconciler without credentials (`NewWithDeps` engines) returns an error before any network call.
8. **In-memory request memory** (amended by #2143, see "Amendment" below: a failed redelivery is requested once more). A `guid` requested in this process is not requested again within the ledger window (covers quick repeated triggers). A request that itself failed is forgotten so a later pass can retry. A redelivery that is requested and then fails again at the daemon stays unseen but is not re-requested until a restart; a short TTL could hammer a daemon that is rejecting deliveries (for example on signature drift). Not persisted: after a restart the ledger and the lookback are the only memory.
9. **Config**: flat `replay_failed_deliveries` (`*bool` in YAML, default true), `--replay-failed-deliveries`, `FABRIK_REPLAY_FAILED_DELIVERIES` (flag > env > YAML), classified `tune` in `internal/workerenv`. It is ignored, silently, for sources other than `direct` and `tailscale`: the replayer is built by the direct start path and, since #2143 (ADR 2143 decision 9), by the tailscale start path. `engine.Config.ReplayFailedDeliveries` defaults to off so `NewWithDeps` engines never replay.
10. **Health**: `localapi.TransportHealth.Replay` (`last_pass_at`, `found_failed`, `requested`, `capped`, `failed`, `outcome`) is additive, present with unknown values before the first pass and omitted for transports without replay. The replayer reports through an optional `replayStatusSink` implemented by `appWebhookTransport`, so `HealthRow()` stays the single source of the row.
11. **JWT access** is two narrow methods on `githubauth.Reconciler` (`ListAppHookDeliveries`, `RedeliverAppHookDelivery`) in the `VerifyGrants` style; a fresh JWT is minted per call. `github/app.go` gains a headers-returning `appDo` (cursor pagination reads the `Link` header; a missing or malformed header ends paging).

## Consequences

- A restart or outage of a direct receiver no longer loses events until the next reconcile: they are redelivered within one pass.
- Redelivery of a stale event is ordered by the observed-at rule (ADR 2348), whose receipt-time fallback is the redelivery's arrival.
- Ledger eviction at 10,000 entries can make an applied delivery look unseen, costing one redundant redelivery that the (idempotent) delta handlers absorb.
- GitHub's retention of the delivery log is not documented; anything beyond it is reconcile's job.
- `direct` is wired and tested here. `tailscale` (#2143) creates its replayer through `newDeliveryReplayer` the same way and is covered by `engine/tailnet_replay_test.go` (ADR 2143 decision 9).

## Amendment (#2143): redeliveries that fail, the follow-up pass and the startup grace

Live use of the tailscale receiver showed that GitHub answers a redelivery request with 202 **before** it attempts the delivery, so a pass cannot see the outcome of what it asked for, and that the startup pass of a freshly started tailscale node ran before Funnel ingress reached it: all 50 redeliveries it requested failed, the pass still read `failed 0`, and decision 8's in-process memory then kept those 50 GUIDs from ever being requested again by that process.

1. **A GUID is done when an attempt succeeded, not when it was requested.** Decision 8's "not re-requested until a restart" is replaced: a requested GUID is requested **once more** when its redelivery was attempted and failed, recognised from the log as the newest attempt being a `redelivery` newer than our request (minus the 5-minute skew margin, so a failed redelivery a person made earlier does not count) and no attempt having succeeded. The bound is `replayMaxRequestsPerGUID` = 2 per process (`replayRequest{at, n}`), so a dead endpoint cannot loop and the hammering concern of decision 8 stays answered. A request that errored keeps the allowance it had. This applies to `direct` as well.
2. **One follow-up pass.** A pass that requested anything arms one follow-up `replayFollowUpDelay` (3 minutes) later (one pending at a time; a follow-up arms none). It reuses the lookback bound of the last full pass: by then the live ledger's newest receipt has moved to about now (live deliveries are accepted again) and a bound derived from it would drop the outage. A reconnect pass arms its own follow-up. The delay is a package variable and goes through the replayer's `wait` seam (`Engine.SetReplayWaitForTest`), cancelled by shutdown.
3. **`requested` counts requests, not deliveries.** Chosen over changing the row: the health summary stays as it was, and the docs say that a pass whose redeliveries later fail still reads `outcome: ok` until the follow-up has looked; the follow-up replaces the summary, so `found_failed` 0 after it is the reliable "nothing left" reading. The log line is unchanged.
4. **Startup grace for `tailscale`.** The tailscale transport holds the startup pass back by `tailnetReplayStartGrace` (90 s, fixed, not configuration) after the node and its Funnel listener are up (`startDeliveryReplayAfter`): `Up` returning does not mean the public relay routes to the node. A reconnect trigger during the grace still runs a pass at once. `direct` is unchanged (no grace). A real reachability probe (#2425) can replace the grace.

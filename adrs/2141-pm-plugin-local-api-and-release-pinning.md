# ADR 2141: Refresh the PM plugin around the local API and pin it to each release

## Status

Accepted. Supersedes ADR 816 for `plugin/fabrik` (ADR 816's patch-bump-on-change rule still governs every other marketplace plugin; `entwurf` was the only one and has since moved to its own repository). Builds on ADR 2140 (the `fabrik` plugin name and the worker exclusion) and ADR 1966-a/b/c (the local API, channels and overseer actions).

## Context

The human-facing `fabrik` plugin read board and worker state by scraping (raw GraphQL, `ps` greps, shell scripts) although the daemon serves a local API and `fabrik mcp` exposes it. Its marketplace entry tracked `main`, so users received unreleased changes, while a fixed `version` string meant installed copies never saw an update unless someone bumped it by hand. Nothing told a user their plugin and binary disagreed, and installing was a manual two-command step nobody was prompted for.

## Decision

1. **Daemon-backed.** The plugin bundles `.mcp.json` starting `fabrik mcp`. Every shell script is deleted; board and issue state come from `fabrik_status` / `fabrik_board` / `fabrik_health`, and the skill and `/fabrik:status` are rewritten around them, the attention states, the human-applied steering labels and the overseer actions. The skill states that no action lifts a pause or posts a free-form comment (ADR 1813, ADR 1966-c). Stage comment bodies are not in the daemon API, so the skill points at `gh issue view --comments` for those; that reads issue content, not state. With no daemon the guidance says so and how to start it, and never falls back to scraping.
2. **Configuration through the environment.** *(Amended by [ADR 2322](2322-fabrik-mcp-subscriber-resolution.md): `userConfig` now declares only `fabrik_dir`; the plugin sets no `FABRIK_SUBSCRIBER`, so the session's own environment decides. Read the next sentence with that in mind.)* `userConfig` declares two optional settings, `subscriber` and `fabrik_dir`. `.mcp.json` passes them as `FABRIK_SUBSCRIBER` and `FABRIK_MCP_DIR`, together with `CLAUDE_PROJECT_DIR`, rather than as arguments: an unset setting is then an empty variable, not an empty `--dir ""` argument whose handling by Claude Code is unknown. `fabrik mcp` resolves its directory as `--dir`, `FABRIK_MCP_DIR`, `CLAUDE_PROJECT_DIR`, then its working directory (the plugin MCP server's working directory is undocumented). A value still containing an unexpanded `${...}` placeholder (should Claude Code leave an unfilled setting's literal text in place) counts as unset in both `subscriberName` and `resolveMCPDir`. `FABRIK_MCP_DIR` is classified in `internal/workerenv.Scrubbed`. This is configuration plumbing, not a new MCP capability. The channel hints that named only `server:fabrik` now also name `plugin:fabrik@fabrik`.
3. **No `channels` key and no default subscriber.** *(Amended by ADR 2322: there is now a fixed default, the OS username, because a stable name is safe. It names the action audit comments but never starts the push stream, which is what this decision was protecting against.)* A shared default name would make every session attach under one name and supersede the others, and a required option would prompt users of non-Fabrik projects. Channels stay a documented opt-in (research preview, per-session flag, claude.ai/Console login, org policy).
4. **Binary-paired version, pinned ref.** `plugin/fabrik`'s `plugin.json` `version` is set to the release version (the tag without `v`, equal to `fabrik --version`) on every release, changed or not, and every `git-subdir` entry of `marketplace.json` has `ref` pinned to the release tag. A `ref` tag is used rather than a `sha`, which is self-referential (the commit that contains it cannot know its own SHA). The checked-in `ref` therefore names the previous release between releases, and later commits to `main` cannot reach users because they do not change the pinned tag. Any other entry (at the time, `entwurf`) is pinned to the tag as well ("users never receive unreleased changes" applies to every entry) but keeps ADR 816's patch-bump-on-change version rule, since it has no binary to pair with. A release with no plugin change still ships a new plugin version, which is what makes Claude Code see an update.
5. **Tooling.** `tools/pin-plugin-release` (`version <manifest> <version>`, `refs <marketplace> <tag>`) edits by targeted text replacement, refuses a version with a leading `v`, and refuses to rewrite refs when the count of `"ref"` fields differs from the count of `git-subdir` entries. `tools/bump-plugin-version` is unchanged. `scripts/cut-release.sh` step 6b names the binary-paired plugins in `BINARY_PAIRED_PLUGINS` and runs the pin on first releases too (only the change-based bump needs a previous tag); `--no-plugin-bump` skips both and warns that refs stay on the previous tag. `.claude-plugin/marketplace.json` joins the dirty-tree allowlist.
6. **Atomic publish.** Step 6b no longer pushes its commit. Step 7 tags that commit and pushes `main` and the tag with `git push --atomic`, so `main` never names a tag that does not exist (a window in which every marketplace refresh would fail to resolve the plugin) and a rejected push publishes neither ref. Recovery messages say what was and was not published. The release workflow's requirement that the tag be reachable from `main` is met because the same push updates `main`.
7. **Skew notice.** A `SessionStart` command hook (`hooks/version-check.sh`, POSIX sh, no `jq`, run as a single quoted command string `sh "${CLAUDE_PLUGIN_ROOT}/hooks/version-check.sh"` rather than an exec-form `args` array, whose support was not confirmed, matcher `startup|resume`, 10 s timeout) compares the manifest version with `fabrik --version` (a leading `v` stripped, as `go install` builds keep it). It prints nothing and exits 0 when `fabrik` is not on `PATH`, either version is unreadable, the string is not made of version characters, the versions match, or `FABRIK_PLUGIN_VERSION_CHECK=off`. Otherwise it prints exactly one JSON object, `systemMessage` for the user plus `additionalContext` so Claude knows too. Versions are compared as opaque strings (no direction), like `skewNote` for the daemon/shim pair; a `dev*` build gets its own wording ("development build, cannot compare") instead of implying a downgrade.
8. **Install hint.** `fabrik init` prints the two `/plugin` commands and the auto-update pointer. A project-scope `.claude/settings.json` entry is not used: project-scoped plugins are not downloaded onto a machine that lacks them and their MCP servers go through per-server approval. Auto-update is a per-user toggle, documented and never changed by Fabrik.
9. **Guards in plain `go test`.** `plugin/pm_plugin_test.go` checks that the manifests parse, every `${user_config.X}` reference is declared, the hook script exists and is executable, every marketplace `git-subdir` entry has a `ref`, no shipped file contains a board/worker scraping route (SC-005), and every `fabrik:*` label the plugin docs name is one `internal/attention.MeaningOf` can explain (so the skill keeps only human-applied labels and cannot drift from the daemon's own table). `plugin/pm_hook_test.go` runs the hook against a stub `fabrik` for match, mismatch, dev build, missing binary, unreadable version, hostile version string and opt-out.

## Consequences

- Users get exactly a release's plugin, and are told when plugin and binary disagree.
- Every release changes the plugin version and so triggers a plugin update for auto-update users, even when its files did not change.
- Two `@arbeithand` commits per release is now one: the notes commit, then the pin commit published with the tag.
- A user who registered the server by hand and then installs the plugin has two servers; the README and User Guide say to remove the manual one.

## Live checks CI cannot prove — NOT yet verified

None of the following can be established without Claude Code. They were **not** exercised on the implementing host and must be run once before the first release that carries this work; record the result here when done.

- [ ] A bare `fabrik` command starts as a plugin MCP server (the docs' own examples rely on PATH lookup, but it is not specified).
- [ ] An unset, defaultless `${user_config.*}` option substitutes an empty string rather than blocking the plugin or leaving the literal text. (If it leaves the literal text, `fabrik mcp` already treats it as unset; a plugin that fails to enable is the remaining risk.) If it does not, give both options a harmless default or fall back to required prompts.
- [ ] The plugin MCP server's working directory (the reason `CLAUDE_PROJECT_DIR` is passed explicitly), and that a session in a non-Fabrik project shows no error output and no noticeable start-up delay (SC-004).
- [ ] The hook's `systemMessage` is shown to the user at session start.
- [ ] `claude --dangerously-load-development-channels plugin:fabrik@fabrik` delivers pushed events from the plugin-bundled server.
- [ ] `FABRIK_LIVE_PLUGIN_CHECK=1 go test ./engine -run TestLive_WorkerExcludesPMPlugin` with `fabrik@fabrik` **installed and enabled** shows the PM plugin, and so its MCP server and action tools, absent from a worker's init event. ADR 2140 recorded that it had never been run in that environment; it matters more now that the PM plugin bundles an MCP server. The realistic blast radius if it fails is small (a worker's worktree has no daemon socket), but it is the only evidence.
- [ ] A dry-run release against a scratch fork: step 6b's commit carries the pinned refs and the paired version, and `git push --atomic main <tag>` lands both.
- [ ] (ADR 2322) A session's own environment reaches a plugin's stdio MCP server once `.mcp.json` no longer sets `FABRIK_SUBSCRIBER`, so an exported `FABRIK_SUBSCRIBER` / `CLAUDE_TOPIC` arrives.
- [ ] (ADR 2322) Removing a `userConfig` key from an installed plugin does not break the upgrade, and a stored old `subscriber` value does not still reach the server.
- [ ] (ADR 2322) The real `initialize` payload from interactive, `claude -p` and Agent SDK sessions, to decide whether the default may ever stream.

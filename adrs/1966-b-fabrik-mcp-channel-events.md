# ADR 1966-b: Fabrik MCP channel events

Status: accepted (issue #1968; builds on [ADR-1966-a](1966-a-fabrik-mcp-read-api.md); proposed in #1966)

## Context

ADR-1966-a gave an overseeing Claude Code session read tools backed by the daemon's in-memory state. They answer a question; they cannot make a session ask it. The events that matter most — an issue reaching Validate settled (above all under `fabrik:cruise`, where nothing further happens until a human acts), a pause, an escalation, an ejection, a timeout — are observed by the daemon the moment they happen and by nobody else. In one real day a single issue lost about 20 hours to pauses, ejections and timeouts that the owning session never heard about.

Claude Code **Channels** (a research preview) let a local MCP server push `notifications/claude/channel` events into a live session. A session only receives them if it was started with the channel enabled for that server (during the preview, `--dangerously-load-development-channels server:<name>` for a server not on the approved allowlist; Team/Enterprise orgs must also allow channels), the server must declare `experimental["claude/channel"]`, notification `meta` keys must be identifiers (a key containing a hyphen is silently dropped), and Claude Code never acknowledges a notification — a session that did not enable the channel drops it with no signal.

## Decisions

### 1. The push stream is the daemon socket, protocol v2

ADR-1966-a framed the socket so that a server-initiated (id-less) frame could share a connection with request/response traffic, and said the next issue would push events over it. This ADR does so: `ProtocolVersion` becomes 2 and `hello` lists `subscribe`, `unsubscribe` and `attach` **only when the engine's channel hub is running** (an optional `localapi.Streamer` implemented beside the unchanged three-method `Backend`). A client that does not find `attach` — an older daemon, or a hub that failed to open — degrades to the read tools; a SIGHUP self-upgrade can leave either side older than the other.

After `attach {subscriber}` the server acknowledges, *then* binds the session (so no push precedes the acknowledgement) and pushes `channel` frames, a `heartbeat` frame every `HeartbeatInterval` (30 s), and a final `superseded` frame if a newer attach under the same name displaces it.

**Amendment to ADR-1966-a's idle bound.** That ADR bounded a hung client with a 10-minute idle read deadline. A push-only subscriber sends nothing, so under that rule it would be dropped after 10 minutes. The deadline stays — `Server.IdleTimeout`, now a field so tests can shorten it — but every *successful server write* on an attached connection (a push or a heartbeat) moves it out by the full idle timeout. A client that is alive keeps the connection; one that is not fails the 5 s write deadline at the next heartbeat and is reaped within one interval, which is a tighter bound on a dead peer than the idle timeout was. A connection that never attaches is bounded exactly as before. Each attached shim holds one of the 32 connection slots; the shim retries a `busy` refusal.

### 2. A held-connection client that reconnects and re-registers

`localapi.RunStream` dials, checks `hello`, `attach`es under the subscriber name, and reads frames, swallowing heartbeats. Three missed heartbeats make a silent connection half-open and it reconnects; failures back off 250 ms → 30 s with jitter, never giving up while its context lives. **Every** connect re-attaches under the same name, so held delivery resumes with no action from the session — which is what makes the SIGHUP re-exec (it closes the socket) invisible. It reports connected/disconnected transitions (once per outage, not once per retry) and stops on `superseded`, because reconnecting would only start a fight with the session that displaced it. `fabrik mcp` turns those transitions into `daemon-unreachable` (still down after a 10 s grace, so a re-exec that re-binds quickly and a crash loop do not spam) and `daemon-reachable` (on the first re-attach after a reported outage, with `down_for_seconds`). Those two are live-only: a daemon that is down cannot hold them.

### 3. Subscriber names, subscriptions and the held queue

A subscriber is identified by a **stable name** supplied at launch (`fabrik mcp --subscriber` / `FABRIK_SUBSCRIBER`) — the operator's topic or session name, never a PID, because the name keys the held queue and must survive the session. With no name the shim makes no push connection and `fabrik_subscribe` refuses with the fix; there is no generated default. A second attach under a name **replaces** the first (rather than fanning out): this keeps delivery exactly-once per name and avoids a reconnect racing the previous connection's teardown.

A subscription ANDs its set dimensions (repos, issues, milestone, label patterns, event types) and ORs the entries within a list. Label patterns are globs where `*` matches any run of characters including `:` and `/`; they filter **label events only**; the default exclusion list (`fabrik:locked:*`, `stage:*:in_progress`, `fabrik:spawned-child:*`, `fabrik:credited-pr:*`, `fabrik:editing`) applies when `exclude_labels` is absent and is disabled by an explicit empty list — so absent and empty must stay distinguishable on the wire (`*[]string`). An item whose milestone is unknown never matches a milestone scope (the read API's "excluded, never guessed" rule); an item that moves into the milestone matches from then on because matching is evaluated at emit time. Bare issue numbers reuse the read API's resolver and its ambiguity error. Account-wide events (`claude-limit-*`, `daemon-*`) have no issue and ignore the repo/issue/milestone scopes.

The hub appends every matching event to a per-subscriber queue **before** any delivery. An attached session's drain loop sends in queue order and deletes an entry only after a successful write, so held and live events share one ordered path: held first (a digest entry queued while the subscriber was away is replayed individually, not re-digested; one collected while a session was attached keeps batching across a brief reconnect), then live. Dedup keys and counters are persisted lazily (coalesced to one `dedup.json` write per 250 ms, flushed by `Close`) so `Publish` never does disk I/O per event on the engine's poll path; a crash inside that window can republish one event. A failed write leaves the entry queued (at-least-once; a crash between write and delete can duplicate one event). Queues are bounded (default 200, `--channel-held-max`): the oldest are dropped and the next delivery starts with one coalesced `events-dropped` notice that does not count against the bound. Entries older than 7 days and subscribers with no attach for 30 days are pruned so the files cannot grow forever. Digest mode is per subscription (30 s–1 h); `validate-settled`, `escalated`, `paused` and `daemon-unreachable` bypass it.

Persistence is `.fabrik/state/channel/` — `subscriptions.json`, one `held-<hash>.json` per subscriber, and `dedup.json` (a bounded set of recent transition keys plus the settle-episode counters). Writes are tmp+rename; an unreadable file is quarantined, never fatal (as `workers.json`). State is loaded before the socket binds, so a reconnect during startup finds it, and because every change is written when it happens the SIGHUP exec needs no flush.

**Trust.** The socket has no authentication beyond its `0600` mode (ADR-1966-a). Any process of the same user can attach under any subscriber name and drain that name's held events, or subscribe on its behalf. That is the same trust boundary that already lets it read every issue's state; it is not widened, but it is no longer read-only.

### 4. Events are derived, never fetched, and never decide anything

R9 (zero GitHub cost) and R10 (observation only) shape everything:

- **Label events come from the store's own diff, not a parallel memory.** `itemstate.Change` now carries `LabelDeltas` (computed by the store from the before/after label sets, only for an item it already held), the mutation's `Origin` (`LocalLabel*` write-through = the engine; webhook; otherwise a poll) and, for webhooks, the sender and whether the engine's echo registry matched. The webhook echo of an engine write is an idempotent store no-op that never reaches an observer, and a reconcile that re-observes an unchanged label is a no-op diff, so **one event per actual change** needs no de-duplication logic. A board population, `Reset`, or an item's first creation is a baseline, not a change, so a (re)start announces nothing. Rejected: a per-item previous-labels map in the deriver, which needs its own cold-start baseline logic and races across observers.
- **Actor** is `fabrik` (write-through, a matched echo, or — under App auth — a sender equal to the App's bot login), `bot`, `human`, or `unknown` (a poll saw it first). Under PAT auth the operator's own login is indistinguishable from Fabrik's, so an unmatched sender is `human`. The echo is registered *after* the engine's REST call, so a webhook delivered in the microseconds between the call returning and the write-through is attributed by the sender rather than the echo; it still produces exactly one event.
- **Pause family from the classifier.** `paused`, `awaiting-input`, `escalated` and `stalled` are transitions into the corresponding `internal/attention` state (re-evaluated after a short debounce on label, stage-state, status and invocation changes, and on a 30 s ticker). They therefore agree with `fabrik_board` by construction, `stalled` uses the one `--stall-threshold` with no per-subscription override, and a pause's labels and `EnginePaused` are classified together rather than as two events. This replaces the originally planned per-site hooks in every `pauseFor*` function: the classifier already encodes the paused/escalated split (`PausedByEngine`, a counter at its limit, `awaiting-runaway-alert`), and a hook at each of ~20 sites would have been a second definition to keep in step.
- **Hooks only where the store has no signal.** `ci-timeout`, `review-timeout`, `children-spawned` and the merge-train events are nil-safe void calls placed after the engine's own writes; `landing-verification-failed`, `blocker-cleared` and `merged` are the label delta of the label the engine applies at exactly that transition (`merged` keys on `fabrik:awaiting-landing-verification`, which every landing path applies right after its Done transition, with `pr` from `fabrik:credited-pr:<N>` for merge-train members); the Claude suspension is an edge check on `claudeSuspendedUntilTime`, so a suspension that simply expires is reported too.
- **Enforcement.** `engine/channel_*.go` and `internal/channelevents` read item state only through `Peek`/`Scan` and are forbidden (by a source-scan test) from the engine's GitHub clients, `Store.Get` (which has a GitHub fallback), the live label-timestamp fallback and the live feedback and review gates; a sim test shows a run with a hub and a subscriber makes the same GitHub mutations in the same order as a run without one.

### 5. `validate-settled`

The label `stage:Validate:complete` is not gate-complete. Under a Validate stage with `wait_for_ci` and `wait_for_reviews` it is applied first, `fabrik:awaiting-ci` is then removed, and only afterwards does the review gate run and apply `fabrik:awaiting-review` — so a predicate over labels alone fires early, which is the failure the issue forbids. The anchor is therefore the engine's own definition of settled:

- **`runCatchUpPhase2`**, reached only when no Phase 1 handler (dependencies, review gate, auto-merge convergence, merge and CI gates) claimed the item. The observation hook (`noteValidateSettled`) sits at the very top, *before* the autonomy gate, because the headline cruise case returns there; it is a void call and changes no control flow.
- **`attemptMergeOnValidate`**, after its dependency, review-thread, review and feedback gates have all passed (`noteValidateLanding`). A yolo item is merged or queued inside that call — from `checkCIGate`'s Phase 1 handler, which claims the item so Phase 2 is never reached — so this is yolo's settle point.

At either point a **cache-only** predicate confirms (Validate, open linked PR, no paused/blocked/awaiting-* labels, no open blocker, no worker, and no unprocessed feedback — the feedback gate's definitions factored into pure cores shared with the live gate, with a drift test; the live gate itself reads GitHub and writes a cooldown, so it cannot run on the event path). The event is captured on the calling goroutine: a yolo item can be merged and moved to Done within the same pass, and an evaluation deferred past that would silently drop the event.

An **episode** starts at the first event and ends when the complete label is removed (`fabrik:revalidate`), the item is closed or leaves Validate, or the PR head moves after Validate completed (a reopen is a close then an open). The episode counter and the dedup key persist, so a restart neither replays an announced episode nor loses an unannounced one. `meta.next` mirrors `attemptMergeOnValidate`: `waiting-for-human` (the raw cruise label wins over yolo, or no autonomy), `auto-merge` (yolo, merge train off or auto-merge already enabled), `merge-train` (yolo, `merge_train: on`). `meta.ci` is read from cached check runs, which fill from `check_run` webhooks and gate reads, so an empty cache reports `unknown` rather than `none`; `meta.ci_gate` separately says the engine's own CI gate was configured and cleared. An item the poll does not revisit after the gates clear cannot be announced until something changes — the moment that clears the last gate is itself such a change.

### 6. Delivery is "written to the shim"

The daemon cannot know whether the session enabled the channel; Claude Code drops events silently when it did not. So the server's `instructions`, the `fabrik_subscribe` description and its response all state the launch requirement, and a successful subscribe does not claim delivery. Everything that depends on the preview contract — the method name, the capability, the params shape and the meta-key rule — is confined to `internal/mcpstdio/channel.go`, so a contract change is a one-file edit and the read tools keep working regardless.

## Consequences

- A session can supervise a milestone without polling; `validate-settled` is announced exactly once per episode and never early.
- The daemon socket is no longer purely read-only and now holds long-lived connections; the idle bound is replaced, for attached connections, by the heartbeat's write deadline.
- Events during a daemon exit, a self-upgrade exec or a crash are not captured; a daemon that is down cannot report itself (the shim does, live).
- A same-user process can drain another subscriber's held queue — unchanged in kind from ADR-1966-a's trust note, widened in effect.
- A restart loses the deriver's per-item memory by design (re-seeded silently); `awaiting-input-stale` cannot fire for an episode that began before the restart.
- The notification contract is a research preview and may change.

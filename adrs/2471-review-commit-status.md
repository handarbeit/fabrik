# ADR 2471: The `fabrik/review` commit status, a conditional-required permission, and review-wait attribution

## Status

Accepted (#2471). Builds on ADR 2465 (the head-aware per-reviewer verdict), ADR 2105 (a required App permission refuses existing installations at startup), ADR 2467 (review-wait anchor), ADR 2135 (warnings panel) and ADR 2466 (declined findings). The origin is community report #2239, mentioned for context only.

## Context

A repository can hold an expensive CI job until the review bot has reviewed the head commit, but only with a CI-side gate job polling the PR's reviews. Fabrik does not know that gate exists, so the held job looks like CI that has been pending for a long time: the CI wait timeout and the `fabrik:awaiting-ci` backstop count the review wait as CI time and the pause comment names the wrong cause. Fabrik already computes a per-reviewer at-head verdict (ADR 2465). Publishing it as a commit status gives workflows something to depend on and gives Fabrik the knowledge to attribute the wait.

Writing a commit status needs `statuses: write` under App auth (`repo` scope with a PAT). Adding it to `RequiredGitHubAppPermissions` would refuse every existing installation for a feature that is off by default (the ADR 2105 experience).

## Decision

1. **A Fabrik-owned status `fabrik/review`** (fixed name, not configurable) on the head of the item's open PR, written by a per-poll settle scan sourced from `board.Items` (`settleReviewStatusScan`). `pending` while an expected reviewer's review of the head is outstanding, `success` when every expected reviewer's review of the head asks for no changes, `failure` when one requests changes. Drafts get a status; closed and merged PRs do not.
2. **One verdict, one additive extension.** The state is `reviewStatusVerdict` over `reviewerStandings`; there is no second collapse of the history. `reviewerStanding` gains two booleans: `CommentAtHead` (the latest `COMMENTED` after any formal verdict is on the head), so a comment-only bot (Pruefer) can be told apart from one that has not reviewed the head, and `CommentFindings` (that review's findings marker, `parseFindingsMarker`, reports findings), so a head-commit review that carries findings does not read as clean. A review with no marker cannot be classified and counts as reviewed. `Kind`, `blocks()` and every existing consumer are unchanged. A declared reviewer with no review is `pending`.
3. **`reviewDecision` is ignored.** It answers "has anyone approved against branch protection", the status answers "have the stage's expected reviewers reviewed this head". The status may be stricter than the gate, which clears on any non-`DISMISSED` review. A declined finding is never treated as resolved (ADR 2466): a formal `CHANGES_REQUESTED` stays `failure`, and a comment-only findings review (`CommentFindings`) stays `pending` ("open findings"); either way until the head moves or the reviewer's latest review at the head changes.
4. **Opt-in, off by default.** A stage key `review_status` (`*bool`) and a flat config key `review_status` (default false); an explicit stage `false` wins over the repo key. Effective only with `wait_for_reviews: true` and a non-empty effective `expected_reviewers`; misconfiguration is a `review_status_config` warnings-panel entry and writes no status, so a dependent job is never held on a verdict that cannot arrive. Neither key adds a flag or environment variable.
5. **Permission tier: conditional-required (refuse if enabled).** `RequiredGitHubAppPermissions` is unchanged. `RequiredGitHubAppPermissionsWithReviewStatus` raises `statuses` to `write` only when `ReviewStatusEnabled` (the repo key or any stage's `review_status: true`); `setUpGitHubAppAuth` and `fabrik init --github-app` use it, so startup and init cannot disagree, and the refusal uses the shared `PermissionShortfallRemedy` plus a `statuses` explanation line. Disabled: the permission is neither checked nor required. Rejected: *required* (refuses every installation), *silently optional* (the feature would quietly never work, the ADR 2071 failure ADR 2105 deleted). Init learns "enabled" from the on-disk config and stages when they exist; otherwise the engine's startup refusal is authoritative. PAT mode is documented only (`repo` scope).
6. **Write failures never block.** A failed write is logged, reported once on the warnings panel (`review_status_write`, stable fingerprint, resolved by the next success), retried every poll (the last-written record is not advanced) and never pauses an item or gates anything. Transport failures are left to the forge-unreachable hold.
7. **Attribution moves the CI dwells and rewords the backstop; it adds no timeout.** While the last written status for the item's PR is `pending`, `max(anchor, reviewWaitFloor)` is used by the liveness-stall dwell and the two `CIWaitTimeout` dwells, so review time never counts as CI time. The `CIBackstopTimeout` is not suppressed: `fabrik:awaiting-ci` skips the review gate, so no review-wait timer runs there, and suppression would leave a silent reviewer unbounded. The backstop fires on its existing schedule and, while `pending`, its pause comment is `🏭 **Fabrik — review wait timeout**` naming the head and reviewers (cause `review-timeout`, same #1408 reuse). Rejected: suppress every CI timer (unbounded wait), fold in `ReviewWaitTimeout` (a new timeout). **Known limitation:** Fabrik cannot see which CI jobs are gated on the status, so the attribution applies to every CI wait of an item while its status is `pending` — not only to jobs that depend on it. A hung CI run during a slow review is therefore bounded only by the `CIBackstopTimeout` and paused as a review wait. Restricting the attribution to gated jobs would need Fabrik to know the workflow's dependencies, which it does not; the user guide tells operators to enable `review_status` only where CI is meant to wait on the review. A failed status write keeps the end of an earlier review wait (as an unwritten record) rather than dropping it, so a retried write does not lose the attribution.
8. **Attribution is memory-only and host-clock.** The record is rebuilt by the first scan after a restart; until then behavior is today's, never a spurious escalation. Its instants are host-clock times because the CI dwells compare with `time.Since` (ADR 2467). A failed write does not count as a review wait: CI is not held on a status that does not exist. Reading the status's `updated_at` back would cost a REST read per item per poll for little gain.
9. **Documented gaps.** A new push has no `fabrik/review` context until the next poll writes `pending`, so a dependent job must treat an absent context as not ready (the worked example does). GitHub Actions has no `needs:` on an external status, so the example is a polling gate job; required-status branch protection gives the same hold. The status applies while the item sits in an enabling stage, so Review and Validate should both enable it.

## Consequences

- No existing installation changes behavior or permissions; operators who opt in are told at startup what is missing.
- The status and the review gate read one standing per reviewer and cannot disagree about it at one head; the status is intentionally the stricter of the two.
- Verified by unit tests per behavior, the three permission cases with `newFakeGitHubAppServer`, init/engine agreement, and a sim twin; each behavior has a per-Engine neutralisation seam (`SetReviewStatusDisabledForTest`, `SetReviewStatusHeadBlindForTest`, `SetReviewWaitAttributionDisabledForTest`) and the permission tier was shown non-vacuous by removing the `statuses: write` raise (four tests fail).
- Sim fidelity: the sim models neither the `statuses: write` permission (a refusal is injected with the fault table) nor the `status` webhook (`tests/sim/simgh/FIDELITY.md`).

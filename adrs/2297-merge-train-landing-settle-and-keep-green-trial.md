# ADR 2297: Wait out a transient `blocked` after mark-ready on the same PR, and keep a green trial that did not merge

## Status

Accepted (#2297). Amends ADR-059 D3 (landing) and D5 (recovery) for the mark-ready → merge window; builds on ADR-1153/ADR-1441 (`mergeable_state` is never a green shortcut), ADR-1410 (blocking landing polls are bounded by `CIBackstopTimeout`), ADR-072 (`MergePR` self-gates on `mergeable_state`) and ADR-2051 (restart resume of a landing via `reconstructTrainState`). The report this fixes is #2237 (mentioned for context only).

## Context

A green trial is landed by promoting its draft CI PR to ready and merging it. Marking a PR ready fires `pull_request: ready_for_review`, which starts a new workflow run on the same head. For a short window that run's required check is queued, pending or not yet visible, and GitHub reports `mergeable_state = "blocked"`.

`pollForMergeable` judged a PR only by its check runs and suites (`classifyLandingCI`), so with the trial's draft-run checks green it said "ready" at once. `MergePR` then refused (`ErrNotMergeableCI`), and both landing paths treated any `MergePR` error as a failed landing: they posted "merge failure — manual intervention may be required", deleted the trial branch (closing the PR, which also cancelled the pending `ready_for_review` run under cancel-on-close workflows and left a `cancelled` check on the green commit) and left the members Queued. The next pass assembled a new trial and ran the full CI again; one single-member train built three ~17-minute trials on an unchanged base this way.

The stage path already treats the same refusal as transient (`reenableAutoMergeAfterRebase`).

## Decision

1. **One settle loop owns the window.** `settleAndMerge` replaces `pollForMergeable`. A merge is attempted only when `classifyLandingCI` is green **and** `gh.MergeableStateAccepted` holds. `mergeable_state` gates the merge but never makes a verdict green, which keeps ADR-1153/ADR-1441 intact.
2. **Two reasons to wait, one deadline.** Pending checks or an outstanding suite wait under `CIBackstopTimeout`, set at entry and never reset. A green verdict with a not-yet-accepted state (`blocked`, `unknown`, `null`, empty) additionally has a short bound, `trainBlockedSettleTimeout` = 5 minutes, a constant with a per-Engine test override. It is not user-configurable: that avoids a new flag, env var, `workerenv` entry and USER_GUIDE section, and can become a setting if a repository's workflows queue slowly.
3. **A refused merge is retried on the same PR.** `ErrNotMergeableCI` re-enters the green-but-blocked wait, sharing the deadline and the short bound, so a perpetually refused PR cannot loop for ever. `ErrNotMergeable` (a `mergeable` GitHub has not computed yet) is treated the same — a small widening of the issue's R3, because a nil `mergeable` just after `ready_for_review` is the same transient; a real conflict is caught by the per-iteration `dirty` check. Any other `MergePR` error ends the attempt.
4. **What ends an attempt as failed:** a confirmed failed check or required context, `dirty`, the PR head moving off the validated head (compared on every read rather than pinning the merge with `MergePRAtHeadSHA`, which would thread a SHA through the callers and the existing recorders; the residual window is one API round-trip, as before), either bound running out, or a non-transient merge error.
5. **Keep a green trial that did not merge.** When an attempt ends without a merge with the bound or backstop expired, a non-transient merge error or a cancellation, **and** a fresh live `FetchCommitsBehind` shows the base unmoved (a read error counts as moved — fail closed, as `trialBehind`), only the local worktree is released and the PR and origin branch stay (`releaseLandingTrial`). The same helper serves `landSingleton`, which has no `trialBehind` gate. Red, not-passed, dirty, moved head, moved base and a merge release the trial exactly as before. Cancelled (shutdown/drain) keeps it: it must not destroy a green trial.
6. **No new resume logic.** The next dispatch finds the kept PR through `reconstructTrainState` Route 2: both the batch integration PR and the singleton draft CI PR carry the member list, so `parseTrainMembers` matches either, and `resumeTrain` → `landGreenBatch` → `landMergeTrainBatch` lands it (a singleton resumes as a one-member batch; the PR is already ready, so it is not re-marked). A restart during the wait leaves a `stepLanding` record that `adoptTrainRun` drops with `discardKeepTrial`; with the PR no longer deleted, Route 2 (open) or Route 1 (merged) finishes it exactly once. Once the base has moved, the existing main-moved rebase path applies unchanged.
7. **One comment, only for a real failure.** A waiting landing posts nothing. `dirty`, a moved head, either bound expiring and a non-transient merge error post one `🏭 **Fabrik merge-train — merge failure**` comment naming the PR, the `mergeable_state` observed and the reason, deduped by a hidden `<!-- fabrik:train-landing-failure pr=N -->` marker in the survivor's cached comments (restart-proof) plus an in-memory set (the window before the cache refreshes). Red and not-passed stay log-only; cancellation posts nothing. The old non-deduped "landing timeout" comment is subsumed.
8. **Seams** (per-Engine): `SetLandingSettleDisabledForTest` (merge at once, no retry — the original defect), `SetKeepGreenTrialDisabledForTest` (always delete — the original cleanup), `SetLandingBlockedBoundForTest`, `SetLandingCleanupObserverForTest`. The sim gains `ReadyForReviewStep` (`SeedReadyForReviewSteps`), recorded in `FIDELITY.md`.

## Consequences

- A transient `blocked` or a single merge refusal no longer discards a validated trial, posts a comment or costs a CI run; a trial that cannot land for another reason is retried on the same PR on the next pass.
- A kept PR that keeps failing is re-landed every train cycle, each with a bounded wait of up to five minutes in a worker goroutine; the failure comment is deduped. Accepted over rebuilding a 17-minute trial each time.
- A resumed kept PR re-polls trial CI first (`pollTrainCI`, up to `CIBackstopTimeout`); a still-pending `ready_for_review` check delays that, and an expiry there dissolves the batch. Existing Route 2 behaviour, now more reachable.
- Other cleanup paths (red, dirty, moved head, moved base) still close the PR and can still cancel the run under cancel-on-close workflows; the classification of the resulting `cancelled` check is ADR 2296.
- No live e2e twin: the window depends on a repository's workflow triggers and timing. The sim and unit tests carry the proof.

# ADR 1250: Review authority — advisory vs. authoritative, an axis orthogonal to autonomy

**Status:** Accepted
**Date:** 2026-07-29
**Issue:** [#1250](https://github.com/handarbeit/fabrik/issues/1250)

## Context

Fabrik's review model treats every review as advisory to its own progression. `checkReviewGate` (the stage-advance gate) and `reviewGateBlocksLanding` (the landing-decision gate, ADR-1216) both clear on the same condition — `reviewGateOutstanding`'s `len(outstanding) == 0 && hasReviews` — which asks only whether reviewers have *responded*, never what they *said*. A `CHANGES_REQUESTED` review does not, by itself, stop advancement; a required reviewer only needs to submit, not approve. On a repo with no branch protection, nothing blocks at all.

This was a reasonable default when CodeRabbit was one advisory voice among several, but retiring CodeRabbit makes Pruefer the sole automated reviewer, and some projects will add required human reviewers and risk-tiered human review (#1051, #1177) whose verdicts must actually bind Fabrik's progression — not just be looked at.

The merge layer already honors verdicts, asymmetrically: `MergePR` refuses when `mergeable_state=blocked` (ADR-072/#1094), and `enablePullRequestAutoMerge` lets GitHub hold the merge until branch protection is satisfied. The stage-advance layer had no equivalent. This ADR closes that gap one layer up — at the advance and landing decisions, not just the final `MergePR` call — extending ADR-072's principle that the engine self-gates rather than relying solely on GitHub configuration.

A second design question this issue resolves: is Fabrik's automation level ("does it proceed without a human clicking go") the same axis as review bindingness ("what must be true before proceeding is allowed")? They were conflated in practice — `yolo`/`cruise` simply advanced or merged once the (advisory) gate cleared, so a project wanting binding review had no way to express it short of disabling `yolo` entirely, which also disables everything else `yolo` automates.

## Decision

**Autonomy and authority are two orthogonal axes**, not one:

- **Autonomy** (`yolo` / `cruise` / manual, #1055's future profiles) controls *timing* — does Fabrik act without a human clicking go, and how far does it advance unattended.
- **Authority** (`review_authority: advisory | authoritative`, this issue) controls *the gate* — what must be true about a review's verdict before advancing or merging is allowed at all.

`review_authority` is a per-stage YAML field on `stages.Stage` (`ReviewAuthority string`, `{"", "advisory", "authoritative"}`, default `""`/advisory), following the exact precedent `WaitForReviews` set: opt-in, stage-scoped, independently configurable on each stage that needs it. `authoritative` is meaningful only alongside `wait_for_reviews: true` — the gate it strengthens.

**The new check is additive, and lives inside the existing clearing branch, never beside it.** `reviewGateAuthorityVerdict(reviewDecision string, reviews []gh.PRReview) (satisfied bool, reason string)` (`engine/reviews.go`) is called from *inside* `checkReviewGate`'s and `reviewGateBlocksLanding`'s `len(outstanding) == 0 && hasReviews` branch — the branch that, in advisory mode, clears unconditionally. In `authoritative` mode it must *additionally* be satisfied. A PR with zero reviews stays blocked by the outer advisory condition regardless of mode; this issue never widens what advisory already clears, only narrows it further when opted in. ADR-1216's forward constraint — any change to the clearing condition belongs in the shared predicate, not duplicated at a call site — is honored by construction: both gate functions call the identical `reviewGateAuthorityVerdict`, so they can never disagree on what "satisfied" means, exactly as they already cannot disagree on "outstanding" via `reviewGateOutstanding`.

**Verdict source: prefer GitHub, fall back to Fabrik's own computation.**

1. When `reviewDecision` is `APPROVED`, `CHANGES_REQUESTED`, or `REVIEW_REQUIRED` — a real branch-protection review requirement, computed server-side including CODEOWNERS and required-approval-count rules — that value is authoritative. Satisfied only on `APPROVED`. Fabrik does no CODEOWNERS parsing of its own; GitHub's server-side computation already folds it in.
2. When `reviewDecision` is `""` (no branch-protection review requirement configured), falling back to advisory behavior would make `authoritative` mode a silent no-op on such a repo — indistinguishable from advisory to an operator who opted in expecting it to matter. Instead, Fabrik falls back to its own computation: satisfied unless any submitted review is `CHANGES_REQUESTED`. This keeps `authoritative` meaningful everywhere, not just on repos with branch protection configured to match.
3. Any other non-empty `reviewDecision` — an undocumented future GitHub enum addition — blocks conservatively instead of silently falling through to (2)'s fallback; GitHub did report a real verdict there, just not one Fabrik recognizes, so treating it as "no requirement configured" could wrongly satisfy the gate.

**`yolo`/`cruise` never bypass an authoritative gate — and need no new code to enforce that.** Because the check lives inside the shared clearing predicate rather than at `attemptMergeOnValidate`'s or `handleStageComplete`'s yolo/cruise decision points, `attemptMergeOnValidate` simply never reaches its merge/enqueue logic while `reviewGateBlocksLanding` returns `true` — the exact same mechanism that already withholds merge from a `yolo` item with an outstanding *requested* reviewer. `authoritative + yolo` therefore "waits" for free: `yolo` still automates the merge's *timing* — no human click is required once the gate clears — but it cannot force a still-`CHANGES_REQUESTED` PR through. This is a deliberate tightening relative to advisory behavior, not a limitation to work around: a risk tier requiring one specific human approval (a future #1051 policy) composes as "`yolo` automates everything except that one approval," exactly as intended. `cruise` composes identically — `hasCruiseLabel` is checked before `reviewGateBlocksLanding` is ever consulted, so a cruise item never reaches the authoritative check at all; cruise's existing "leave the PR for human merge" behavior is unaffected by `review_authority`.

**Fetching `reviewDecision`: live-fetch only when opted in, not a new cached field.** `FetchPRReviewDecision(owner, repo string, prNumber int) (string, error)` (`github/prs.go`) is a new GraphQL-by-PR-number query, mirroring `prNodeID`'s shape (`repository(owner,name){ pullRequest(number){ reviewDecision } }`) rather than nesting inside `closedByPullRequestsReferences`. REST has no equivalent field, so this cannot be retrofitted onto the existing `FetchPRReviews`/`FetchPRReviewRequests` REST calls. The by-PR-number shape works identically for default-branch and `base:<branch>` items — no dependency on `closedByPullRequestsReferences`, which is structurally empty for the latter. The call is added to `engine.GitHubClient`, `boardcache.ReadClient` + `GitHubAdapter` (pass-through) + `CacheImpl` (delegate-always, no caching — mirroring `FetchPRReviews`/`FetchPRReviewRequests`'s "review state is highly volatile" rationale), and is made only when `stage.ReviewAuthority == "authoritative"` and the gate has already reached the branch where it matters — so the extra GraphQL round-trip is paid only by stages that opt in, never by advisory (default) stages.

This was a deliberate simplification over the alternative of adding `LinkedPRReviewDecision` to `gh.ProjectItem`, extending `fetchItemDetailsQuery`, and teaching `boardcache/delta.go` to keep it fresh via `pull_request_review` webhooks. The live-fetch approach avoids a schema/cache-freshness project entirely, is symmetric across both PR-linkage paths, and mirrors `reviewGateBlocksLanding`'s pre-existing "always re-fetch live, never trust the snapshot" design (ADR-1216) — review state is exactly the kind of highly volatile data that design already exists to handle correctly.

**Fetch failure blocks conservatively, never falls back silently.** A `FetchPRReviewDecision` error at either gate site does not clear the gate and does not fall back to the no-branch-protection computation — an unreadable verdict is unknown state, not "no branch protection configured." This mirrors the existing `FetchPRReviews`/`FetchPRReviewRequests` failure handling in both functions (discard, block, log, retry next poll).

**Graceful non-clear reuses the existing pause path — no new machinery.** A verdict that never resolves (an unfixable finding, or a required human who never approves) falls through into whatever "still blocked" logic already existed for that outstanding state: `checkReviewGate`'s bot-escalation ladder and `checkAwaitingReviewTimeout`, ultimately `pauseForReviewTimeout`/`pauseForReviewCycleLimit`. The existing `ReviewWaitTimeout`/`MaxReviewCycles` bounds apply unchanged. `checkAwaitingReviewTimeout` gained one new parameter (`authorityReason`) purely for messaging — so an operator watching a paused issue sees "a reviewer explicitly requested changes" rather than the misleading "no reviews submitted yet."

## Consequences

**No behavior change for advisory (default) repos.** The authoritative check is gated on `stage.ReviewAuthority == "authoritative"` exactly, checked first; every pre-existing `checkReviewGate`/`reviewGateBlocksLanding`/`attemptMergeOnValidate` test passes with zero changes to its setup (pinned by `TestCheckReviewGate_Advisory_ChangesRequestedReview_StillClears` and `TestAttemptMergeOnValidate_Advisory_ChangesRequestedReview_StillMerges`, which additionally assert `FetchPRReviewDecision` is never called in advisory mode).

**Forward constraint: authority checks belong inside the shared clearing predicate, never beside it.** Any future change to what "satisfied" means in authoritative mode must be made in `reviewGateAuthorityVerdict`, called identically from both gate sites — never duplicated inline at either call site, and never layered on top as a separate yolo/cruise-aware branch. The latter is the specific mistake this design avoids: adding a yolo-aware bypass around the gate (instead of a check inside it) would silently reintroduce "yolo forces through a still-blocking verdict," defeating the entire feature. A reviewer implementing #1051's risk-tiered policy on top of this mechanism should set `review_authority` per stage/repo and rely on the gate; it must not add its own bypass logic.

**One extra GraphQL call per gate evaluation that reaches the "would otherwise clear" branch**, paid only on stages with `review_authority: authoritative`. Stages without it are unaffected — pinned by the advisory-mode non-regression tests above, which assert zero `FetchPRReviewDecision` calls.

**CODEOWNERS and required-approval-count enforcement is entirely GitHub's**, whenever `reviewDecision` reflects a real branch-protection requirement. Fabrik adds no parsing of its own; the no-branch-protection fallback is explicitly scoped to the case where no such requirement exists, so CODEOWNERS is moot by definition there.

## Alternatives Considered

**Add `LinkedPRReviewDecision` to `gh.ProjectItem`, kept fresh via GraphQL query + webhook deltas.** Rejected as the initial implementation: more code (schema change, delta handler, freshness invariant to maintain across two independent PR-linkage paths), for a benefit (avoiding one GraphQL call per authoritative gate evaluation) that only matters at a polling cadence far above what `ReviewWaitTimeout`-bounded gates need. The live-fetch approach can migrate to this later if call volume ever becomes a real cost, without changing the pure-function contract (`reviewGateAuthorityVerdict` takes `reviewDecision` as a plain string regardless of where it came from).

**Enforce authority only at the landing gate (`reviewGateBlocksLanding`), not the advance gate (`checkReviewGate`).** Rejected: the issue explicitly requires both — a `CHANGES_REQUESTED` review with a top-level body but no inline comments produces zero reinvoke dispatch today (`handleReviewGate`'s `buildReviewThreadComments` check only fires on inline comments), so enforcing at the landing gate alone would let such a PR sit unactioned yet still eventually attempt to land, relying entirely on `reviewGateBlocksLanding` to catch it every poll. Enforcing at `checkReviewGate` too means the item never leaves `fabrik:awaiting-review` in the first place, correctly engaging the existing timeout/escalation ladder from the point the verdict is known, not just at the final landing attempt.

**Add a `yolo`/`cruise`-aware bypass around the review gate instead of a check inside it.** Rejected — this is the composition risk the issue itself flags, and the specific bug the "inside the clearing branch, not beside it" placement exists to prevent. A bypass would have to be re-added by every future landing path; a check inside the shared predicate is enforced everywhere the predicate is consulted, by construction.

**Repo-level config (a `map[string]string` on `Config`, mirroring `RequiredStatusContexts`) instead of a stage YAML field.** Rejected: `checkReviewGate`/`reviewGateBlocksLanding` already receive `*stages.Stage` at every call site, so a stage field requires zero new plumbing, while a repo-level map would need owner/repo threaded through both functions for no compensating benefit — `wait_for_reviews`, the gate this feature strengthens, is already stage-scoped, and `review_authority` should follow the same precedent rather than introduce a second configuration surface for the same gate.

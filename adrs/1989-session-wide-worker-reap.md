# ADR 1989: Reap a killed worker's whole process tree — its session and the command sessions it spawned

## Status

Accepted (#1989). Revised after a live validation finding (see "What the first design got wrong").

## Context

When the engine stopped a Claude worker, the worker's `go test` → `sim.test` / `vitest` / `tsc` trees could survive and run on, orphaned, for hours (12 orphaned `sim.test` processes at ~94% CPU on 2026-09-30, load ~30, timing out the sim pre-gate).

`setCmdProcAttr` starts the worker with `Setsid` (#1798), so the worker's PID is both its process-group ID and its session ID (SID). The stop path, `killProcGroupGraceful`, signalled `-pid` — the worker's **process group** only. #1798 (`reapTrackedDescendants`) and #1814 (the registry-independent worker-session sweep) SIGKILL session members, but only per PID, only with SIGKILL, only at invocation end — and, as the finding below shows, only members of the **worker's** session.

### What the first design got wrong

The first version of this change assumed Claude's Bash tool starts each command in a process group of its own **within the worker's session**. The ADR flagged that as an unverified assumption, and it was false. Observed live on macOS, three running workers (and re-confirmed from this very worker's own tree):

```
WORKER 37170 pgid=37170 sid=37170   claude --output-format stream-json …
   49064 ppid=37170 pgid=49064 sid=49064   /bin/zsh -c source …/shell-snapshots/…   ← Bash-tool shell: its OWN session
   49066 ppid=49064 pgid=49064 sid=49064   node …/pnpm exec vitest …
   49069 ppid=49068 pgid=49069 sid=49064   node …/vitest …                          ← separate group, the SHELL's session
```

Each Bash-tool command runs through a shell that calls `setsid()` itself. None of 33 inspected descendants had `sid == worker PID`. So:

- `sessionreap` keyed on the worker's SID reached none of them, and neither did #1798's `reapTrackedDescendants` or #1814's session sweep, which also filter on `Getsid(pid) == workerPID`. That — not "the sweeps failed open under load" — is the simpler explanation of the 2026-09-27/30 orphans, and it means the *normal* case is what the earlier ADR called a "known gap" (a descendant that calls `setsid()`).
- Only two things link a Bash-tool tree to its worker: the **parent chain while the worker is alive** (the shell's PPID is the worker, until the worker exits and the shell is reparented to PID 1), and the **worktree cwd** (ADR 063's teardown reaper).
- The earlier R1 tests passed because their synthetic child stayed in the worker's session (`setpgrp` / `set -m`). That shape does not occur with the real CLI.

### R1 — recorded outcomes

Against the unmodified code, a same-session, separate-group child received neither SIGINT nor SIGTERM from `killProcGroupGraceful` and was SIGKILLed only at invocation end by the #1798/#1814 sweeps ("survives the stop path, caught later"). That is the shape of a child the worker itself leaves in its own session (a hook, an MCP server). The shape of a **Bash-tool command** is different and strictly worse: against the pre-change code *and against the first version of this change*, the command session is never reached at all — not by the stop path, not by either sweep. The engine test `TestBashToolSession_*_WorkerSIDOnlyLeavesItRunning` pins that.

## Decision

1. **The target set is `{worker SID} ∪ {command-session SIDs}`.** Every process in any of those sessions is a member. Command sessions are discovered from the **parent chain while the worker is alive**: walk the process table by PPID from the worker; every descendant whose session ID is not the worker's names a command session. This is safe by construction — a descendant either inherits the worker's SID or is the leader of a session some descendant created, so any other SID it carries was created below the worker.
2. **Discovery runs only while the worker is provably ours.** Once the worker is reaped its PID may belong to an unrelated process, whose descendants must never be adopted. `Track` records the worker's start-time token right after `cmd.Start()`, when the PID belongs to exactly one process, and discovery proceeds only while the live holder of that PID still has that token. The post-exit `Sweep` never discovers; it uses only sessions sampled while the worker lived.
3. **Sampling during the invocation.** Once the worker exits, its children are reparented to PID 1 and the chain is gone, so `sessionreap.Tracker` samples the tree on a cadence (`commandSessionSampleInterval`, 2 s; one process listing per sample) and accumulates the command sessions. The stop path additionally re-discovers immediately before each signal, so a command started during a grace window is still reached, and `Escalate` remembers sessions found at an earlier step so they still receive SIGTERM/SIGKILL after the worker (their anchor) has died. **Residual gap:** a command that starts and orphans itself between two samples, after which the worker exits cleanly, is not seen; ADR 063's worktree-cwd reaper is the cover.
4. **A command session's SID is trusted only while it provably names the sampled session.** A recycled PID that became a session leader would otherwise alias an unrelated session (for instance another worker). Each sampled session carries the leader's start-time token (`/proc/<pid>/stat` field 22 on Linux, `kinfo_proc.p_starttime` on macOS). If no live process holds PID == SID, the leader is gone and any member carrying the SID belongs to the old session (a PID naming a live session is not reused). If a live process holds it, it is the sampled leader only if its token equals the recorded one; a recorded "" (leader already gone at sampling) or an unreadable token fails closed. Checked at resolve time and again every sweep pass; `leaderWatch` additionally abandons a session whose leader PID reappears mid-escalation.
5. **`Escalate`** applies today's SIGINT → grace → SIGTERM → grace → SIGKILL, with unchanged durations and zero-grace semantics, to every member of every target session (leader included; zombies excluded — they answer `Getsid` but cannot be acted on, so counting them would hold a grace window open and inflate the R5 count). The liveness probe is "any member of any target session alive". `killProcGroupGraceful` keeps its signature and finds the tracker through a registry keyed by worker PID. `killProcGroup` stays group-only (the webhook subprocess uses it and has no grace escalation).
6. **`Sweep`** is the post-exit step: SIGKILL every remaining member of the worker's SID and of each valid sampled command session — including a command shell that is still alive, orphaned. For the worker's own SID a live process whose PID equals the SID is a recycled PID, and that SID is refused; command sessions are validated independently. It runs in `runClaude` after `killProcGroup` and before the #1798/#1814 reapers, which stay as the backstop for the worker's own session.
7. **Survives an engine restart.** Each newly observed command session is persisted in `.fabrik/state/workers.json` as a child record of the worker's record (`parent_id`, the session leader's PID as `pid`, the start token as `start_token`). The proc-janitor reaps a command session only once its parent worker record is confirmed dead or recycled, or is gone — never while the worker lives, since a command a live worker deliberately left running is its own business — and only through the same start-token validation. A command-session record is never swept as if it were a worker (it carries no worker identity; doing so would reap a live invocation's command). At invocation end, records of sessions that are now empty are removed; a session with a surviving member keeps its record for the janitor. Pruning uses the same two-consecutive-empty-scans rule as worker records.
8. **R4 safety**: every SID in the set passes `CheckSID` (0, 1 and the caller's own session are refused and logged); `Getsid(pid) == sid` is re-checked immediately before each signal against the SID the member was enumerated under; a listing error degrades to the leader's process group, never wider.
9. **R5 visibility**: one line per signal step and per sweep with the member count, truncated command names, and — when present — `+ N command session(s) [SIDs]`. A non-zero count with `exit=clean_exit` is the signal that a worker left work running.
10. **What happens to #1798/#1814.** Their `Getsid(pid) == workerPID` filters are **correct but narrow**: they reach processes that stay in the worker's own session (a hook, an MCP server, anything `claude` itself forks without `setsid`) and nothing else. They no longer claim to cover Bash-tool commands. #1814's janitor is extended for command sessions through the child records above rather than by loosening the filter; #1798's per-descendant registry is left as is for what it does reach. Neither is retired.
11. **Shared package, Pruefer.** `internal/sessionreap` is a leaf shared by `engine` and `pruefer` (log output via a caller-supplied `Logger`). This overrides ADR-1113 §6's duplication choice for the session logic. Pruefer starts Claude with `Setsid`, tracks and escalates through the same package, and runs `Sweep` after `Wait`; it keeps no worker records or janitor (so a Pruefer crash mid-review leaves its command sessions to the cwd reaper).

## Consequences

- A worker's Bash-tool commands and the `go test` / vitest / tsc trees below them receive SIGINT/SIGTERM and then SIGKILL on every stop path; a post-exit sweep reaps leftovers on clean exits; the janitor reaps them after an engine crash — in each case without depending on per-candidate `ps` probes.
- Several SID-based killers coexist; a duplicate SIGKILL is harmless, and `Sweep` running first keeps counts and logs consistent.
- Each sample costs one process listing (`/proc/*/stat` reads on Linux, one sysctl on macOS), plus `Getsid` for the worker's descendants only.
- **Shared long-lived servers (accepted trade-off)**: a command session is the worker's to reap because a command in it was started below the worker, not because the session is provably exclusive to it. A server that a Bash-tool command starts, that calls `setsid()` while still a live descendant of the worker at a sampling instant, and that another worker or later command then reuses (e.g. a build server) is reaped when the worker's invocation ends, and the other user sees a dropped connection. A daemon that double-forks is reparented to PID 1 immediately, is never named by the parent-chain walk, and is not touched. A cwd restriction was considered and rejected: the orphans this issue exists for ran from sim-test temp dirs outside the worktree. Every such reap is visible in the R5 line (`exit=clean_exit` with the command names). This is unconfirmed against a real shared server; if one turns up, the fix is a per-tool allowlist, not a narrower target set.
- **Known gaps**: a command started and orphaned between two samples, with the worker then exiting cleanly (ADR 063 covers it where its cwd is in the worktree); a descendant of the command that itself calls `setsid()` again (a nested daemon) is a session no parent-chain walk names *unless* it is sampled while its parent chain is intact — the walk follows PPID transitively, so it is, but only while the chain lasts.
- Tests carry neutralised twins (`Options.WorkerSIDOnly`, the pre-command-session behaviour, at the package and engine level) asserting that the Bash-tool command session is **not** reached without the extension, so the acceptance assertions are not vacuous; fixtures use `setsid()` via perl so they run on the Linux CI's dash as well as macOS.
- **Live confirmation.** The process shape above is confirmed live (this worker's own tree: `claude` leads its own session, its Bash-tool shell leads another). A live R5 line from a real `max_wall_time` stop during a `go test` run still has to be captured by an operator on a worker running this binary; it is not part of the automated suite.
- The helper API (SID in, refusals, re-check) is reusable by #1957 (group-ownership verification before stored-PID kills).

# ADR 2171: The situation view, the `fabrik_situation` tool and the `situation` digest

**Status:** Accepted
**Issue:** #2171
**Builds on:** ADR-1966-a (local read API, zero GitHub cost), ADR-1966-b (channel hub, subscriptions, held queue), ADR 2120 (pending decisions, options), ADR 2124 (poll liveness, partition state, `pipeline-stalled`), ADR 2170 (anomaly episodes)
**Amends:** ADR 2169 (the catch-up becomes the digest for subscriptions that take it), ADR-1966-b (adds an event type and a read method)

## Context

The most useful message in the 2026-10-11 in-situ session was the five-entry catch-up on resubscribe: one item awaiting input and four settled at Validate. That one snapshot was the whole "what needs you" picture. An overseer could not get it on demand or on a cadence: it rebuilt it from `fabrik_board` filters, `fabrik_health` and its memory of earlier pushes, then went to `gh` and the log for merge-train state and anomalies. Every piece already existed separately (attention classification, the catch-up builder, health, the anomaly episodes). What was missing was one view that rolls them up, and a push that delivers it only when it changed.

## Decision

1. **One builder, three consumers.** `engine/localapi_situation.go: buildSituation(scope)` produces a `localapi.SituationView`; `engine/channel_situation.go: renderSituation` renders it. The `fabrik_situation` tool, the requested and scheduled `situation` digest, and the attach / reconnect / restart catch-up all call them, so their content is identical for the same state (tested at the engine and in the sim). There is no second classifier: items are placed by `internal/attention`'s own `(State, Code)` through `attentionInput`; gate holds and retry facts come from the `anomalyState` the `item-wedged` / `retry-starved` events read (now behind one accessor, `openAnomalyFacts`); poll, worker, Claude-hold and partition facts come from `Health`'s own sources.
2. **Sections.** `merge_decisions` (code `awaiting-merge-decision`: Validate complete under `fabrik:cruise` with an open PR; the review verdict is `reviewSummary` and the CI verdict `cachedCIVerdict`, the cores `validate-settled` already uses - so there is one CI classifier in play, not `localAPIBackend.ciVerdict`'s second one), `gates`, `human_input` (`needs-human` and `escalated`, with `ResumeVia`), `decisions` (`suspended`), `stalled` (R1 names no section for it; an item the classifier calls stalled must not vanish), `merge_train`, `health`, `anomalies`. "Awaiting a merge decision" follows the classifier: an item with no autonomy label at Validate is `idle`/`waiting`, whereas the older per-item `validate-settled` catch-up also reported it as waiting for a human - a known difference; yolo items, which the engine lands, are not listed. "Queued" under health means train-queued members summed over partitions; a dispatch deferred for lack of a worker slot is not counted.
3. **One item, one section.** Placement is a function of the single classification, so an item is in at most one item section. A gate entry exists for an item classified `waiting` / `idle` that has an unannounced hold (or a `fabrik:awaiting-ci` / `fabrik:awaiting-review` label wait); a hold already announced as `item-wedged` is reported under `anomalies`, which carries its gate and start, and is excluded from `gates`. Anomalies are account-level observations and may name an item that also sits in an item section.
4. **Unknown is unknown.** A hold or label wait the daemon did not see begin is `"unknown"` for its start and age, never "now". Open managed items whose labels are not read yet are counted in `unclassified_items`, not placed, and `nothing_needs_you` is true only with nothing to report and no unclassified item. The unclassified count is account-wide even in a scoped view: an item with unread labels cannot be matched against a scope, and counting it is the fail-safe choice. An empty view is explicit (`nothing_needs_you`, empty lists, never `null`).
5. **Bounds.** Each section is cut at 10 entries (`situationSectionMax`) before rendering, in rank order (gates: longest held first), with an exact `omitted` count; account sections are bounded the same way. Ten is the order of the five-entry snapshot that motivated the view, with headroom. The digest body is a readable rendering of the bounded view; `meta` carries the counts as strings.
6. **Read path.** The builder uses `Scan` (never nested with `Peek`), the health mirror and `anom.mu`; it never reads consumer-owned memory (`ce.memo`, `pollEp`, `partEp`), so the stall state is re-derived from the health verdicts exactly as `pipelineCatchUpEvents` does. The files are named `localapi_situation.go` and `channel_situation.go` so they fall inside the existing GitHub-free scan globs (`TestSituationSourcesAreInsideTheGitHubFreeScans` pins that); the scans are not weakened and a nil-client / counting-fetcher test shows zero GitHub calls.
7. **The tool.** `fabrik_situation` is served by `localapi.SituationBackend`, an optional interface beside `Streamer` / `Actor` (the three-method `Backend` is unchanged); `hello` advertises `situation` only when set and an older daemon answers `unknown_method`, which the shim reports as "this daemon predates fabrik_situation" (ADR 2168 version-skew rule). It is annotated read-only: its optional `push` queues the view into the caller's own channel and writes nothing to GitHub or the board; that is a deliberate trade against a permission prompt on every status check. The tool is account-wide and unscoped.
8. **The event.** `situation`, subscribable, `Immediate` (never folded into a `digest_seconds` batch) and `AccountWide` (`Matches` ignores repo / issue / milestone scope; the builder narrows by `Subscription.ScopeMatches` over the union of the subscriber's subscriptions that take it, while merge-train, health and pipeline sections stay whole-account). The name does not collide with the synthetic `digest` type.
9. **Who takes it.** `Subscription.TakesSituation()`: an explicit `events` list naming it, or the semantic default (`EventsDefault`). A grandfathered subscription and an explicit list without it do not, and keep the per-item catch-up; they move to the digest by naming `situation`. This keeps a running overseer's shape stable (ADR 2169's grandfathering rule).
10. **Cadence.** `Subscription.SituationSeconds` (`situation_seconds`), default 0 = off, bounds 60 s - 24 h (`MinSituation` / `MaxSituation`), refused when the subscription does not take `situation`. It is separate from `digest_seconds` (batching of ordinary events). The floor is two of the deriver's 30 s ticks: a cadence the tick could not honour is refused, not silently rounded. A subscriber with several subscriptions uses the shortest cadence. Evaluation is `publishSituations` from `onTick`, for attached subscribers only (a detached one is caught up on attach, as for reminders), on `e.now()`.
11. **Dedup.** Per subscriber, by a fingerprint of the view, kept in the hub and persisted in `dedup.json`. The hub's existing `DedupKey` mechanism is global and permanent and cannot resend "A, then B, then A", so `Hub.PublishSituation` is a separate path (like `PublishReminders`). The fingerprint (`situationFingerprint`) is an explicit allowlist projection, so a field added to the view later cannot leak into dedup by accident: identity, title, link, state, code, rank, options, gate name / reason / start, verdicts, resume method, pending kind and blockers, partition members / phase / idle reason, slots, train queued, the overdue verdict and back-off reason, anomaly kind / subject / start, truncation counts. Excluded: the `as_of` envelope, every age, duration or `*_seconds` figure, whether a poll is running right now, the poll step and the classifier's prose reason. A send replaces any `situation` still queued for that subscriber, so one that is away holds at most one, the newest. Persisting the fingerprint is what stops the first scheduled digest repeating the catch-up that #2169 queues after every restart. Forgotten when the last subscription goes.
12. **On demand.** `fabrik_situation` with `push: true` queues the digest to the caller's own subscriber (the launch `--subscriber` name only; there is no per-call override, as for the action tools, so a call cannot queue into another subscriber's channel or overwrite its dedup memory), deduplicated like any digest; `force: true` sends it anyway. Without a subscriber, or with no subscription that takes `situation`, the view is still returned and `push_note` says nothing was pushed.
13. **Catch-up is the digest.** For each selected subscription that takes `situation`, `catchUp`, `catchUpAll` and `catchUpLate` push a forced digest (`trigger=catch_up`, `catch_up=true`, `source=catch_up`), identical in content to the requested digest. They also record its fingerprint and, for subscriptions with `remind_after`, restart the decision reminder clock (`Hub.RestartReminders`), which the per-item catch-up did as a side effect. The per-item `catchUpEvents` snapshot goes only to subscriptions that do not take `situation` (`Hub.CatchUpWhere`). Who receives a catch-up, when (the readiness gate), and the downtime deltas are unchanged.
14. **`cache-divergence` is active for the window.** It is a point event with no state, so `anomalyState` gains a bounded (50) ring of divergences inside `cacheDivergenceWindow`, recorded where the event is built. This is a memory of an existing signal, not a new one.
15. **Seams.** `SetSituationDedupDisabledForTest` (every digest is sent: the sim's non-vacuity check) and `SetSituationMinForTest`.

## Consequences

- An overseer answers "what needs me?" from one call or one push. A busy board reads as ten entries per section plus counts.
- A default-family subscriber's catch-up changes shape: one `situation` event instead of N per-item events. Subscribers that named their events, or predate the semantic default, are unchanged. The #2169 tests that asserted per-item catch-up for a default subscription were moved to a subscription that names its events.
- The digest's `Content` includes ages, so two digests with the same fingerprint differ in text; only a change of substance is sent, and the text shown is accurate at send time.
- Cadence granularity is the 30 s tick, and a quiet system sends nothing after the first digest.
- Known gaps: a hold or episode the daemon did not see begin is unknown; an `item-wedged` item is under `anomalies`, not `gates`; the view is account-wide for the tool but scoped for a subscriber's digest, so the two are equal only for an unscoped subscription.

# ADR 2052: The merge train tells CI infrastructure failures from real ones

## Status

Accepted (#2052). Amends ADR-1822 point 4 (the workflow-run read is now made, softly). Softens ADR-1153's Strict non-required-failure policy by exactly one failed-job re-run.

## Context

Two failures of the CI *provider* were read as the members' fault or as "still pending":

1. **A run that never started.** A workflow run that fails before creating any job (`startup_failure`) leaves zero check runs on the trial SHA. `pollTrainCI` read zero check runs as "not reported yet" and polled to `CIBackstopTimeout` (4h), then returned `TrainCIPending`, discarded the trial and rebuilt the same batch (shadoworg/liminis-models, trial PR #1651, run 37244372903, a worker slot held for 2h). Worse, with no required checks `mergeable_state` is `clean`, required contexts are trivially satisfied and the suite is `completed`, so the zero-check shortcut returned **green** and landed a batch whose CI never ran. The stage `wait_for_ci` gate has the same blind spot on an item's own PR.
2. **A single flaky test.** One red check started a bisection of full CI cycles and could end by blaming an unrelated member (verveguy/concept-maps, 2026-10-03: two different flakes pinned #1417 as the "poisoner").

GitHub refuses to re-run a run that never started (403 "cannot be retried"), but a `pull_request` close/reopen fires a fresh run. Reading workflow runs needs `actions: read`; `rerun-failed-jobs` needs `actions: write`. ADR-1822 point 4 rejected the workflow-run read for exactly that reason (the App is not granted it; making it required would trip ADR-1713's fail-hard startup grant check for every existing installation).

## Decision

1. **Detect from the workflow runs, only when there are zero check runs.** `FetchWorkflowRuns` (`GET /actions/runs?head_sha=`, plus one `jobs?per_page=1` per completed run for the job count) is called solely on the zero-check-run path, so the extra API cost is bounded. A run is a startup failure when it is `completed` and concluded `startup_failure`, or has zero jobs and concluded `failure` (an allow-list: a zero-job `action_required` run is waiting for a human's approval, and `skipped`/`stale`/`success` are not provider failures). The check runs *before* the zero-check green shortcut, closing the false-green path.
2. **A zero-job `cancelled` run is not a startup failure** (nor is any other non-`failure` zero-job completion, see point 1). A concurrency-group supersession (#2033) cancels a run before any job exists; treating it as infrastructure would close and reopen a PR over a deliberate cancel. A genuine startup failure that reports `cancelled` falls through to today's behaviour.
3. **Retrigger by close/reopen of the trial PR, bounded.** `maxCIRetriggers` = 2. `retriggerPR` reopens immediately after closing (retried 3 times; failure to reopen abandons). The retrigger state (`startupWatch`) is local to one `pollTrainCI` call and counts only runs **absent from the baseline snapshotted at the last retrigger** (R3a): the dead run stays on the head SHA and would otherwise burn the budget in one loop. If no new run appears within `ciRetriggerNewRunDwell` (5m — covers a workflow whose `types:` omits `reopened`) the trial is abandoned.
4. **`TrainCIInfra`, a distinct result — not `TrainCIPending` plus a flag.** `TrainCIPending` is charged by `assembleAndValidate` and read as a green half by `bisect`. A new value, placed last so existing iota values do not shift, forces every call site to decide explicitly: no `recordTrial`, no bisection (a sub-trial returning it aborts the whole episode — nothing is ejected because ejection follows bisection), no ejection, pause, `MaxMergeTrainEjections` count or "batch dissolved" comment. Members stay Queued.
5. **Abandon cooldown, not a hard cross-trial bound.** After an abandon, `dispatchMergeTrainWorker` holds the `(repo, base)` partition off for `trainInfraAbandonCooldown` (5m, in memory). Nothing is charged, so the runaway guard cannot bound a permanently broken workflow; the cooldown limits it to one trial per cooldown. **Residual:** a batch containing a member that permanently breaks the workflow file re-forms indefinitely at that cadence. A cross-trial pause (after N consecutive abandons) is a possible follow-up.
6. **One failed-job re-run before red (R5).** The first confirmed check-run failure takes workflow-run IDs from each failed check's `DetailsURL` and calls `RerunFailedJobs` once per distinct run, then keeps polling. A failed check with no Actions run behind it, or an erroring re-run request, is red at once (today's behaviour). The second failure counts only if a failing latest-per-name run has an ID absent from the first failure — the stale failure is still visible for a poll or two after the re-run is accepted and must not be counted as the second — with `trainRerunSettleDwell` (2m) bounding a re-run that never materialises — once it elapses, one of the re-run workflow runs (matched by run ID) still `queued` or `in_progress` (`rerunInFlight`) keeps the trial waiting — a re-run queued behind runner capacity is not a second failure — for at most `trainRerunMaxWait` (30m) past the dwell. Unrelated workflows and `waiting`/`pending` runs never delay the verdict. State is local to one `pollTrainCI` call, so each bisection sub-trial gets its own re-run. `RequiredContextsFailed` and `dirty` stay immediately red (no workflow run to re-run). `ciSuiteHold` keeps the gate unsettled while the re-run runs. Trade-off: a genuinely red trial is detected one CI cycle later.
7. **`actions` is optional, with a soft degrade.** `RequiredGitHubAppPermissions`, `VerifyGrants` and the startup grant check are **unchanged** (pinned by a test). `OptionalGitHubAppPermissions()` (`actions: write`) is added to a *new* App's manifest by `fabrik init --github-app` only. A refused call — `gh.ErrForbidden` (new sentinel for a non-rate-limit 403; rate limiting is untouched) or `ErrNotFound` — logs once per process and the engine behaves exactly as before. Documented as optional-but-recommended.
8. **Interface on `GitHubClient`, per the spec.** `FetchWorkflowRuns` and `RerunFailedJobs` are on the interface (and the mock, `simgh.Sim`/`Instrumented`, `cmd` doubles) rather than an optional-capability assertion.
9. **Ownership of the closed window (R3).** Close/reopen runs only inside the owning worker's polling loop. `reconstructTrainState`'s stale-PR sweep is reached only through `prepareTrainWorker`, after the `mergeTrainInFlight` `LoadOrStore`; a second dispatch returns first. `escalateClosedUnmergedTrial` is reachable only from `landMergeTrainBatch`, after green. Both are pinned by tests (including an AST check that `pollTrainCI` calls neither and that only `pollTrainCI` and `ciStartupCheck` call `retriggerPR`). **Crash inside the window:** a closed-unmerged trial PR with no worker is not open and not merged, so the sweep does not close, reopen, land or escalate it; orphaned branches are cleaned silently and a fresh train forms (pinned by `TestMergeTrainInfra_SweepOnAClosedTrialPRWithNoWorker`).
10. **R6: the stage gate has the same blind spot, and gets the same handling.** `clean` + zero check runs cleared the gate with CI never run (rule 9 / "no CI configured"); `blocked` + zero runs waited for the backstop. `settlePRMergeStateForCIGate` (called by `handleMergeAndCIGates` only — the auto-merge convergence path keeps the plain form, GitHub owns that merge) applies the same `startupWatch`, keyed per PR and head SHA in memory (a restart may grant one extra retrigger; a push resets it), for `wait_for_ci` stages only. A retrigger returns `PRMergeUnsettled` with `MergeableState` omitted; an abandon sets `PRSettleResult.StartupFailure`, which routes ahead of the other gates to `pauseForCIStartupFailure`, a pause naming the startup-failed run; the pause drops the PR's retrigger state so a human's resume (with the head SHA unchanged) gets a fresh retrigger budget instead of an immediate re-pause. Label-based counters were rejected: durable churn on user-visible state for a rare, self-healing case.
11. **Accepted trade-off on an item's own PR.** Unlike the train there is no in-flight marker, so the closed window cannot be made exclusive. Mitigated by closing and reopening back to back with a retried reopen, and by treating a PR that reads `closed` within `ciRetriggerGrace` (2m) of an engine retrigger as `PRMergeUnsettled` rather than `PRMergeTerminal` (which would pause the item as "closed without merging" if the cache lagged the reopen). Close/reopen also re-triggers review bots and `closed`-reacting workflows; the bound of 2 limits it.

## Consequences

- A trial whose CI never started is retriggered and, if that fails, abandoned in minutes; it no longer polls to 4h, and no longer lands on a `clean` zero-check state.
- A single flake no longer triggers bisection or an ejection.
- Without the `actions` permission nothing changes except one log line.
- **Live coverage gap.** A `startup_failure` cannot be induced on demand against the e2e bed, so there is no live twin and `tests/e2e/registry/registry.json` (keyed by live test) is unchanged. The sim twin (`tests/sim/mergetrain_ci_infra_test.go`) and unit tests carry the proof; the model's limits (no real `types:` filtering, reopen is scripted not derived, runs and check runs not linked) are recorded in `tests/sim/simgh/FIDELITY.md`. The wire-contract fixtures for the three new REST endpoints are **transcribed from GitHub's documented response shapes, not recorded live** (the `provenance.source_repo` field says so), because the bed credential may lack `actions`.
- Existing red-path expectations get one extra CI cycle.
- Reopen side effects, the permanent-breakage livelock residual (decision 5), and the restart-grants-one-extra-retrigger behaviour are accepted.

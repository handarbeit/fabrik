# ADR 2425: Probe the Funnel name's public DNS before reporting the tailscale transport healthy

## Status

Superseded by ADR 2452 (the probe, its states, panel entry and replay hold were removed; route liveness from the delivery log replaced them). Originally: amends ADR 2143 (the fixed 90 s replay grace and the `funnel` health values) and builds on ADR 2142 and ADR 2144.

## Context

With `event_source: tailscale` (ADR 2143) a new node's Funnel hostname does not resolve publicly for several minutes (about 15 in the #2143 live check). Meanwhile GitHub's deliveries fail with `502 failed to connect to host`, yet `fabrik_health.webhook.transports` reports `listening` / `funnel: ok`, because `ok` is tsnet's local capability check, not reachability. The delivery replay (ADR 2144) runs at start (after a fixed 90 s) and on the reconnect signal, both inside the window, so the deliveries that failed in it are not recovered, and the early passes would spend the per-delivery request budget (`replayMaxRequestsPerGUID`) on requests bound to fail. Polling and reconcile keep the board current, so the defects are a wrong health report and unrecovered deliveries.

Two traps constrain any check. The local resolver of a host on the tailnet answers with the tailnet IP (MagicDNS), which says nothing about the public name. A public recursive resolver caches negative answers, so asking one can delay its own success and keep a published name looking missing.

## Decisions

1. **Ask the authoritative servers only.** The probe walks the delegation itself, from the IANA root hints, over UDP with TCP on truncation, with recursion desired off, following referrals (NS records and their glue; a glueless name server is resolved by a bounded nested walk). It never uses `net.Lookup*`, `net.Resolver`, the system resolver or a recursive resolver address; a source scan test and a fake-tree test that checks RD=0 and the destination of every query pin this. Rejected: a hard-coded `ts.net` name-server set (goes stale, and which zone holds the per-tailnet records is unverified), a custom `net.Resolver` (sends RD=1, hides the AA bit, applies the host's search list), a public resolver (the negative caching above). The walk works for either zone layout, `ts.net` itself or a per-tailnet delegation.
2. **Trust only authoritative replies.** An answer is accepted from a server that sets the AA bit; a reply with RA and no AA is refused (observed once: a query sent to a named authoritative server came back recursive-looking, which is how an intercepting network would answer for a name that is not yet published); a referral must lead strictly toward the name; a CNAME may not leave the zone. A name counts as resolved only if it has an A or AAAA record outside `100.64.0.0/10` and `fd7a:115c:a1e0::/48` (IPv4-mapped addresses are unmapped first). NODATA and NXDOMAIN are "unresolved", not errors; a failure to find out is an error.
3. **A dependency on `golang.org/x/net/dns/dnsmessage`.** The standard library cannot send a non-recursive query or expose the AA bit. The module is already in the build graph through tailscale (`// indirect`); using it directly only drops the marker (no new module, no `go.sum` change). This is the one exception to "minimise dependencies" this ADR takes.
4. **The probe state is its own dimension.** `appWebhookTransport.dnsProbe` (off for `direct`, pending, resolved, unknown) is composed with the tsnet inputs in `state()` and `HealthRow()`; it is not a value of `networkCondition.funnel`, which every tsnet state change overwrites. Pending is set before `Start`, so the transport never reports healthy first, makes `state()` unhealthy (so `webhook.mode` follows with no change to the aggregate) and the row `listening (not publicly resolvable)`. `funnel` precedence: tsnet `unavailable` (the more actionable) > `pending-dns` > `unknown` (the probe failed) > tsnet's own value, so pending clears to tsnet's value, not a hard-coded `ok`.
5. **Unknown does not degrade serving.** A probe that fails (no network, nameservers unreachable) reports `funnel: "unknown"` and leaves the transport healthy and listening, because the failure says nothing about whether webhooks arrive and the probe must never be a new way for the daemon to fail. Only a definite "not resolved" is unhealthy.
6. **Backoff and grace are constants.** 10 s, 20 s, 40 s, then 60 s until the name resolves, then never again for the life of the node; a failure or pending result is logged at most once per backoff level. The panel entry `tailscale_funnel_dns` (subject: the node's reported DNS name) appears after 10 minutes unresolved, measured with `e.now()` from the first probe, and clears on resolution. It names the likely causes: propagation, Funnel not granted to the node's tag, HTTPS certificates disabled. The name is the node's reported one (tsnet suffixes a taken hostname), taken from `Up` or, if absent there, from the first watch state; a changed name before resolution restarts the loop with the once-flags kept.
7. **One reconnect call.** On the first resolution after the name was seen pending or the probe failed, the transport's reconnect handler is called once (`requestReconcile` plus a replay trigger); a name that resolves at the first definite answer never calls it, and nothing calls it twice per node lifetime. A spurious catch-up is harmless; a missed one loses deliveries, so error-then-resolved counts as the transition.
8. **The startup replay pass is held back while pending, at the call site.** `startTailnetReplay` replaces `startDeliveryReplayAfter` for this transport: after the 90 s grace it triggers the pass unless the probe is still pending, in which case the probe records that it was held back and its resolution triggers the pass. `delivery_replay.go` is untouched. Rejected: resetting the replayer's `requested` map on the R4 trigger (changes replay logic) and leaving the early pass (it would spend the request budget in the window, so the pass that matters would skip those deliveries). An unknown probe never holds the pass back, and one held back for a probe that then turns unknown runs at once, so a broken DNS path cannot disable the startup replay.
9. **Scope.** `event_source: direct` is not probed (its public name belongs to an external proxy). Probe state is in memory; a restart is a new node lifetime and probes again, normally resolving at the first probe.

## Consequences

- `fabrik_health` is honest during propagation, the operator is told when it takes too long, and deliveries missed in the window are recovered as soon as the name resolves.
- Resolved DNS does not prove that Funnel ingress routes to the node; the replayer's follow-up pass and the periodic reconcile cover that residue.
- A network that blocks outbound port 53 gives a permanent `unknown`: honest, and the panel entry appears after the grace, but noisy.
- The 90 s grace of ADR 2143 stays as a floor for the pass, but is no longer the only gate.
- Live behaviour (the propagation time, which zone holds the record) is verified once on a test bed with a new node name (AC7) and recorded in the PR; it is not exercised by CI.

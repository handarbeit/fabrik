# ADR 2366: Pruefer loads the review plugins a repo names, from the repo's standard Claude Code plugin declarations, read at the base ref — operator-gated, default off

## Status

Accepted. Supersedes the "Deferred to #2366" section and decision 2 ("No code from the reviewed repo is loaded", and its static ban on any tree or blob reader) of ADR 2307. The rest of ADR 2307 (one base SHA per review, the plugin order and first-wins rule, the `Skill(<ref>)` grant, the scrubbed environment, the visible fallback and its sanitised notice), ADR 2306, ADR 1642, ADR 1446 and ADR 1952 stands. The first, bespoke implementation (`.pruefer/plugins/<name>/`) stays on branch `pruefer/repo-plugins-fetch` as a reference for the tree reader, the caps and the path validation.

## Context

ADR 2307 let an operator load review plugins and let a repo choose which of their skills reviews its PRs, but deliberately loaded no code from the reviewed repo. A bespoke `.pruefer/plugins/` tree was dropped because it invents a Pruefer-only plugin format, has to be copied into every repo, and is separate from the plugin the repo's developers already use with Claude Code. A repo should be able to point Pruefer at a normal Claude Code plugin it already declares.

This is the first time Pruefer runs code supplied by the reviewed repo on the Pruefer host. A plugin's hooks, MCP servers and scripts run as the daemon's operating-system user, outside the reviewer's path-scoped tool rules (ADR 2307 residual risk). Content on the base ref has been merged by the repo's maintainers, but it is still content from the reviewed repo. The PR head stays untrusted (ADR 1446 C1): the clone is the head, and the reviewer runs with `--setting-sources ""`, so Claude Code never loads project settings itself.

## Decision

1. **Declarations are the standard Claude Code ones, read at the base SHA.** Pruefer reads `.claude-plugin/marketplace.json` (the repo's own marketplace) and `.claude/settings.json` (`extraKnownMarketplaces`) through the Contents API at the review's resolved base SHA — the one SHA ADR 2307 decision 1 pins every base-ref read to — never from the clone. `enabledPlugins` is not read: naming a plugin is the opt-in, so a plugin the repo merely enables for its developers is never loaded. Each file is capped (256 KiB, UTF-8). A missing, oversized or malformed file yields no plugins from it, never a failed review.
2. **Three opt-ins, in a fixed order.** (a) The operator's `repo_plugins` (default **off**; flag `--repo-plugins`, `PRUEFER_REPO_PLUGINS`, YAML; live-reloadable; an unparseable env value fails closed to off). When off nothing below runs: no read, no fetch, no `--plugin-dir`. (b) The repo names each plugin it wants, as `<plugin>@<marketplace>`, in a `plugins:` list in its base-ref `.pruefer/config.yaml`; every other plugin it declares is ignored. `plugins` is parsed by the same strict repo-config struct as the other repo keys, so no operator-only key becomes readable from a repo file; it is a different key from the operator's `plugins:` (local directories). (c) The base must have resolved to a SHA — plugin code never falls back to a branch name the way config text does — and the PR's base must be the repository's default branch (`PRDetails.DefaultBranch`, from `base.repo.default_branch` in the REST payload at no extra call; an unknown default fails closed). A stacked PR's base is another contributor's branch that no maintainer gate has seen. `evaluateRepoPluginGate` is the only producer of an open `repoPluginGate`, and `fetchRepoPlugins` refuses a closed one.
3. **`repo_review_skill: false` does not stop plugins loading.** It is the operator's veto on a repo choosing a skill; `repo_plugins: off` is the switch for loading repo code. A plugin that loads but is not selected is simply unused — but its hooks and MCP servers still start when the CLI is given `--plugin-dir`, so an operator who does not want repo code to run turns `repo_plugins` off.
4. **Sources.** Resolved through a marketplace the repo declares at the base SHA: its own in-repo `.claude-plugin/marketplace.json`, or an `extraKnownMarketplaces` entry. A plugin entry's `source` is a relative path inside its marketplace's repository (`./x`, `.` for the root, or a bare name under `metadata.pluginRoot`; no `..`), or a `github` / `git-subdir` object (or a `url` object) naming a repository on github.com. Everything else — `npm`, `archive`, `command`, another host, a `path` or `sparsePaths` on a marketplace, `directory`, `file`, `url`, `settings` marketplaces — is refused and reported, never best effort; the marketplace format belongs to Claude Code and drifts, so "refuse and say why" is the only safe reading of anything new. Entry fields that would substitute for a plugin's own manifest are not applied: the directory must be loadable by `--plugin-dir`, so it needs `.claude-plugin/plugin.json`, and that manifest's `name` must equal the marketplace entry name (Claude Code's documented rule), which keeps `plugins:` (entry name) and `review_skill:` (manifest name) consistent. An `extraKnownMarketplaces` entry that names the reviewed repository itself is the in-repo marketplace at the base SHA; its `ref` is ignored.
5. **External repositories are allowlisted, per repository, and pinned to a fixed commit.** Any repository other than the reviewed one is read only if it is on the operator's `repo_plugin_marketplaces` allowlist (default empty; exact `owner/repo` or `owner/*`, case-insensitive; flag/env/YAML, live). The match is on the **resolved repository**, never on a marketplace name the reviewed repo chose (FR-011), so a repo gains nothing by naming its marketplace like an allowlisted one. The allowlist is not a delegation: a plugin entry inside an allowlisted marketplace that points at a third repository needs that repository allowlisted too, and the same for the marketplace's own repository. This tightens the issue's "its marketplace is allowlisted" wording and stays fail-closed.
   The source must resolve to a fixed commit: a full 40-hex `sha` is used as is (it wins over `ref`, as in Claude Code); a 40-hex `ref` is accepted as a pin; any other `ref` is resolved with `git/ref/heads|tags` — a tag is peeled (annotated tags through their tag objects) to its commit and that SHA is recorded; a branch, a name that is both a branch and a tag, a name that does not resolve, and no ref at all (which would follow the default branch) are refused. The documented `extraKnownMarketplaces` `github`/`git` sources have no `sha` field, so an external *marketplace* is pinned by a tag or a 40-hex `ref`; its manifest is read at that commit. Everything external goes through the API with the review's own installation token; a repository that token cannot read is refused and reported, never retried, never with another credential.
6. **No reachability check on a pinned SHA.** The Git API serves a commit by SHA from anywhere in a repository's fork network, so a pinned SHA may never have been on a branch or tag of the allowlisted repository. Pruefer does not verify ancestry: the SHA is named by the reviewed repo's maintainers (it is in base-ref content), and the allowlist is trust in a repository identity, which that fork network sits under. The residual risk is stated, not hidden (below).
7. **Caps and path validation, from tree metadata, before any blob.** A plugin directory is found with one non-recursive tree read per path segment (`FetchSubtreeSHA`), then listed once recursively (`FetchTreeBySHA`). From the listing alone `validateRepoPluginTree` refuses the whole plugin for: a truncated listing; a symlink (`120000`), a gitlink (`160000`) or any mode other than `100644`/`100755`; a path that is empty, absolute, has a `.`, `..` or empty segment, a backslash or control character, a `.git` segment, or is over the length caps; two paths that differ only in case; a file over 1 MiB; more than 500 files or 4 MiB in one plugin; and, across the plugins of one review, more than 1000 files or 8 MiB. The constants are fixed and documented, not settings. Each rule is separately neutralisable in tests (`disableRepoPluginRuleForTest`) with a fixture that is refused with the rule and accepted without it. A blob larger than the cap is refused before decoding and its decoded length must match the reported size. A plugin whose root is the repository root (`.`, or a `github` source with no `path`) lists the whole repository and will often truncate or exceed the caps; that is refused, fail-closed, by design.
8. **Cache.** A process-wide, mutex-guarded LRU bounded by **bytes** (32 MiB), because one plugin may be 4 MiB and an entry-count bound would not bound memory. Keyed by `(repository, tree SHA)` and, for an external source, also `(repository, commit SHA, path)`: a tree SHA is content-addressed, so an unchanged plugin has the same one at every commit and a hit skips the recursive listing and every blob read (an in-repo plugin still pays the cheap per-segment descent to learn its tree SHA; a cached external plugin costs no request at all). The repository is part of the key so a SHA present in two repositories can never carry a trust decision between them. Only fully read, validated trees are stored; a refusal or failed read is never cached. In memory only.
9. **Loading.** Fetched trees are written under the per-review root in `repo/NN/` directories — `NN` an index, never repo-controlled text — with exclusive file creation, a containment check and the executable bit preserved (hook and MCP scripts must run), and passed with `--plugin-dir` after the embedded and operator plugins. Embedded-name reservation, first-wins (a repo plugin can never shadow an operator plugin), the scoped `Skill(<ref>)` grant, the scrubbed environment and removal of the root on every exit are unchanged from ADR 2307. The `review_skill` resolver and the visible fallback are unchanged; a skipped plugin shows up as "did not resolve" plus its reason in the set's notes, which the existing fallback notice already carries (sanitised, in a code span, with no local path — a plugin id is rendered as "plugin in marketplace m" because `@` is not allowed in a posted reason).
10. **Failures and memoisation (ADR 1952).** A deterministic refusal (cap, path rule, allowlist, unpinned source, an unreadable external repository, unsupported kind) is a verdict and stays conclusive. A transport, 5xx or rate-limit failure while reading a declaration, resolving a ref, listing a tree or reading a blob marks the outcome degraded, so it is not memoised. As before, a changed plugin declaration does not re-review a head that was already reviewed, and a tag that moves changes the bytes without re-review; the resolved SHA is logged and keys the cache, so each review is auditable.
11. **The record (R8).** Every review with the capability on logs each loaded repo plugin with its origin (`in-repo`/`external`), repository, commit, path, tree SHA and whether it came from the cache, and each skipped plugin with its reason and log-only detail. The per-plugin `review plugin:` line carries the same provenance. A closed gate that is worth saying (not the default-off) logs why.
12. **Reachability is proved by a static guard.** `TestRepoPluginReadersAreOnlyReachableBehindTheGate` replaces ADR 2307's blanket ban: the tree, blob, subtree and ref readers are called from `repoplugin_fetch.go` only; `fetchRepoPlugins` has one call site, in `ReviewPR`, guarded by the value `evaluateRepoPluginGate` returned; a non-zero `repoPluginGate` is built in that function only; the files that decide, fetch and validate cannot import `os`, `os/exec` or `path/filepath` (so cannot read the clone); and the tree/blob endpoints appear in one file of the `github` package. Behavioural tests with a counting fake prove that no read happens with the capability off.
13. **Repo plugins get the same author-class policy as operator plugins (ADR 2308).** After a repo plugin is written under the per-review root, `buildPluginSet` passes it through a `repoPluginPolicy` built in `RealClaudeInvoker.Review`: for an outside author (`Grant.StripPluginHooks`) it is loaded from a read-only copy without hooks, MCP servers and tool pre-approvals (`stripOperatorPlugins`); for a trusted author it is used in place unless its `allowed-tools` frontmatter names a tool outside the review grant, in which case it is loaded from a copy without that key (`sanitizeOperatorPreapprovals`). A plugin that cannot be prepared is left out and noted, never loaded unfiltered. The posted `Read-only review` notice names such a plugin as `<name> (repo plugin)`. Base-ref content is written by the repo's maintainers, not the PR author, but the CLI honours `allowed-tools` past the grant and a hook runs over the untrusted head, so exempting repo plugins would let a repo plugin undo the read-only review ADR 2308 promises an outside author.

## Trust model

- **Who can supply plugin code.** Only maintainers of the reviewed repository, through its base ref (a plugin in its own marketplace, or a pinned reference to another repository), and — only for repositories the operator allowlisted — whoever can push a commit to those repositories. A PR author cannot: plugin content is read at the base SHA, so a PR that changes the plugin has no effect on its own review, and a PR that changes `.pruefer/config.yaml` or the marketplace file has no effect until merged.
- **Where it runs.** On the Pruefer host, as the daemon's operating-system user, started by the `claude` CLI (hooks, MCP servers, scripts). The review environment scrub applies — no GitHub token, App key or `.env` value in the environment — but a plugin process is not confined to the clone and can read files that user can read, including the GitHub App private key (`.pruefer/app-private-key.pem`). This is the dominant risk, and it is new: before this change no reviewed-repo content could reach it. The path-scoped tool rules bind the reviewer's own tools, not a hook.
- **How the operator turns it off.** Leave `repo_plugins` at its default (off), or set it to `false` (flag, `PRUEFER_REPO_PLUGINS=false`, YAML) — a live setting, effective for the next review. Narrower levers: leave `repo_plugin_marketplaces` empty (only plugins inside the reviewed repo itself can load); the capability never applies to a PR whose base is not the default branch.
- **What the operator is trusting when it turns it on.** Every maintainer of every repository whose PRs Pruefer reviews to run code as the daemon user, plus the maintainers of each allowlisted repository, at whatever commit a reviewed repo pins. Enable it for repositories whose maintainers you would let run code on the machine.

## Residual risks

- Plugin processes are not sandboxed (ADR 2307's residual risk stands, now with repo-supplied code behind it). A malicious maintainer, or a compromised maintainer account, can run code as the daemon user on the next review of a default-branch PR.
- A pinned SHA may come from an unreviewed fork in an allowlisted repository's network (decision 6). A tag can move between reviews.
- A moved tag, an edited marketplace file or a changed `plugins:` list does not re-review a head already reviewed (ADR 1952).
- A loaded plugin the effective `review_skill` does not select still starts its hooks and MCP servers.
- Live loading of a plugin written to the per-review root with preserved executable bits under `--setting-sources ""` is covered by the existing opt-in `TestLiveProbePlugins` (a locally authored plugin directory); this change adds no new live dependency and the loader is the same `--plugin-dir` path.
- The marketplace schema is third-party and may change; unrecognised shapes are refused and reported rather than guessed at.

## Consequences

- Operators get an explicit, off-by-default switch and an allowlist, with a per-review audit trail of what loaded, from where and at which commit.
- A repo can use the plugin its developers already use, without copying it into a Pruefer-specific layout.
- A review of an unchanged plugin costs no blob reads after the first; an uncached plugin costs one tree read per path segment, one recursive read and one blob read per file (up to 500), bounded by the caps.
- `GitHubReviewer` and `gh.PRDetails` gained members (`ResolveRefKind`, `FetchSubtreeSHA`, `FetchTreeBySHA`, `FetchBlob`; `DefaultBranch`), so every fake grows.

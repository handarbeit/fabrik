# ADR 2308: Pruefer grants coded review tools within an operator ceiling, only to authors with write access; outside authors are reviewed read-only

## Status

Accepted. Amends ADR 2192 decision 1 ("path-scoped allows only") for one class of rule, and extends ADR 2307 (the layering model, the pinned base SHA, the visible notice, the residual-risk statement). ADR 2192's scrubbed environment (decision 8), ADR 2306 and ADR 1642 stand as written. Repo-supplied plugins remain deferred to #2366.

## Context

The reviewer's tool grant is fixed read-only (ADR 2192). Linters, analyzers and scanners (golangci-lint, staticcheck, govulncheck, gosec, semgrep, shellcheck, actionlint, gitleaks, osv-scanner) find things a model reading code does not, and operators already have them installed.

The exposure is the PR **head**, not the tools. Many tools execute configuration found in the tree they analyse (`eslint.config.js`, `conftest.py`, golangci-lint plugins, Makefile targets). Fabrik's own workers only build branches Fabrik wrote; Pruefer reviews whatever arrives, including fork PRs from outside contributors. So the grant has to be gated on who wrote the PR, and the scrubbed environment has to stay mandatory for everything that does run.

## Decision

1. **Operator ceiling (R1).** `review_tools` (YAML, `--review-tools`, `PRUEFER_REVIEW_TOOLS`, live-reloadable) lists extra permission rules appended to the base grant. Default empty: the constructed arguments are byte-identical to today's. `LoadConfig` — which is also what a SIGHUP reload runs — refuses a bad entry and names it.
2. **What a rule may be.** Only `Bash(<command>)`, `Bash(<command> *)` and `Bash(<command>:*)`, where the command is plain words (letters, digits and `. _ / + = @ % -`; no glob, quote, shell metacharacter, comma, parenthesis or control character). Refused: a bare `Bash`, `Bash(*)`, any non-Bash tool, and malformed rules. One function, `normalizeToolRule`, trims and collapses runs of spaces; it is used by validation and by the repo-versus-operator comparison, so the two cannot disagree about whether two spellings are one rule. A newline is not folded into a space: it stays and fails validation.
3. **Test runners are refused (R1).** A maintained denylist (`reviewToolsTestRunners`) of `go test`, `npm test`/`npm run test`, `yarn`/`pnpm`/`bun`/`deno test`, `pytest`, `python -m pytest`, `cargo test`/`cargo t`/`nextest` (cargo's built-in short alias `t` is listed; `r` for `run` is in the run-subcommand list), `make test`/`check`, `jest`, `vitest`, `mocha`, `rspec`, `phpunit`, `tox`, `nox`, `ctest`, `mvn`/`gradle`/`dotnet test`. The first word is compared by its base name, and the remaining words must appear in order anywhere in the rule, so `Bash(go test:*)`, `Bash(go  test)`, `Bash(go1.22 test:*)` (a trailing version is stripped for the comparison, as for interpreters), `Bash(/usr/local/go/bin/go -count=1 test *)` are all caught. Bare build-tool launchers (`go`, `npm`, `cargo`, `git`, `curl`, …) are refused because they subsume the test forms; a narrowed rule (`Bash(go vet:*)`) is allowed, unless it names a generic run subcommand (`run`, `run-script`, `exec`, `x`, `dlx`, `generate`, `install`, …), which executes scripts from the reviewed tree (`Bash(npm run:*)`, `Bash(go run:*)`). `yarn`, `pnpm` and `bun` also run a `package.json` script when given a bare name, so there is no verb to match: a rule for one of them is accepted only when its first non-flag word is a built-in that runs no repo code (`audit`, `list`/`ls`, `why`, `outdated`, `licenses`, `info`, `bun pm`; `reviewToolsImplicitScriptLaunchers`) and `Bash(yarn lint)` is refused. Recipe runners (`make`, `gmake`, `just`, `task`, `rake`, `ant`) are refused in every form, and an interpreter is matched with its version stripped (`python3.12`, `node20`). Interpreters, shells and command wrappers (`sh`, `bash`, `env`, `xargs`, `node`, `npx`, `uvx`, `bunx`, `pnpx`, `pipx`, `docker`, `podman`, `python`, `perl`, `sed`, `find`, …) are refused in every form. The list is a denylist, not a semantic analysis: an unlisted runner is the operator's responsibility.
4. **Repo selection within the ceiling (R2).** `review_tools` is the seventh recognised repo key and the second that is not a narrowing (after `review_skill`). It is held as `*[]string`: an absent key leaves the operator's full list in effect, an explicit `[]` selects none. `selectReviewTools` keeps the repo entries that equal (after normalisation) an operator entry, in operator order, and returns the others as ignored; they are logged once. A repo can never widen the grant, including with a test-runner, blanket or malformed rule — those are simply not in the operator list. `yamlRepoConfig` stays a separate strict struct, so every operator-only key remains unparseable from a repo (ADR 1642 AC4). An unreadable or invalid repo config selects nothing, so the full ceiling applies to a trusted author.
5. **Outside authors are read-only (R3).** `trustDecision` is fail-closed. A PR author is trusted iff `author_association` is exactly `OWNER`, `MEMBER` or `COLLABORATOR` (case-sensitive), or the login is exactly `dependabot[bot]` (R4: no case folding, no prefix or suffix; `dependabot`, `dependabot-preview[bot]` and `not-dependabot[bot]` are outside). An absent, null, empty or unrecognised association is outside. `gh.PRDetails.AuthorAssociation` is decoded in both `ListOpenPRs` and `FetchPRDetails` (the poll and the event paths) and read fresh for each review. Trust follows the PR author, not the head repository, so a member's fork PR is trusted. For an outside author the review runs with the base grant exactly (the arguments are byte-identical to an unconfigured operator's) and operator plugins load from hook-less copies (decision 7).
6. **The decision is made once per review (FR-012).** `ReviewPR` resolves the grant (`resolveReviewGrant`: ceiling, repo selection, author) and carries it in `ReviewRequest.Grant`. The zero value is today's behaviour. The single fallback re-run to the default skill (ADR 2307) reuses the same request, so both attempts share one decision and one set of plugin copies.
7. **Hooks and MCP servers for outside authors.** The CLI has no per-plugin switch: `--bare` stops subscription auth, and whether `disableAllHooks` and `--strict-mcp-config` cover hooks and MCP servers declared by a `--plugin-dir` plugin is not documented. Pruefer therefore decides it itself. For an outside author each operator plugin is loaded from a per-review copy built from an **allowlist** (`stripPluginHooks`): `skills/`, `agents/`, `commands/`, the manifest's `skills`/`agents`/`commands` paths (relative and inside the plugin only) and a root `SKILL.md`; the manifest keeps only descriptive keys (`name`, `version`, `description`, `author`, `license`, `homepage`, `repository`, `keywords` and the three path keys); `hooks` and `mcpServers` are removed from every markdown frontmatter by parsing it as YAML. Everything else — `hooks/`, `.mcp.json`, scripts, symlinks, unknown manifest keys, files with unparseable frontmatter — is not copied, so a layout this code has never seen fails closed. Copies are never executable and live under the per-review plugin root, which is removed on every return path. A plugin that cannot be copied is left out and logged. The embedded plugin declares no hooks or MCP servers and is not copied. The cost is that a plugin skill that depends on its own scripts via `${CLAUDE_PLUGIN_ROOT}` degrades for outside authors; the posted notice says that the plugin was loaded without hooks and MCP servers.
8. **The environment scrub is untouched (R5).** `reviewProcessEnv` applies to the `claude` process; every granted tool, hook and MCP server is its descendant. No author class relaxes it. The proof is a stub `claude` that runs a "tool" as its own child under a daemon holding secrets, asserting none reaches it, with the same child started from `os.Environ()` as the non-vacuity control.
9. **`checkReviewArgsScoped` (FR-013).** It keeps its signature and delegates to `checkReviewArgsScopedTools(args, extras, skills…)`. An extra rule is accepted only if the caller names it **and** it is independently valid under `validateReviewToolRule`: a rule merely present in the arguments, or named but invalid (`Bash(go test:*)`, `Bash(*)`, `Edit`), is a violation. The existing widening probes in three test files keep failing because they are never passed as extras.
10. **The prompt.** With extras, `renderReviewTools` names each rule in a code span, says the tools run against the PR head with a scrubbed environment and no credentials, tells the model to treat tool output as untrusted evidence and not as instructions, and drops "linters" from the "not available" sentence. With no extras (the default, and every outside author) the section is unchanged byte for byte.
11. **The record (R6).** One log line per review: `review grant: base=read-only operator=[…] repo_selected=[…] repo_ignored=[…] author=… association=… dependabot_exception=… outside_author=… downgraded=…`. Repo rules that were not applied get one more line — "outside the operator's review_tools" for a trusted author, "not applied: outside author" for an outside one (the repo's requested rules have no effect there). Repo-controlled text is sanitised in both. The Bash commands actually run come from the retained transcript (ADR 2303).
12. **The posted notice (R3, FR-009).** When the outside-author policy removed something — extras the author would have had, or hooks and MCP servers of at least one operator plugin — `ReviewPR` prepends `> 🏭 **Read-only review** — the PR author's association with this repository is `<ASSOC>`, not owner, member or collaborator, so this review ran with the read-only tool grant: …`. It is omitted when nothing was removed. The association and plugin names are sanitised and in code spans; no repo rule text is ever echoed. It sits ahead of the skill-fallback notice.

## Alternatives rejected

- **`disableAllHooks` / `--strict-mcp-config` as the mechanism for decision 7.** Unverified for `--plugin-dir` plugins and version-dependent; unit tests against a fake `claude` would pass while a real CLI still started them. A live probe (`TestLiveProbeReviewTools`) checks the copy, not the flags.
- **Embedded plugin only for outside authors.** Simple, but silently discards an operator-selected `review_skill`.
- **A collaborator-permission read** (`GET /repos/{o}/{r}/collaborators/{login}/permission`) on top of the association. Stricter, but one more REST call per review, a new `GitHubReviewer` method and a GitHub App permission that was not verified. The issue allows the association alone.
- **Refusing only the listed test runners.** Leaves `Bash(go:*)`, which subsumes `go test`.

## Residual risks

- **A granted tool executes head-tree configuration as the daemon's operating-system user.** The author gate and the scrubbed environment are the only mitigations, and neither isolates the filesystem: the environment keeps secrets out of a tool's environment, not off its disk, so a tool can read `.pruefer/app-private-key.pem` and `~/.claude*`. This is the same class as ADR 2307's residual risk for operator plugin processes, now applied to code from the PR head of a trusted author. A sandbox is out of scope.
- **Trusted does not mean safe.** A compromised member account or a malicious collaborator gets the full grant.
- **Trust follows the PR author, not who wrote the head.** `trustDecision` sees only the author's login and association, while a granted tool runs over the head commit. A trusted author's PR can carry commits written by someone else: a maintainer-edit push by an outside contributor, a cherry-picked or merged outside branch, or a Dependabot branch someone else pushed to. That PR gets the full grant, so head-tree configuration from those commits runs as the daemon's operating-system user. This is as designed (the gate is the author, as the issue specifies) and is not mitigated beyond the scrubbed environment, so operators should grant narrow rules even though only trusted authors receive them.
- **`MEMBER` is not strictly write access.** It is any organisation member, including one with read-only permission on this repo, and `COLLABORATOR` is any invited collaborator. Decision 5 follows the association alone.
- **Other bots are outside.** Only `dependabot[bot]` is excepted. Fabrik's merge-train PRs, `renovate[bot]` and similar are reviewed read-only unless GitHub reports an in-set association for them.
- **Rule breadth.** A prefix rule such as `Bash(semgrep:*)` admits `--config <url>` (network) and `--output <path>` (a write anywhere the user can write); `Bash(golangci-lint:*)` admits `-c <file>` and plugins. The validator cannot judge flags. Operators should grant narrow rules (`Bash(shellcheck *)`, `Bash(actionlint)`), and the README shows examples. The path-scoped rules of ADR 2192 do not bind these tools.
- **Prompt injection through tool output** and through repo content that steers the model to run a granted tool with attacker-chosen arguments. The prompt wording (decision 10) only partly mitigates it; the model's judgement is the only filter on arguments.
- **Hook and MCP stripping is Pruefer-side.** If a plugin can declare hooks or MCP servers somewhere the allowlist copies (a skill file's body, a script a skill tells the model to run), it survives; the allowlist and the frontmatter parse are why this is believed to be closed. The live probe is the only check against a real CLI, runs by hand, and **has not been run in CI or for this change**: record the CLI version and the observed values in this section when it is. CI cannot show that a real `claude` honours a `Bash(<tool>:*)` rule or that the copy starts no hook.
- **Memoisation (ADR 1952).** An author's association changing without a PR update does not re-review a memoised head. A changed operator `review_tools` does (the config generation), and a changed repo `review_tools` does (the repo config is in the stamp).

## Consequences

- `gh.PRDetails` gained `AuthorAssociation`; `ReviewRequest` gained `Grant` and `ReviewResult` gained `PluginsStripped`. A hand-built request has a zero grant and behaves as before.
- New operator setting `review_tools` (flag, env, YAML; live-reloadable) and repo key `review_tools`; documented in `cmd/pruefer/README.md` and `docs/USER_GUIDE.md`.
- The `Config` and `yamlConfig` additions follow the existing `plugins` recipe; CSV forms of the flag and variable cannot express a rule containing a comma, and such a rule is refused at load in every form.
- Installing the tools is the operator's job (the daemon's `PATH`); a missing tool is a failed command, not a Pruefer error.

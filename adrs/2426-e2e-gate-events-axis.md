# ADR 2426: The live e2e gate plans how events are ingested — an `events` axis (poll | webhook), a per-cell poll cadence, and webhook cells the ledger requires

## Status

Accepted (#2426). Successor to ADR 1975 (the sparse auth × train matrix), which it extends with a third axis. Builds on ADR 1933 (the per-test registry), ADR 1972 (the coverage ledger), ADR 1976 (multi-bed scheduling), ADR 1978 (the poll hold/trigger seam) and ADR 2408 (the bed event source and the per-leg delivery preflight). **Amends ADR 2408 decisions 4 and 8** for gate-planned cells (below). ADR 1454 is unchanged: every live scenario still runs live before a release, and nothing moves to the sim.

## Context

The gate planned legs over two axes, auth (`pat|app`) and train (`off|on`). How the engine ingests GitHub events — poll-only, or with webhooks as the primary wake source — is a third dimension with its own failure modes (ordering, dedupe, echo, wake-ups, replay). The gate could not schedule, require or record it, so a release that changed ingestion could pass without a single scenario having run with webhooks. #2408 gave beds a webhook transport and a delivery preflight; this ADR makes the gate use them as a planned, ledger-required dimension.

A steering comment on this issue raised a cadence problem. #2408 runs a webhook leg's bed at 180 s (`bedevents.WebhookPollSeconds`) so a quick effect can only have come from a delivery. Many scenarios' fixed waits are tuned to a 60 s poll, so running the **whole** suite on a webhook cell at 180 s would produce Inconclusive results and failures unrelated to webhooks, making the full plan an unreliable release gate.

## Decisions

1. **`Cell` has an `Events` dimension, `poll | webhook`** (the zero value is poll). The label of a poll cell stays `auth/train` (`app/on`); a webhook cell's is `auth/train/webhook` (`app/on/webhook`). Poll labels are unchanged, so every ledger record written before this ADR keeps its key (outcome files stay `app-on.jsonl`, archive directories `app-on`); only webhook cells get a third part. The inverse of the file-name mapping (`legFromFile`) and the archive/void directory name (`cellDirName`) understand the three-part form. Webhook cells are App-auth only: `pat/*/webhook` is never planned. The sparse baseline test (`Cell.isBaseline`) also requires `Events == poll`, so `app/on/webhook` is never mistaken for bed A's baseline.

2. **The registry gains a required `events` field** (`sensitive | neutral`, `events_reason` required for `sensitive`, no default), the same shape as `auth`/`train` (ADR 1975). The completeness test requires `events: sensitive` for every test that reaches `bedWebhooksEnabled` or the FR-005 helper `webhookEffectMissing` — including a `HoldPolls` caller that does so to isolate a webhook effect (`ScanBedWebhookCallers`/`CheckBedWebhookCallers`, the same reference-closure scan as the other callers checks). A test that only holds polls for a state window (the merge-train batch-cap test) is not thereby events-sensitive. `skip_ok_legs` patterns are now `<auth>/<train>[/<events>]`: a two-part pattern matches a webhook label on its first two parts, and `*/*/webhook` / `*/*/poll` name the events part, which is how the two webhook-aware tests record their structural self-skips (`TestMergeTrainColdCacheBaseMember` skips on a webhook cell, `TestWebhookChangeSurvivesReconcile` on a poll cell and on PAT). This replaces ADR 2408 decision 8's interim skips that cited #2427.

3. **The sparse plan** is the existing baseline and narrowed cells unchanged, plus one cell, `app/on/webhook`, planned last and running exactly the `events: sensitive` tests minus pairs the registry marks structurally skipped there. **`E2E_MATRIX=full`** is the four poll cells plus `app/on/webhook` and `app/off/webhook`, both running the **whole** suite: a release that changes ingestion must show every scenario still converges with webhooks as the primary wake source (use it for such a release, as for one that changes the auth layer or the landing path). `buildPlanInput` stays the one source for `gate run` and `gate coverage`, so the required set and the plan cannot diverge. Webhook cells are ordered after every poll cell, so a failed webhook preflight leaves the poll coverage already recorded. In a multi-bed run a failed leg stops new cells as before; the webhook pairs then stay uncovered.

4. **Poll cadence is part of the cell** (`Cell.PollSeconds`), set when the plan is built, printed with the plan (`app/on/webhook@60s`), passed to the bed restart for the leg and archived with it (`bed.json`, `phases.json`). **Every planned cell, webhook cells included, runs at 60 s**, so the existing suite's fixed waits hold and an `events: neutral` test behaves as on the matching poll cell. No gate-planned cell runs at 180 s. This **amends ADR 2408 decision 4**: `bedevents.WebhookPollSeconds` (180) remains only the default for an *ad hoc* webhook bed run that does not go through the plan. Webhook-path evidence in `events: sensitive` tests comes from structure, not timing: the per-leg delivery preflight (ADR 2408 decision 5, reused unchanged and now keyed on `cell.Webhook()`), a delivery observed in the bed's health or the leg's delivery count, an effect that lands while polls are held (`HoldPolls`, ADR 1978), or the App's delivery log.

5. **The planned cadence travels in its own variable.** The gate sets `E2E_CELL_POLL_SECONDS` per leg; `E2E_BED_POLL_SECONDS` stays the operator's override. The harness resolves the bed's `-poll` as override, then the cell's cadence, then the source's ad hoc default (`bedevents.ResolvePollSeconds`, pinned by `launch_contract_test.go`). Keeping them apart is what makes an override distinguishable from the plan. An override equal to the planned cadence is not an override. Any other value prints a loud banner, is recorded as `poll_override` on the leg, and the leg **runs and is archived but writes no ledger records**, so it cannot satisfy the cell it would otherwise cover. ("Does not count" means *not recorded*, rather than recorded with a flag every reader of the ledger would have to honour.)

6. **The event source of a leg is the cell's.** `E2E_EVENT_SOURCE` is set per leg from `Cell.EventSource()` (`tailscale` for a webhook cell, `poll` otherwise) and no longer read as a run-wide input by the plan. For compatibility, `E2E_EVENT_SOURCE=tailscale` on the gate is a **deprecated alias for `E2E_EVENTS=webhook`** (a partial run, with a notice). `E2E_EVENTS` (`poll | webhook | unset`) is the new filter, working like `E2E_AUTH_MODE`: a filtered run is partial and is not accepted by `gate coverage`. A direct `go test` of the harness still honours `E2E_EVENT_SOURCE`.

7. **Webhook cells run only on webhook-capable beds.** `bed-webhook-provisioning` is now per bed (`bedWebhookProblems`): a bed that has its own hostname, secret variable and auth key or stored login is *capable*. When the plan has a webhook cell (App auth planned and `E2E_EVENTS` not `poll`), the preflight refuses (exit 7) a run in which **no** bed is capable, naming every gap — a webhook cell is refused up front, never run poll-only — and merely reports incapable beds when another can serve. `MultiBedScheduler` hands a webhook cell only to a capable bed. The identity set is unchanged (`identitySet(auth)` depends on auth only; the transport adds no GitHub identity).

8. **On a webhook leg a missing webhook effect is a failure, not Inconclusive** (FR-005). The delivery preflight has proved delivery, so a test that expected a webhook effect and did not see it found a defect in ingestion. `webhookEffectMissing` fails the test on a webhook leg and stays `Inconclusive` otherwise; it is used by `TestWebhookChangeSurvivesReconcile`. Waits for a *starting state* (not a webhook effect) stay Inconclusive.

9. **`gate report` and the leg archive show the events dimension** (FR-006). `phases.json` gains an `events` block (dimension, cadence, override and, for a webhook leg, `deliveries`, `deduped`, `dropped`); `bed.json` gains `events`, `poll_seconds`, `poll_override`; `gate report` prints them per cell and invocation; the coverage and release-notes lines count against the full matrix (the four poll cells plus the two webhook cells). The counts come from inside `tests/gate`, with no engine change: deliveries from the App's delivery log over the leg's window (`DeliveryOps.AppDeliveries`, the newest page), dedupe and drop counts from the intake's `duplicate delivery` and `intake queue full … dropping` engine-log lines written during the leg. The engine exposes no such counters (only `last_delivery_at` and rejection counts); adding them would change `docs/state-machine.md` §7.8b and is left alone. A pruned or rotated log, or a very busy leg, under-reports; the summary records the source of the figures.

## Consequences

- A default (sparse) gate now includes an `app/on/webhook` cell and needs at least one webhook-provisioned bed, or must be run with `E2E_EVENTS=poll` as an explicitly partial run. The full matrix is six cells.
- The `events` classification of the 52 live tests is a judgement recorded with a reason per `sensitive` entry. Under-classifying weakens the sparse webhook cell; `E2E_MATRIX=full` is the safeguard for a release that changes ingestion.
- The set of `events: neutral` tests that cannot pass on a webhook cell for a reason unrelated to webhooks is discovered by a live full-plan run, and each such entry needs a `skip_ok_legs` pattern with a reason in the registry note. Two are known (above); there is deliberately no unexplained exception list.

## Verification limits

CI proves the planning, labels, ledger keys, registry rules, cadence resolution and scheduling with fakes. It cannot prove real tailnet delivery, the delivery preflight against a real App, or that every `events: neutral` test passes on a webhook cell at 60 s (SC-005): those can be verified only by a live full-plan run before a release.

# ADR 1142: Hookdeck as an App-Auth-Only Ingestion Transport, Kept Structurally Apart from `--webhooks`

**Date**: 2026-09-16
**Status**: Accepted
**Issue**: #1142 — multi-repo webhook subscription silently covers only one repo

## Context

`gh webhook forward` (the mechanism behind `--webhooks`, `engine/webhook.go`'s `webhookManager`) declares `--repo` as a singular flag. Fabrik's `buildGhArgs` appended one `--repo=` per managed repo; Cobra's `StringVar` overwrites on repeat, so only the last flag took effect — a multi-repo board silently received webhooks for one repo while the engine reported the stream healthy throughout. Confirming the bug also surfaced a harder constraint discovered mid-investigation: `gh webhook forward` refuses GitHub App installation tokens outright ("you do not have access to this feature") — a CLI feature gate, not a permission shortfall, and unfixable by any App permission grant. This ruled out every remedy the issue originally considered for App-auth deployments (org mode, per-instance identities, accept-poll-only) simultaneously, since all three still route through `gh webhook forward`.

Pruefer had already built and tested a complete alternative transport for exactly this purpose: `pruefer/events/hookdeck/`, a Hookdeck-based `EventSource` implementation, built under ADR-1254 explicitly as a low-risk place to prove out an event-driven ingestion pattern "before touching Fabrik's own webhook infrastructure," and hardened by ADR-1563's drop accounting and signature-drift escalation after a real (if Pruefer-internal) silent-failure incident. Under the per-account private-App model (#1722), a GitHub App has exactly one webhook URL and one secret covering every repo the installation is granted — there is no per-repo subscription to get wrong, so `--repo`-is-singular has no analogue for this transport.

This ADR records why the fix does not touch `gh webhook forward`'s existing behavior at all (R6: PAT-mode keeps it, made observable rather than replaced) and instead extracts Hookdeck into an engine-usable package as a second, App-auth-only ingestion mode — plus the four load-bearing implementation decisions that are not otherwise discoverable from the diff.

## Decisions

### 1. `event_source: hookdeck` is a config axis structurally independent of `--webhooks`, never merged into or gated by it

`Config.EventSource` (`engine/engine.go`) is a separate field from `Config.Webhooks`, with its own pair of refusal functions in `engine/github_app_auth.go` — `RefuseHookdeckWithoutGitHubApp` (Hookdeck requires App auth; it has no PAT-mode equivalent, since it consumes the App's own webhook secret, which doesn't exist without an App) and `RefuseHookdeckWithWebhooks` (the two transports are mutually exclusive: `gh webhook forward` is PAT-only, Hookdeck is App-auth-only, so a config enabling both is always contradictory). Both are wired into `New()` alongside — not inside — `resolveGitHubAppAuth`'s existing App-auth-specific checks (GHES refusal, `RefuseWebhooksWithGitHubApp` from #1752/#1753).

This was the deciding design constraint, not an incidental one: #1752 (open and unmerged at Plan time) was independently adding `RefuseWebhooksWithGitHubApp` to refuse App auth + `--webhooks`. Had this issue's new mode been implemented as a value *of* `cfg.Webhooks`, or required `resolveGitHubAppAuth` to special-case around #1752's refusal, the two issues would have raced to write overlapping guard logic with subtly different wording or behavior depending on merge order. A structurally separate field means `--webhooks` refuses App auth exactly as #1752 wrote it, unaware `EventSource` exists at all, and `event_source: hookdeck` is refused independently under PAT mode or alongside `--webhooks` — the two guards can never collide because they never share a code path.

### 2. Config naming mirrors Pruefer's `event_source`/`hookdeck.*` convention, not Fabrik's `FABRIK_*`-direct style

`EventSourcePoll`/`EventSourceHookdeck` constants, `Config.HookdeckAPIKeyEnv`/`HookdeckWebhookSecretEnv` — each field names an environment variable holding the actual secret (indirection, not the secret itself), exactly `pruefer/config.go`'s `hookdeck.api_key_env`/`hookdeck.webhook_secret_env` shape. Flags: `--event-source`/`--hookdeck-api-key-env`/`--hookdeck-webhook-secret-env`, env vars `FABRIK_EVENT_SOURCE`/`FABRIK_HOOKDECK_API_KEY_ENV`/`FABRIK_HOOKDECK_WEBHOOK_SECRET_ENV`, following `cmd/root.go`'s existing `--webhooks`/`FABRIK_WEBHOOKS` pattern for how the flag/env-var pair itself is wired. An operator already running Pruefer with Hookdeck recognizes the shape immediately, and it is the natural fit for two binaries sharing the same extracted package. The literal default env var names differ from Pruefer's own (`FABRIK_GITHUB_WEBHOOK_SECRET` here vs. Pruefer's `PRUEFER_GITHUB_WEBHOOK_SECRET`) since this is Fabrik's own secret value, not one Pruefer's process also reads — the two need not (and in a mixed Fabrik+Pruefer deployment, must not) collide on the same env var name by default.

### 3. A minimal shared `eventIngestionManager` interface, not a parallel type hierarchy — and echo-check is deliberately not part of it

`engine/ingestion.go` defines `eventIngestionManager`, covering exactly the methods `poll.go` and roughly 40 scattered call sites already invoke unconditionally through `e.webhookMgr`: `IsHealthyOrStartingUp`, `IsDisabled`, `Stop`, `UpdateRepos`, `RegisterEcho`, `RegisterEchoIfSubscribed`, `MatchEcho`. `*webhookManager` already satisfied this method set without any change; `Engine.webhookMgr`'s field type changed from concrete `*webhookManager` to this interface, so every existing call site (health check, `UpdateRepos`, the `RegisterEcho*` sites) compiles and behaves identically regardless of which transport (if either) is active.

`hookdeckManager` (`engine/hookdeck.go`) implements `RegisterEcho`/`RegisterEchoIfSubscribed`/`MatchEcho` as no-ops, and `IsDisabled` unconditionally `false`. This is not an oversight: gh-webhook-forward's echo-check mechanism exists specifically to infer "the subprocess *looks* alive but isn't actually delivering," a failure mode Hookdeck does not have — its `OnHealth` callback reports genuine WebSocket connectivity directly, so replicating the mutation-echo heuristic on top of it would be pure, unmotivated duplication of a signal already available natively. Likewise, `IsDisabled` has no App-level analogue to gh-webhook-forward's per-repo 422 circuit breaker — there is nothing per-repo to get a 422 on, since one App webhook covers every granted repo uniformly.

Two behaviors that *are* transport-specific — the coverage re-check (`checkWebhookHookCoverage` for gh-webhook-forward, `checkHookdeckInstallationCoverage` for Hookdeck) and health-state transitions on cache drift (`transitionHealthState`) — are deliberately **not** part of the shared interface. `reconcileLoop` (`engine/reconcile.go`) is retyped to accept `eventIngestionManager` but recovers the concrete type via a type switch for these two behaviors, rather than growing the interface to fit them. Both concrete managers expose a `transitionHealthState(WebhookHealthState, string)` method with the same signature (structural, not interface-enforced), so `reconcileLoop`'s `transitionMgrHealthState` helper can call either without duplicating the drift-driven health logic per transport.

### 4. `DropReason`'s existing 10-value set moves unchanged; the engine only ever emits the 6 transport-side ones

`internal/events.DropReason` (extracted verbatim from `pruefer/events/events.go`, ADR-1563) keeps all 10 values rather than being trimmed or forked into an engine-specific subset. `hookdeck.Source.Config.OnDrop` only ever fires the 6 transport-side reasons (`DropSignatureMissing`/`Invalid`, `DropMalformedEnvelope`/`Attempt`/`Payload`, `DropDedupe`) regardless of caller; the other 4 (`DropUnwatchedOwner`, `DropUnwatchedRepo`, `DropReviewInFlight`, `DropPRNotOpen`) are raised by `Daemon.ReviewFromEvent` — Pruefer-review-domain-specific code that never moves with the extraction. Trimming the type would only remove four unused constants at the cost of two divergent copies of an otherwise-shared type; `hookdeckManager.DropCounts()` simply never accumulates against the four it can't see.

### 5. `engine/webhook.go`'s `verifySignature` is retired in favor of the extracted `internal/events.VerifySignature`

Both were byte-for-byte identical HMAC-SHA256 implementations, deliberately duplicated per ADR-1113's "no shared imports between `engine` and `pruefer`" — a constraint that already had two precedent exceptions (`internal/selfupgrade`, `internal/githubauth`) before this extraction added a third (`internal/events`). Once both call sites were one import away from the same function, keeping two copies was unmotivated duplication with zero behavioral upside; `engine/webhook.go` now calls `events.VerifySignature` directly, and the local copy plus its dedicated tests were removed (call-site coverage in `engine/webhook_test.go` confirms the wiring instead).

### 6. PAT-mode's one-effective-repo behavior is unchanged; only its observability changes

The intuitive fix — one `gh webhook forward` subprocess per repo — remains unvalidated: the suspected one-session-per-account limit (documented in the issue body, corroborated by an operator's own config comment and by five concurrent Fabrik instances yielding exactly one live forwarder) was never empirically confirmed, since doing so would require creating real webhook subscriptions against real repos from an unattended agent. Rather than gate this issue on that experiment, R6 keeps `webhookManager`'s existing single-subprocess design and instead makes its one-effective-repo behavior **visible**: `supervise()`'s repo-list construction is now deterministic (sorted, not map-iteration-order-dependent), every subprocess (re)start logs the actually-effective subscribed repo or org, a startup-and-periodic-reconcile-tick assertion (`checkWebhookHookCoverage`, backed by the new `github.HasForwardingHook`) verifies a forwarding hook actually exists per managed repo, and any gap is surfaced as a `CoverageNote` alongside the existing connectivity health state (`tui.WebhookStatusEvent`). If a future issue refutes the session-limit finding, subprocess-per-repo becomes its own follow-up design — this issue does not need to anticipate it.

## Consequences

- **Positive**: An App-auth deployment now has a real-time ingestion path at all — previously, App auth + wanting anything faster than polling was a dead end, since `--webhooks` is unconditionally refused for App auth (#1752) and had no App-compatible alternative until this issue.
- **Positive**: `boardcache/delta.go`'s seven typed handlers are completely unmodified — both transports funnel into the exact same `deltaFn` closure `poll.go` already built for the PAT-mode path (`cacheImpl.ApplyDelta` + `applyLayer1StatusRefresh`), confirming Research's finding that the delta-application layer was never the problem, only the producer.
- **Positive**: R5's "the silence is the bug" guarantee is mechanism-independent by construction — both coverage checks write into the same `CoverageNote` field, so a caller checking webhook health never needs to know which transport is active to learn about a coverage gap.
- **Trade-off**: `internal/events/hookdeck`'s `SetLogf`/`logf` remains process-global package state (inherited unchanged from the Pruefer extraction) — fine for two independent binaries (`fabrik`, `pruefer`), but means a future same-process merge of the two would need to revisit this before either could run with an independent logging convention. Not a problem today; worth remembering if that day comes.
- **Trade-off**: The Hookdeck transport requires new operator-facing setup entirely outside Fabrik's own code — enabling the GitHub App's webhook and pointing it at a Hookdeck account is a manual prerequisite (documented in `docs/USER_GUIDE.md`'s § Event-Driven Ingestion via Hookdeck), not something `fabrik init --github-app` or any other Fabrik command automates.
- **Accepted risk, unchanged from ADR-1254/ADR-1563**: Hookdeck's CLI-session protocol is reimplemented from observed behavior, not a documented/versioned public API — a future wire-format change on Hookdeck's side would need a fix in `internal/events/hookdeck`, exactly as it would have needed one in `pruefer/events/hookdeck` before the extraction. The extraction changes where this code lives, not this pre-existing risk.
- **Deferred, not resolved**: the PAT-mode per-account session-limit question (Decision 6) is still open. R6's design is compatible with either outcome, but a future issue refuting the limit would need to design subprocess-per-repo supervision from scratch — this ADR does not attempt that design.

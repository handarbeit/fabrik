# ADR 1893: App Mode Runs Without an Operator Identity

**Date**: 2026-09-27
**Status**: Accepted
**Issue**: #1893 — App auth: run without an operator identity (no user, no PAT; commits, locks and mentions as the App)
**Relates to**: [ADR-007](007-label-based-locking.md), [ADR-1713](1713-engine-github-app-auth.md), [ADR-1846](1846-app-auth-https-git-credential-helper.md), #1754 (no ADR file — routed self-recognition through `selfLogin()`)
**Reverses**: the exception in `selfLogin()`'s doc comment (from #1754) that `fabrik:locked:<user>` and `LocalLockAcquired` "must keep using `e.cfg.User`".

## Context

Under GitHub App auth (#1713) posting, API calls and pushes already ran as the installation. Everything else still used the human operator's `cfg.User`: the startup `user is required` check, the git author on every commit, the lock label and its tie-break, the `@mention` in "awaiting input", spawned-child assignees, the TUI stop comment, and (via `cfg.Token`) the release-upgrade check. An App-mode deployment therefore still needed a username and could still carry a PAT, and authored commits as a person while pushing as `<slug>[bot]`.

## Decision

Under App auth the engine resolves one **App identity** at construction (`engine/app_identity.go`) and every site above reads it through an accessor. Each accessor returns the exact previous `cfg.User`-based value when `e.ghAppAuth == nil`, so PAT mode is unchanged by construction (R6).

**Lock identity: `<slug>-<6 hex>`, instance-distinct.** The hex is the start of `sha256(hostname NUL abs(fabrikDir))`. The label never contains `[bot]`. `fabrik:locked:` is 14 characters, so the identity is capped at 36; the slug is truncated to 29 characters, deterministically (the hash keeps truncated slugs apart). We rejected "one installation ↔ one instance": a foreign `fabrik:locked:<slug>` label would be indistinguishable from our own, so every check silently misbehaves — the `label != lockLabel` skip test reads another instance's lock as ours, `runStartupCleanup` of a second instance strips the first's live lock, and the lexicographic tie-break degrades to "both win" (the case ADR-007 calls unsupported). A derived identity keeps all existing lock logic correct with no new machinery. A general configurable `instance:` config key was rejected as scope growth; review of the PR found that a container/pod hostname changes on every restart and would strand a crashed run's lock every time, so a narrow env-only override was added: `FABRIK_INSTANCE_ID` replaces the hostname in the hash, and startup logs the derived label. Known cost: renaming the host or moving `fabrikDir` orphans a crashed instance's old label until removed by hand (documented). An over-long label silently disables locking (a failed label add is only logged), so the bound is enforced by construction and covered by a test.

**Legacy lock sweep.** After a PAT→App switch a crashed instance may leave `fabrik:locked:<user>`, which now reads "locked by another instance" and strands the item. `runStartupCleanup` removes exactly `fabrik:locked:<cfg.User>` (App mode, `user:` still set) from items with no live local worker. Sweeping every foreign `fabrik:locked:*` was rejected: it would kill a live second instance's lock. The configured user is read only to name that label and is never used as an identity (R8). Nothing ties that label to this instance, so review added an age gate: a label applied less than 2h ago (`legacyLockMinAge`), or whose age cannot be read, is left in place with a log line — a live PAT-mode instance running as the same user would otherwise lose its lock, while a stranded label is recoverable by hand. A label with no recorded apply event is swept. The 2h window is a heuristic — no process can see whether another process is alive — so it only matters when a PAT-mode and an App-mode instance share a username and a board: a PAT-mode stage longer than 2h (possible with no `max_wall_time`) could still have its live lock swept when the App-mode instance starts.

**Commit identity.** `user.name = <slug>[bot]`, `user.email = <bot-user-id>+<slug>[bot]@users.noreply.github.com`, the ID from `GET /users/<slug>[bot]` (new `(*gh.Client).FetchUserID`), resolved once in `New()`. A failed lookup is **soft**: a loud startup warning and the ID-less `<slug>[bot]@users.noreply.github.com` (still authored by the App, not avatar-linked). Failing startup over an avatar link was judged disproportionate.

**Existing bare clones — marker protocol.** `setIfUnset` never overwrites, so a migrated deployment's clones would keep the operator identity Fabrik itself wrote. In App mode Fabrik records what it wrote in `fabrik.managed-name` / `fabrik.managed-email`. A local value is overwritten only when it equals its marker (Fabrik wrote it — this also upgrades the ID-less email once a lookup succeeds; the upgrade is one-way, so a later transient lookup failure never downgrades an ID-bearing email back to the ID-less form) or, with no marker, equals the legacy `<cfg.User>` / `<cfg.User>@users.noreply.<host>` form. Anything else — an operator's own value, or a value edited after Fabrik wrote it — is preserved, satisfying R2's "never override a local identity". Limitation: with `user:` also cleared, the legacy form is unknown and the old value is treated as the operator's; unset it by hand. PAT mode calls the unchanged `setCommitterIdentity` and writes no marker keys.

**Notifications (R4).** "Awaiting input" mentions the item's human assignees, else its human author, else nobody. GraphQL reports `Bot.login` without `[bot]`, so `author` gains `__typename` and a `Bot` login is normalized to `<login>[bot]` at parse time (the precedent for review authors); REST logins already carry the suffix and `FetchProjectItem` now fills `Author`. The engine additionally excludes any login whose `[bot]`-stripped form equals the App's own slug, covering shallow/cached items. GraphQL `Issue.assignees` is a `User` connection, so it needs no typename. Spawned children inherit the parent's *human assignees* (not the author); an HTTP 422 on them (unassignable in the child's repo) is retried once with none rather than aborting the batch — an unassigned child beats a failed spawn, and unlike PAT mode's `cfg.User` nothing here was misconfigured by the operator. PAT mode still fails loud.

**No PAT in App mode (R5).** `releaseUpgradeToken` returns `""`: the release repo is public on github.com, while the installation token is scoped to the customer's organization. `claudeGHToken` is `""` (the live installation-token override always won anyway), and `New()` zeroes `cfg.Token` after the existing "PAT configured alongside App" log so "no PAT" is structural. Per-site audit of the remaining `cfg.Token` reads: daemon paths — fixed as above; `engine/startup.go`'s push-access message is already App-aware; `fabrik upgrade` and `fabrik watch` are operator-run CLIs that work without a token (`watch` merely omits PR/CI status) and are justified as operator-side; non-App `init --create-board` needs a PAT by nature; `fabrik repair-board` **gains an App path** (`appBoardClient`, reusing `runGitHubAppSetup`'s adopt flow, with `--token` still winning) because it would otherwise be unusable on an App-only deployment; `tests/e2e/harness.go` is test infrastructure. Operator-side git over SSH remains an explicit operator choice.

**Startup and init (R1, R7, R8).** `user is required` is skipped when App auth is intended; a still-configured `user:` is tolerated, ignored, and logged once. `fabrik init --github-app` does not prompt for a username, the `--user` help and the config template describe it as PAT-mode-only, and the banner prints the App installation instead of a user.

**Sim seam.** `SetGitHubAppModeForTest`'s zero-value Reconciler carries no bot login, which would key the lock on an empty slug. `SetGitHubAppIdentityForTest(slug, botUserID, instanceKey)` supplies one (and lets a scenario model two instances); an App-mode engine with no identity gets a fallback slug so `fabrik:locked:` can never be produced.

## Consequences

- App-mode deployments need no username and no PAT; commits are authored by `<slug>[bot]`.
- Two local instances sharing one installation stay distinguishable and the ADR-007 protocol holds unchanged; ADR-007's "identical identities unsupported" now only concerns PAT mode with a shared `user:`.
- Not verifiable in the sim or unit tests, and left to the live App-auth e2e legs (#1861): commit-avatar linking of the `<id>+<slug>[bot]` email, label creation with the hashed suffix, and GitHub's real 422 on an unassignable assignee.

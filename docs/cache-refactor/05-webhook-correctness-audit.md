# Webhook Correctness Audit

**Date:** 2026-07-26 against commit `c3a8f26` (branch `fabrik/issue-957`). **Read this after** `01-state-inventory.md`, `04-phase4-audit.md`, and `adrs/003-polling-over-webhooks.md`.

## §0 Executive summary

This audit answers one question for every cached-state category the engine reads: **if webhooks are disabled or unhealthy, does the poll loop alone still converge on the correct GitHub state?** Per ADR 003 (`003-polling-over-webhooks.md`), the answer must always be yes — webhooks exist to cut latency and API spend between polls, never to supply logic the poll path itself lacks.

`#955` proved one violation of that invariant (the `LightReconcile`/`Reconcile` ticker was lexically nested inside `if e.cfg.Webhooks`) and this issue's discussion turned up two more of a *different* shape while looking for others: not a webhook-gated code path, but a **stale-cached-deep-field freshness trap** — a deep field (`item.BlockedBy`, `item.Comments`) served from cache under a freshness gate keyed on the item's `updatedAt`, where the underlying GitHub mutation (removing a dependency, posting a comment mid-race) doesn't reliably bump `updatedAt`. The trap has nothing to do with webhooks per se — it fires identically whether webhooks are on or off — but it produces the same symptom as a webhook gate (an item stranded indefinitely) and was discovered by the same audit, so it's catalogued here alongside the webhook-coupled categories.

## §2 The `blockedBy` fix (this issue)

**Root cause, precisely stated:** it is not that `checkDependencies` "trusts a stale field" — it never sees anything but what the deep-fetch layer hands it. `boardcache.CacheImpl.FetchItemDetails` (`boardcache.go:642-693`) only calls `c.store.Apply(itemstate.ItemDeepFetched{...})` — the mutation that would refresh `BlockedBy` — on a cache **miss or stale** path. Removing a dependency via the REST dependencies API does not bump the blocked issue's `updatedAt`, so the cache is judged fresh and the Store is never touched. The staleness is a **missed refresh**, not a stale-but-present read.

**Fix:** `checkDependencies` (`engine/dependencies.go`) now computes `alreadyBlocked` up front and, when `alreadyBlocked && len(item.BlockedBy) > 0`, performs one cache-bypassing `e.client.FetchItemDetails` call (the raw `GitHubClient`, not `e.readClient`) before evaluating open dependencies. On success, the corrected `BlockedBy` is used for that evaluation and written back via `e.store.Apply(itemstate.ItemDeepFetched{...})` so other Store readers (e.g. `PushUnblockObserver`) see it too. On failure, it logs a warning and falls back to the existing (possibly-stale) list — non-fatal, matching Go-conventions guidance for non-fatal engine errors.

**Why this needs no new cooldown:** `checkDependencies` only runs for an already-blocked item once its `dep-blocked` `CooldownAt` has expired (`itemMayNeedWork`, `engine/item.go:260-269`) — that gate is the existing #576 wake-loop mitigation, and the live re-read piggybacks on it for free. First-time blocking is unaffected (`alreadyBlocked` is false), since that `BlockedBy` came from a genuinely fresh deep-fetch (first population is always a cache miss).

**Known, accepted asymmetry:** the fix's `ItemDeepFetched` write-back does not, by itself, make `PushUnblockObserver`'s `BlockedByChanged` trigger fire for the "edge fully removed" case — `OnChange` explicitly no-ops when `BlockedBy` becomes empty after a mutation (`engine/observers.go`, covered by `TestPushUnblockObserver_BlockedByChanged_NoOpWhenBlockedByEmpty`). This is fine: `checkDependencies`'s own `len(openDeps) == 0` branch removes the label directly using the now-fresh local list, so correctness never depended on the observer noticing — only latency does (the label clears within one poll cycle either way, since the push path was already not the mechanism here). Documented as a deliberate non-fix, not an oversight; revisiting it is a separate, small, out-of-scope follow-up if ever needed.

## §3 Open items for future audit (not fixed by this issue)

These are recorded here per this issue's scope ("Redesigning webhook architecture broadly... [is] out of scope"; "category 6... beyond what's needed to document" is explicitly excluded) — they are **not** confirmed correctness gaps, just categories this audit's method (look for a deep field gated on `updatedAt` freshness with no live-read fallback) flags as structurally similar to the two confirmed traps (`blockedBy`, comments):

- **Merge-queue membership** (`LinkedPRIsInMergeQueue`/`LinkedPRIsMergeQueueEnabled`, `engine/merge_queue.go`). Same shape as `blockedBy`: GraphQL-only, no webhook delta, `updatedAt`-gated deep-fetch, no live-read fallback. Unlike `blockedBy`, there is no confirmed live repro of a queue-membership change that fails to bump `updatedAt` — GitHub's merge-queue transitions are plausibly always accompanied by a PR or project-item mutation that does bump it, but this has not been verified. If a future incident reproduces staleness here, the `blockedBy` fix in `engine/dependencies.go` (and the pattern in ADR-074, see below) is the template to follow.
- **General PR-field staleness** (title/state/draft drift outside the confirmed linkage-healing gap `verifyAndHealLinkage` already covers). No confirmed live repro; unaudited beyond that one gap.
- **Comment staleness at call sites other than `preImplement`'s Plan-comment check.** `recoverMissingPlanComment` fixes the one call site with a confirmed live repro (#982). Other code that reads `item.Comments` (e.g. comment-processing dispatch in `engine/comments.go`) has not been individually audited for the same freshness-trap shape.

## §4 Method

For each category: (1) find every `boardcache/delta.go` webhook handler that mutates it, (2) find whether `LightReconcile`, a targeted live re-read, or the deep-fetch freshness gate itself provides a poll-only path to the same state, (3) check for a confirmed live reproduction in this issue's discussion thread or linked issues, (4) classify **optimization** (webhooks strictly redundant with poll) or **correctness** (poll alone was, or plausibly could be, insufficient). §3's items are the categories where step (2) found no live-read fallback but step (3) found no confirmed repro — flagged for future audit rather than fixed speculatively, consistent with this issue's explicit scope boundary against redesigning webhook architecture broadly.
